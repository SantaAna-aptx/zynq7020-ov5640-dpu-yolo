# 实测性能数据

> 全部为板端实测值。数据来源：应用自身的周期统计日志（`[LOOP]` / `[INFER]`）、
> HTTP `/stat` 端点、以及独立于应用之外的摄像头帧率测量。

## 1. 摄像头帧率（独立测量）

**不依赖应用**的一次测量，用 Python 轮询相机行计数器（`0x41220000`，
即 `line_cnt_r[11:4]`，取值 0..44）：

| 项 | 值 |
|---|---|
| 采样点数 | 263,423 |
| 采样间隔 | 22.8 µs |
| 观察窗口 | 6.00 s |
| 行计数器回绕次数 | 45（= 45 帧） |
| **推出帧周期** | **133.33 ms** |
| **推出帧率** | **7.50 fps** |

**这个数字是本系统的硬上限** —— 显示帧率不可能超过它。

## 2. 逐阶段耗时

### 2.1 优化前（单线程耦合，60 帧平均，两次采样一致）

| 阶段 | 耗时 (ms) | 占比 |
|---|---|---|
| grab（等帧边界 + memcpy 1.4 MB） | 58.9 | 14.7% |
| cvt（RGB565→BGR，OpenCV NEON） | 6.5 | 1.6% |
| pre（letterbox 416×416 + 量化） | 55.4 | 13.8% |
| **dpu（硬件推理）** | **125.5** | **31.4%** |
| decode（YOLO 解码 + NMS） | 60.7 | 15.2% |
| draw（画框 + 状态栏） | 11.3 | 2.8% |
| **jpeg（编码）** | **81.2** | **20.3%** |
| **合计** | **399.5** | **→ 2.4 fps** |

### 2.2 优化后（显示线程，连续 4 次采样覆盖 240 帧）

```
[LOOP]  60 frames  7.4 fps | grab 34.0  cvt 6.8  draw 0.0  jpeg 80.5 | infer 191 ms, 0 boxes,  29 inferences
[LOOP] 120 frames  7.4 fps | grab 33.0  cvt 6.7  draw 0.0  jpeg 80.3 | infer 193 ms, 0 boxes,  58 inferences
[LOOP] 180 frames  7.4 fps | grab 33.8  cvt 6.3  draw 0.0  jpeg 80.0 | infer 193 ms, 0 boxes,  87 inferences
[LOOP] 240 frames  7.4 fps | grab 33.7  cvt 6.5  draw 0.0  jpeg 80.0 | infer 193 ms, 0 boxes, 115 inferences
```

| 阶段 | 耗时 (ms) |
|---|---|
| grab（含等帧边界） | 33.0 – 34.0 |
| cvt | 6.3 – 6.8 |
| draw | 0.0（测试场景无检测框） |
| jpeg | 80.0 – 80.5 |
| **显示通路合计** | **~120 ms < 133.33 ms** ✅ |

**决定性证据：`pre`（55.4 ms）与 `decode`（49.2 ms）从显示通路上消失了。**
四次采样一致（7.4 fps），说明稳定。

> `draw 0.0` 是因为实时场景没有检出目标（见 §5），不是绘制被跳过。

## 3. HTTP 推流

### 3.1 `/stat` 端点响应

```json
{"display_fps":7.5,"display_frames":794,"infer_ms":192,"inferences":381,"boxes":0,"clients":2}
```

| 字段 | 含义 |
|---|---|
| `display_fps` | 显示帧率（滑动窗口） |
| `display_frames` | 累计显示帧数 |
| `infer_ms` | 最近一次推理耗时 |
| `inferences` | 累计推理次数 |
| `boxes` | 当前检测框数量 |
| `clients` | 在线 M-JPEG 客户端数 |

> ⚠️ **判断"系统正在跑"不能只看一次 `/stat`。**
> 一次读到的响应，一个**陈旧或挂起的实例同样能返回**。
> 正确判据是**隔几秒读两次，`display_frames` 与 `inferences` 都在增长**。
> （本项目的 bring-up 脚本最初只检查响应体 > 20 字节，这个检查不足以排除陈旧实例。）

### 3.2 M-JPEG 带宽

| 项 | 值 |
|---|---|
| 观察窗口 | 8 s |
| 接收字节数 | 3,091,660 B |
| **带宽** | **377 KB/s** |
| 相当于 | 约 6.9 帧/s（略低于 7.5，差值来自测量窗口内的网络开销） |
| 单帧大小 | 约 52.8 KB（JPEG 质量 60） |

### 3.3 JPEG 参数的影响（实测，非估算）

| 项 | 质量 72 | 质量 60 | 变化 |
|---|---|---|---|
| 编码耗时 | 81.2 ms | 80.0 ms | **仅 −1.2 ms** |
| 单帧大小 | 66 KB | 52.8 KB | −20% |
| 带宽 | 177 KB/s | ~140 KB/s | −21% |

**结论**：降低 JPEG 质量**几乎不省时间**（耗时主要在色彩转换、DCT 与量化表，
质量参数只影响熵编码），但**能显著省带宽**。所以它只适合当带宽杠杆，不适合当提速手段。

> 这一条是本项目里**被实测否定**的一个优化假设（原预期省约 20 ms）。

## 4. 优化前后总览

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 显示帧率 | 2.4 fps | **7.4 – 7.5 fps** | **+208%** |
| 显示通路耗时 | 328 ms | ~120 ms | −63% |
| 框更新率 | 2.4 /s | 3.9 /s | +63% |
| 分辨率 | 1025×720 | 1025×720 | 不变 |
| 画面撕裂 | 无 | 无 | 不变 |
| 比特流 | — | **完全相同** | 零硬件改动 |
| 资源占用 | — | **完全相同** | 零增长 |

**同一个比特流**（md5 `54e99b97a838cdfb155c7b7cd72252fa`）跑出两个帧率，
所以这 3 倍增益**可证明是纯软件的**。

## 5. 关于 `boxes: 0`

进程统计里的 `boxes 0` 需要解释，避免被误读为故障：

| 事实 | 说明 |
|---|---|
| 同一模型在 `dog.jpg` 上 | 稳定检出 3 个正确目标（见 [`validation_scorecard.md`](validation_scorecard.md)） |
| 实时场景（对着房间） | `raw=0 nms=0` —— **场景中没有 COCO 类别的显著目标** |
| 数据确实在流动 | 实时帧的 `identical=1`（`run1=run2=-7280294`、`-7292533`），且**重复推理的置信度在 0.977 → 0.818 → 0.562 之间变化** |

置信度随真实画面变化而变化，同时 `identical=1` 恒成立 ——
这证明系统消费的是**真实变化的数据**，不是缓存或常量。

**判据总结**：`boxes=0` 本身不是故障信号；
"`identical=1` + 置信度随输入变化 + 帧计数在增长" 三者同时成立才说明链路正常。
