## 1. 选题背景与创新点

### 1.1 要解决的实际问题

边缘侧的实时视觉检测有一个具体的矛盾：**云推理的延迟与带宽不可接受，而通用处理器跑不动检测网络。**

以本作品的目标场景为例——把物体举到摄像头前，希望屏幕上**立刻**出现类别和框。
这条链路上有两个硬约束：

1. **延迟**：一次检测 200 ms 级的滞后在"举起来看一下"这个动作里是可感知的；
2. **带宽与隐私**：把 1025×720 的连续视频流送到云端，既占带宽也不适合某些场景。

FPGA 的价值在这里是可量化的：**同一个检测网络，在 Zynq-7020 的 DPU 上跑 125.5 ms，
而这片器件的通用处理器（双核 Cortex-A9 @666 MHz）跑同样的网络要慢一个数量级以上。**
所以把计算放进 PL 不是"为了用 FPGA 而用 FPGA"，而是这个场景下延迟预算的唯一出路。

### 1.2 前人做过什么，本作品补了什么

Xilinx/AMD 提供了 DPU 的参考设计（DPU TRD）与大量**静态图片**推理示例，
PYNQ 生态也有成熟的 Overlay + Jupyter 范式。
但这些材料的终点通常是"**在 `dog.jpg` 上跑出框**"。

**从"静态图片能出框"到"摄像头实时画面带框可看"，中间隔着一段真实工程。**
本作品补的正是这一段，并且把这段路上的判据全部做成了可测量的：

| 从参考设计到可用系统，必须解决的事 | 本作品的做法 |
|---|---|
| 摄像头数据要连续落进 DDR，且要被 PS 实时读到 | 自研 `frame_writer` 滚动写入（DPU TRD 的 VDMA 路径在本设计上无法工作，见 §3.4） |
| 静态图推理的"能出框"不等于"算得对" | 建立**黄金参考逐字节比对**（`identical=1`）+ 8 图标准答案验收 |
| 一份比特流里同时放摄像头与 DPU | 定位并修复了两个独立根因（配置不匹配、时钟比例），见 §4.2 |
| 推理 193 ms 会拖死画面刷新 | **显示/推理解耦**：显示帧率 2.4 → 7.5 fps，**硬件零改动** |
| 画面要给人看，而板子没有显示器 | HTTP M-JPEG 推流，浏览器直接看，**画面全程不落盘** |

### 1.3 创新点

按赛题评分中权重最高的"创新性与应用价值"（30 分），本作品的创新点集中在**工程判断**而非算法：

**① 用"非确定性"作为故障分类的判据。**
DPU 输出每次都不一样（15 个荒谬类别、越界坐标）。
通常的直觉是"错得离谱 → 去查配置"；本作品的关键判断是：
**配置错误会稳定地错，只有时钟/时序错误才会随机地错。**
据此直接转向时钟比例检查，从 IP 自己生成的约束文件
（`dpu_ip/dpu/ttcl/timing_clocks_xdc.ttcl` 里的 `set_multicycle_path 2`）
确认了两路时钟必须**精确** 2 倍，把 150 MHz 改回 200 MHz 后输出即逐字节一致。

**② 把"文档说不清楚的地方"变成可重跑的测量。**
"传感器行宽是多少"这个问题，配置值是 1280，而实测是 **1025**。
本作品没有继续争论，而是设计了一个**只依赖数据本身**的方法：
假设候选行宽、重排数据、计算相邻行相关系数、取最大者。
结果 1025 的相关系数是 **+0.9929**，1280 极低 —— 一次性定案。
（这个假设错误此前制造了一个"每 4 行重复"的假象，误导排查很久。）

**③ 用"把慢的移出关键路径"替代"把慢的变快"。**
显示通路自己只需要 94.4 ms，本来就能跑满传感器的 7.5 fps；
它之所以只有 2.4 fps，是因为**推理的 230 ms 串在同一个循环里**。
拆成两个线程、只通过检测结果交汇之后，显示回到 7.5 fps ——
**同一个比特流、同一个二进制模型、硬件完全未改动，帧率提升 208%。**

**④ 把"可复现"当作功能的一部分来交付。**
作品不只交出功能，还交出**让错误变成硬失败的检查**
（模型段计数门禁、IP 锁定门禁）、**能重跑的验证脚本**、
以及一份如实标注"已证实 / 未证实 / 已排除"的记录（见 §9）。

### 2.2 数据通路与内存映射

| 区域 | 物理地址 | 大小 | 用途 |
|---|---|---|---|
| 帧缓存 | `0x08000000` | 1,476,000 B | 摄像头写入、PS 读取（**必须在 `mem=` 之外**，见 §3.5） |
| CMA | `0x04800000` | 48 MB | DPU 张量（`cma=48M`） |
| DPU 寄存器 | `0x40000000` | 16 MB 窗口 | 控制与状态（签名 `0x0D9C13F1`） |
| DPU 签名 | `0x40F00000` | — | 探测用（`0x0C014450`） |
| 相机调试字 | `0x41220000` | 4 B | 行计数器 `line_cnt_r[11:4]`，取值 0..44 |
| 内核可用内存 | `0x00000000` | 120 MB | `mem=120M`，使帧缓存落在内核管理范围之外 |

### 2.3 时钟设计（本设计的核心约束）

| 时钟 | 频率 | 来源 | 驱动对象 |
|---|---|---|---|
| `FCLK_CLK0` | **50.000 MHz**（精确） | PS `FCLK0_CTRL = 0x00201400`（IO_PLL 1000 ÷ 20） | `clk_wiz` 输入、`frame_writer`、`S_AXI_HP3` |
| `clk_out2` (`m_axi_dpu_aclk`) | **100.000 MHz** | `clk_wiz`（VCO 1000，MULT_F=20，DIVIDE 10/10/5） | DPU 数据面 + 指令 |
| `clk_out3` (`dpu_2x_clk`) | **200.000 MHz** | 同上，`DIVIDE2=5` | DPU 内部 2x 域 |
| `cmos_pclk_clk` | 约束 100 MHz（实际 84 MHz） | 摄像头 PCLK | `cam_top` 采样域 |
| `clk_24m` | 24.000 MHz | MMCM（VCO 1200，DIVCLK_DIVIDE=2，MULT=48，CLKOUT0=÷50） | OV5640 XCLK |

> **`clk_out3` 必须精确等于 `clk_out2` 的 2 倍。**
> 这不是时序偏好：DPU IP 自己生成的约束
> （`dpu_ip/dpu/ttcl/timing_clocks_xdc.ttcl`）里写的是
> `set_multicycle_path 2 -setup -from dpu_2x_clk -to m_axi_dpu_aclk`，
> 说明 **2x 域的状态机按"2 个 2x 周期 = 1 个 1x 周期"的节拍工作**，
> 这是 RTL 的功能假设。100 MHz 与 150 MHz 不是整数倍关系，相位持续漂移，
> 结果就是"每次跑出来的推理结果都不一样"。

## 3. 软硬件划分依据与接口设计

### 3.1 划分原则

| 功能 | 放在 | 依据 |
|---|---|---|
| 摄像头并行接口采样、跨时钟域、成帧 | **PL (RTL)** | 84 MHz 的字节流需要逐周期对齐；用软件无法保证确定性时序 |
| 帧数据落 DDR | **PL (RTL)** | 由摄像头节奏驱动，不占用 CPU |
| 目标检测推理 | **PL (DPU IP)** | 通用处理器跑不动：DPU 125.5 ms vs A9 慢一个数量级以上 |
| 预处理（letterbox + 量化）、解码、NMS | **PS (C++)** | 与输入尺寸/网络结构强耦合，用软件改起来快；DPU 只接受定长张量 |
| 画框、JPEG 编码、HTTP 服务 | **PS (C++)** | 纯数据搬运与格式转换，且需要与网络栈交互 |
| 显示与推理的并发 | **PS（双线程）** | 见 §4.3：这是**关键路径划分**，不是计算划分 |

**一句话概括划分依据**：**凡是"必须与外部信号保持确定时序"的放 PL；
凡是"需要灵活变更或与软件栈交互"的放 PS；
而"耗时但不必与显示同步"的，放到独立线程上。**

### 3.2 摄像头接口（DVP 并行）

| 信号 | 方向 | 约束/处理 |
|---|---|---|
| `cmos_pclk` | 输入 | `create_clock -period 10.000 -name cmos_pclk_clk`（按 100 MHz 约束，实际 84 MHz） |
| `cmos_vsync` | 输入 | **低有效，RTL 中取反后使用** |
| `cmos_href` | 输入 | 行有效；**注意：本板 HREF 一行内可能有多个脉冲** |
| `cmos_data[7:0]` | 输入 | RGB565，**每 2 个 PCLK 一个像素** |
| `cmos_xclk` | 输出 | 24 MHz，**由 MMCM 的 LOCKED 门控**（未锁定则关闭） |
| `cmos_scl` / `cmos_sda` | 输出/双向 | SCCB @ **33 kHz**，SDA **开漏**，`IOBUF.T` 由数据值驱动 |
| `cmos_pwdn` | 输出 | **必须拉低**（模组上拉电阻在原理图中标注为 DNP） |
| `cmos_reset` | 输出 | **必须拉高**（悬空会让传感器停在复位态） |

**真实行宽是 1025 像素，不是配置值 1280。**
一帧 = 1025 × 720 = 738,000 像素 = 1,476,000 字节。
`frame_writer` 不依赖摄像头的行长信号，而是**自己数像素**生成帧边界
（`REAL_FRAME_PX = 738000`）—— 因为 HREF 与 tlast 在本板上不可靠。

### 3.3 采集通路（自研 RTL）

| 模块 | 职责 | 关键设计 |
|---|---|---|
| `rtl/ov5640_cam_top.v` | DVP 采样、跨时钟域、成帧、AXIS 输出、SCCB 主机 | 见下表 |
| `rtl/frame_writer.v` | 把 AXIS 流滚动写入 DDR 固定区域 | **零寄存器**：单拍 64 位 AXI 写，纯顺序滚动，不做行距假设 |

`cam_top` 中值得说明的四处设计：

1. **自愈式 SCCB 配置**：配置完成后观察 PCLK 自由计数器，
   若 PCLK 不出现则每约 2.5 s 重跑整张 252 项配置表，直到传感器开始出时钟为止。
   理由是**写操作没有任何反馈** —— 一次配置可能永远留下一个沉默的传感器。
2. **粘滞 ACK 探针**：latch 一个"从机把 SDA 拉低过"的位并暴露给软件。
   因为 SCCB 写阶段的第 9 位是 "don't care"，**不能用它判断设备是否存在**。
3. **AXIS 握手合规**：1 级保持寄存器 + 背压
   （`can_issue = (~axis_valid_r) | axis_consumed`）。
   同步读 FIFO 的 `rd_data` 在 `rd_en` 之后一拍才有效，
   所以**读使能不能依赖它自己的输出**（否则永久死锁）。
4. **跨时钟 FIFO 的格雷码指针必须同步进"对面"时钟域**：
   读指针同步进写时钟用于 `wr_full`，写指针同步进读时钟用于 `rd_empty`。
   接反会让 `wr_full` 由读域寄存器组合驱动 BRAM 写使能，
   形成一条裸的跨时钟路径（本项目实测 WNS −9.212 ns，是全设计唯一失败的时钟对）。

### 3.4 为什么不用 VDMA

AXI VDMA 是常规选择，但在本设计上走不通，原因是四条同时存在：

1. 数据流在 S2MM 启动前就到达，把 `ERR_INTERNAL` / `ERR_FSZ_MORE` 永久锁存
   （通道复位清不掉）；
2. `CR` 的 Fsync 源选择位必须置位，否则 IP 去听一个未连接的端口；
3. Block Design 的 AXIS 接口**没有携带 TUSER**（缺 `HAS_TUSER`），
   网表里有这个网络但 IP 从来收不到；
4. `C_USE_S2MM_FSYNC=0`（自由运行）配置下该 IP **无法在时序内实现**，
   配置进 PL 的设计是死的。

**处置**：把 `cam_top` 配置后的静默窗口从 11 帧延长到 130 帧让软件先启动 S2MM，
最终**删除 VDMA，改用自研 `frame_writer`**（单拍 64 位 AXI 写直接进 `S_AXI_HP3`）。
代价是失去了 VDMA 的帧同步能力，改为自己数像素生成帧边界。

### 3.5 内存与启动参数

```
fatload mmc 0:1 0x01000000 image.ub          # 必须低地址：FIT 内 DTB 偏移 0x3F2BE4
setenv fdt_high 0xffffffff                   # 禁止 U-Boot 把 DTB 搬到 RAM 顶端
setenv devicetree_load_address 0x01000000
setenv bootargs console=ttyPS0,115200 earlyprintk root=/dev/mmcblk0p2 rw \
       rootfstype=ext4 rootwait init=/bin/sh mem=120M cma=48M
bootm 0x01000000
```

| 参数 | 为什么是这个值 |
|---|---|
| `0x01000000` | `image.ub` 内的 DTB 在偏移 `0x3F2BE4`。若加载到 `0x10000000`，DTB 落在约 260 MB，**超出 `mem=120M` → 内核在 `Starting kernel ...` 后永久沉默** |
| `fdt_high=0xffffffff` | 否则 U-Boot 把 DTB 重定位到 RAM 顶端（实测 `0x1fff9000` = 512 MB），同样够不着 |
| `mem=120M` | 把摄像头帧缓存 `0x08000000`（128 MB）**挡在内核管理范围之外**；同时保证 `0x40000000` 不被内核分配 |
| `cma=48M` | DPU 张量靠 CMA。U-Boot 的 `bootargs` **完全覆盖** DTB 里的值（DTB 里的 `cma=256M` 装不进 120 MB） |
| `init=/bin/sh` | 板子没有可用的自启动（旧的自启脚本会在坏比特流状态下 `insmod` 导致内核 oops） |

## 4. 优化过程与性能资源对比

### 4.1 先量化：帧率"台阶效应"

设相机帧周期 `T_cam = 133.33 ms`（7.5 fps，实测）、单次循环总耗时 `T_proc`，则

```
T_total = ceil(T_proc / T_cam) × T_cam          fps = 1 / T_total
```

**为什么是台阶而不是平滑下降**：每一轮循环都以"等下一个帧边界"结束，
所以一轮的总时间必须是帧周期的整数倍；`ceil()` 的代价是每显示一帧丢掉 `ceil−1` 个传感器帧。

| `T_proc` | `T_total` | fps |
|---|---|---|
| < 133.3 ms | 133.3 ms | **7.5** |
| 133.3 – 266.7 ms | 266.7 ms | 3.75 |
| 266.7 – 400.0 ms | 400.0 ms | **2.50** ← 解耦前 |
| 400.0 – 533.3 ms | 533.3 ms | 1.88 |

### 4.2 解耦前的逐阶段耗时（基线）

单线程循环，60 帧平均，两次采样一致：

| 阶段 | 耗时 (ms) | 占比 |
|---|---|---|
| grab（等帧边界 + memcpy 1.4 MB） | 58.9 | 14.7% |
| cvt（RGB565→BGR，OpenCV NEON） | 6.5 | 1.6% |
| pre（letterbox 416×416 + 量化） | 55.4 | 13.8% |
| **dpu（硬件推理）** | **125.5** | **31.4%** |
| decode（YOLO 解码 + NMS） | 60.7 | 15.2% |
| draw（画框 + 状态栏） | 11.3 | 2.8% |
| **jpeg（编码）** | **81.2** | **20.3%** |
| **合计** | **399.5** | **→ 2.4 fps** |

阶段和与总耗时吻合。**DPU 31% + JPEG 20% + 解码 15% + 等待 15% + 预处理 14%。**

### 4.3 优化一：把慢的移出关键路径（解耦）

**关键判断**：显示通路自己只需要 `grab 33.7 + cvt 6.5 + draw ~3 + jpeg 80.0 ≈ 120 ms < 133.33 ms`，
**本来就够跑满相机帧率**。它之所以被拖到 2.4 fps，是因为推理的 230 ms 串在同一个循环里。

**做法**：拆成两个线程，**只通过检测结果（归一化坐标）交汇**。

| 设计要点 | 说明 |
|---|---|
| 唯一共享状态 | `g_boxes` + 一把小锁。**锁的持有时间被限制在 5 ms 的 memcpy 上** |
| 预处理放置 | 55.4 ms 的预处理发生在**私有副本**上，不占锁 |
| 帧传递 | 用序号计数器而非条件变量 —— 推理只关心最新帧，**中间帧自动丢弃** |
| 无撕裂的论证 | 一次读取约 5 ms，而写入一帧需 133.33 ms。读在帧边界（行计数器回绕到 0..2）之后**立刻**开始，**读指针始终跑在写指针前面**，读到的每个字节都属于上一帧的完整数据 |

**代价**：画面滞后一个相机帧周期（133.33 ms，对预览无影响）；
检测框滞后约 253 ms（`5 + 6.4 + 55.4 + 125.5 + 49.2`），框更新率 3.9 次/秒。
接受的理由：**125.5 ms 的 DPU 是硬件下限，只能在"画面变慢"和"框变慢"之间选一个**。

### 4.4 优化二：解码路径的扁平化（微优化）

`detect()` 里 26×26 层构造了 676×3 = 2028 个 `vector<vector<vector<float>>>`。
改为扁平数组：**decode 60.7 → 49.2 ms（−11.5 ms）**，风险极低且可用 `RAWOUT` 逐字节比对验证。

**⚠️ 这里有一条重要的反例**：同一轮里还试了"JPEG 质量 72 → 60"，
**预期省 20 ms，实测只省 1.2 ms**（81.2 → 80.0）。
原因：JPEG 的耗时主要在色彩转换、DCT 与量化表，**质量参数只影响熵编码**。
→ **"降质量换速度"这条路不成立**，它只适合当带宽杠杆（单帧 66 → 52.8 KB）。

**更重要的是**：这一轮微优化总共省了 12.7 ms，**帧率一点没变** ——
`340.6 ms` 和 `327.8 ms` 都落在同一级台阶里（`ceil = 3` → 400 ms）。
省下的 12.7 ms 被"等待时间"原样吃掉（等待从 58.9 涨到 71.6 ms）。
**这就是"先用公式判断在哪一级台阶，再决定是否优化"的价值。**

### 4.5 优化前后性能对比

| 指标 | 解耦前（基线） | 解耦后 | 变化 |
|---|---|---|---|
| **显示帧率** | 2.4 fps | **7.4 – 7.5 fps** | **+208%** |
| 显示通路耗时 | 328 ms | **~120 ms** | −63% |
| 显示通路构成 | grab/cvt/pre/dpu/decode/draw/jpeg | **grab/cvt/draw/jpeg** | 移除了 pre 与 decode |
| 检测框更新率 | 2.4 /s | **3.9 /s** | +63% |
| 分辨率 | 1025×720 | 1025×720 | 不变 |
| 画面撕裂 | 无 | 无 | 不变 |
| **比特流** | `unified_clkfix_sw.bin` | **完全相同** | **零硬件改动** |
| **资源占用** | 同上 | **同上** | **零增长** |

> **同一个比特流（md5 `54e99b97a838cdfb155c7b7cd72252fa`）在同一个二进制上跑出了 2.4 fps 与 7.5 fps 两个结果**，
> 所以这 3 倍增益**可证明是纯软件的**。
> 这也是对赛题"合理使用片上资源，避免以显著的资源代价换取有限的性能收益"的正面回应：
> **本次性能提升的资源代价是 0。**

### 4.6 资源占用（最终实现，`report_utilization` 实测）

| 资源 | DPU OOC 单独 | **整个设计** | 器件可用 | 整个设计占比 |
|---|---|---|---|---|
| Slice LUTs | 34,019 | **37,338** | 53,200 | **70.18%** |
| Slice Registers | 63,101 | **67,932** | 106,400 | **63.85%** |
| Block RAM Tile | 123 | **123.5** | 140 | **88.21%** |
| DSP48E1 | 212 | **212** | 220 | **96.36%** |
| Slice | — | **13,057** | 13,300 | **98.17%** ← 最紧 |
| BUFGCTRL | — | 4 | 32 | 12.50% |
| MMCME2_ADV | — | 2 | 4 | 50.00% |
| Bonded IOPADs | — | 130 | 130 | 100% |

**结论**：DPU 单独就吃掉了约 91% 的 LUT、**96.36% 的 DSP** 和 **88.86% 的 BRAM**。
**DSP 与 BRAM 已见底，没有任何余量去放大或复制加速器** ——
这就是为什么"再堆一个 DPU"或"换更大的模型"在本器件上不是选项，
也是为什么选择**降低关键路径耗时**（软件）而不是**提高加速器吞吐**（硬件）的原因。

> 一条相关的资源教训：一个 1024×18b 的异步 FIFO，用跨时钟域 read-first 语义写出来
> 综合成了约 **19,000 个触发器**而不是 BRAM；改写成标准 BRAM 模板后**省下 3,500 个 slice** ——
> 这正是"DPU + 摄像头"这个组合最终能塞进 7z020 的原因。

### 4.7 时序收敛结果

| 指标 | 数值 | 失败端点 |
|---|---|---|
| **WNS** | **+0.718 ns** | 0 / 144,296 |
| **WHS** | **+0.051 ns** | 0 / 144,256 |
| WPWS | +2.000 ns | 0 / 72,192 |

`All user specified timing constraints are met.`

> 值得记录的是：**在本项目历史上时序从未收敛过**（WNS 长期在 −7.0 至 −10.5 ns 之间）。
> 真正的转折点不是加约束，而是**修正跨时钟 FIFO 的架构错误**
> —— 见 §3.3 第 4 条。**"时序不收敛"有时根因不在约束，而在 RTL 的结构。**

### 4.8 被评估并否决的方案

| 方案 | 预期收益 | 否决理由 |
|---|---|---|
| 直接降分辨率（1025×720 → 800×562） | 编码 80 → 50 ms | 标签文字变糊，而"能读出识别结果"正是本页面的核心价值 |
| JPEG 单独开线程 | ~81 ms | 需双缓冲，同步错误表现为**间歇性撕裂**（最难查的一类 bug）；不如整体解耦 |
| 预测帧边界替代轮询 | 58.9 → ~5 ms | 依赖帧周期稳定，但 **OV5640 自动曝光会随光线改变行时间**；预测早了会读到正在写的帧 → 撕裂 |
| 提高相机帧率（改寄存器表 + 重建比特流） | 周期 133→33 ms | 根因很可能是自动曝光拉长行时间，**缩短曝光会让图像变暗、增加暗部噪声 → 小目标漏检**；摄像头通路本身花了很久才稳定 |
| **DPU 超频**（2x 200 → 250/300 MHz） | 125.5 → ~100 ms | 需重建比特流；**时序几乎不可能收敛**（该域在 150/300 MHz 下历史 WNS 为 −7.0/−7.2/−8.4/−9.4/−10.5 ns，而 100/200 MHz 是 +0.505 ns）；且**资源已见底**，超频后仍须重新验证计算正确性 |
| 换更小的模型 | 绕开 125.5 ms 下限 | 新模型要重过 `dnnc`、重跑 8 图标准答案、还要确保 DPU 特性开关与新模型匹配（可能又牵出一次比特流重建） |
| 更好的 NMS（best-class） | decode 60.7 → ~20 ms | **改变后处理语义**，会丢失 `identical=1` 的逐字节可验证性；解耦后 DPU 已不在显示路径上，收益不再必要 |

**说明**：这些否决理由比"我们这么做了"更有价值 ——
它们把结论变成了"在这个约束条件下为什么只能这么做"的推理。

赛题要求"说明功能正确性是如何确认的"。本作品采用了**三层递进的验证**。

### 5.1 第一层：RTL 仿真

`rtl/` 下有三个 testbench，用 `xvlog → xelab → xsim` 流程运行（归档于 `sim/`）：

| testbench | 覆盖对象 | 检查内容 | 结果 |
|---|---|---|---|
| `fw_tb.v` | `frame_writer` | 4 像素打包、写入指针回绕、帧边界对齐 | PASS |
| `cam_tb.v` | `ov5640_cam_top` | AXIS 打包、`sof` / `eol` 正确性 | **`[TB-PASS] 共校验 64 像素 / 4 帧, 错误 0`** |
| `cam_tb2.v` | `ov5640_cam_top` | 改成"数像素成帧"后的确定性仿真，**注入 tready 停顿** | PASS（128 拍、2 帧、errors=0、tdata 稳定） |

`cam_tb2` 会**主动注入下游背压**（每 97 拍停 23 拍），
用来验证 AXIS 握手在 `tready` 拉低时不会改变 `tdata` —— 这是修复"无条件弹出 FIFO"那个 bug 的回归测试。

### 5.2 第二层：黄金参考逐字节比对

**这是本项目最有说服力的验证手段。** 应用内建 `DETERM_CHECK`：
同一张输入图**连续推理两次**，逐字节比较两次的输出缓冲区。

```
DETERM_CHECK: run1=-7891502 run2=-7891502 identical=1
BOXES: raw=6 after_nms=3
```

**为什么这条自检特别有价值**：它能同时发现两类完全不同的故障
（时钟比例错误、输入缓冲区被输出覆盖），而这两类故障的**外在现象完全相同**。
有了它，任何改动引起的回归都会立刻暴露。

同一张 `dog.jpg` 的结果与历史 8/8 验收记录**逐字节一致**：

```
car    conf=0.880797  box=(434,74)-(709,174)
truck  conf=0.989013  box=(509,60)-(649,194)
dog    conf=0.679179  box=(108,167)-(396,533)
```

### 5.4 端到端闭环

| 层次 | 证据 |
|---|---|
| 比特流生效 | `0x40000000 = 0x0D9C13F1`、`0x40F00000 = 0x0C014450`（**不是**相信 `state=operating`，它是假阳性） |
| 时钟正确 | `0xF8000170` 读回 `0x00201400`；`cmos_pclk` 实测 84 MHz；2x/1x = 200/100 MHz |
| 摄像头出流 | 调试字 `0x41220000` 在 0..44 之间滚动；帧缓存 `0x08000000` 非零且随时间变化 |
| 帧率 | `[LOOP] 240 frames 7.4 fps`（连续 4 次采样一致） |
| 推流 | `/stat` 返回 `{"display_fps":7.5,"infer_ms":192,"inferences":381,"clients":2}`；实测 377 KB/s |
| 画面质量 | 1025×720 真实场景可辨认；相邻行相关 **+0.9929**、相邻列相关 **+0.995** |

> 而 `identical=1` 始终成立 —— 说明消费的是**真实变化的数据**，不是缓存或常量。

## 7. 技能包的提炼过程

### 7.1 提炼方法

1. **先做矛盾扫描**：把项目里关于同一件事的**所有说法并列**，逐条按证据强度裁决。
   这一步找出 **13 处互相矛盾**，其中 **2 处推翻了先前写进项目 README 的结论**：
   - 某两个摄像头寄存器的补丁**未达成目标**（补丁后行宽仍为 1025，并未恢复 1280）；

3. **每篇保留"提炼过程"**：记录当时错误地以为是什么、以及是什么观察扭转了方向。
4. **可执行的东西做成脚本**，而不是停留在描述。

## 8. 复现说明

完整步骤见 [`../skill/templates/zynq-power-cycle-bringup.md`](../skill/templates/zynq-power-cycle-bringup.md)
（断电上电 bring-up）与 [`../skill/templates/cross-compile-without-board-sysroot.md`](../skill/templates/cross-compile-without-board-sysroot.md)（交叉编译闭环）。
此处只列**复现前必须知道的前提**，这些是复现失败最常见的原因：

### 8.1 工具版本

| 工具 | 本项目使用 | 赛题推荐 | 说明 |
|---|---|---|---|
| Vivado | **2019.1** | 2026.1 或 2025.2 | ⚠️ **低于推荐版本**，见下 |

**为什么用 2019.1**：本作品的加速器是 **DNNDK v3.1 + DPU IP v3.0（Arch B1152）**，
这套工具链**绑定 Vivado 2019.1**；板子的根文件系统（PetaLinux 2019.1、内核 4.19.0-xilinx-v2019.1、
glibc 2.28）也是同一代产物。换用新版 Vivado 会导致 DPU IP 版本不匹配、
且板端驱动与库无法对应。

**脚本可复现性保证**：所有构建动作都由 Tcl / PowerShell 脚本完成，
不依赖 GUI 手工操作。工程脚本会**校验关键参数**（DPU 三个特性开关、时钟 2 倍关系），
不满足则 `exit 1` 拒绝出片。

### 8.2 复现前必须知道的六条前提

| # | 前提 | 不知道会怎样 |
|---|---|---|
| 1 | **板子没有自启动**，必须 `init=/bin/sh` 手动进入 | 以为上电就能跑，实际停在无 shell 状态 |
| 2 | **抓 U-Boot 的脚本必须在上电之前启动**（autoboot 窗口只有几秒） | 抓不到命令行，只能再断电一次 |
| 3 | **`reboot -f` 会让本板停机**（`Reboot failed -- System halted`），只能物理断电 | 以为可以软重启，把板子留在死状态 |
| 4 | **板子没有编译器**，任何软件改动都要在主机交叉编译后推送 | 在板子上找 gcc 找不到 |
| 5 | 板子**磁盘仅剩约 47 MB**，应用本身 9.1 MB | 传输失败或写满静默截断 |
| 6 | 串口**不要设置 `DtrEnable` / `RtsEnable`**，否则板子完全不应答 | 误判为板子死机 |

## 9. 已知限制与未证实项

### 9.1 已确认的限制

| 项 | 现状 |
|---|---|
| 画面帧率上限 | **7.5 fps**，被 OV5640 的输出帧率卡住（传感器实测 133.33 ms/帧）。要提高需改摄像头寄存器表并重建比特流，且缩短曝光会影响画质与识别率 |
| 检测框滞后 | 约 253 ms。快速移动的目标框会"飘" —— 这是 125.5 ms DPU 硬件下限的直接结果 |
| 开机自启 | 未做。断电后需运行 bring-up 脚本 |
| 滚动缓冲接缝 | 由于放弃帧同步改为纯像素计数，缓冲区里有一处滚动回绕接缝（位置取决于抓帧时刻）。对识别无影响 |
| 现场画面检出率 | 同一模型在 `dog.jpg` 上稳定检出 3 个正确目标；**实拍场景 raw=0 / nms=0**。原因是场景中无 COCO 类别的显著目标，不是链路故障（`identical=1` 成立证明数据在流动） |

### 9.2 ⚠️ 未证实项（如实列出）

以下内容在本项目中**没有被证明**。列出它们是为了避免把假设当成结论：

| # | 未证实项 | 实际情况 |
|---|---|---|
| 1 | 摄像头寄存器 `0x3820`/`0x3821` 补丁的效果 | 补丁的**目标没有达成** —— 补丁之后所有交付帧仍然是 1025×720，并未恢复 1280 |
| 2 | DVP 输入延迟的 `-clock_fall` 约束 | 被报告为"已应用并验证"，但**当前代码树里没有任何 XDC 包含它** —— 该约束只存在于叙述中，未落到文件 |
| 3 | 传感器 PWDN 接地是根因 | 接地并断电重启后**仍然零 ACK**，因此记为"已排除"而非"已修复" |
| 4 | 传感器 IO 电平域（1.8 V）与 FPGA bank（3.3 V）不匹配 | 记录为"最大嫌疑"，**未证实**；最终结论是"模组坏了或没供电" |
| 5 | 寄存器表长度常量截断 | `LUT_SIZE = 256` 使索引 258 的表项**永远写不出去**（已定位，未修复） |

### 9.3 一条未处理的 DRC 警告

```
[DRC REQP-1840] RAMB18 async control check: ... 
  driven by a register that has an active asynchronous set or reset.
  This may cause corruption of the memory contents and/or read values
```

出现在 `cam_top` 的跨时钟 FIFO 的 BRAM 上。
**当前画面干净**，但**如果出现随机坏行或噪声，应优先查这里**。
缓解措施已在 RTL 风格中：存储器的读写块不含任何复位。
