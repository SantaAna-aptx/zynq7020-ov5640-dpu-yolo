# 大模型协作记录

> 对应赛题 3.3.3.1 与 3.3.5.3 第 5 条：**须提交体现大模型协作过程的交互记录，
> 含提示词、模型回答与自我纠错轨迹**。
>
> 本文件如实记录本项目开发过程中与大模型协作的方式、实际使用的提示词、
> 以及**包括判断错误在内的**纠错轨迹。

---

## 1. 协作方式与分工

### 1.1 基本事实

| 项 | 内容 |
|---|---|
| 协作形式 | 会话式协作，贯穿整个开发周期（采集通路 → DPU 打通 → 实时推流 → 性能优化 → 文档整理） |
| 大模型承担 | 故障假说生成、日志与报错解读、脚本与 RTL 片段编写、文档撰写与结构化、**跨文件不一致的核查** |
| 人承担 | **上板执行与测量**、硬件接线与物理排查、判断哪个假说值得验证、最终决策与验收 |
| 关键约束 | 大模型**看不到板子**。所有硬件状态都必须由人转述或读回，这决定了提示词的写法（见 §2） |

### 1.2 一条贯穿始终的原则

**大模型擅长生成假说，但假说的验证必须在真实硬件上完成。**

本项目因此形成了一条固定的协作循环：

```
人：提供原始现象（完整报错 / 日志 / 读回值），不给结论
        ↓
模型：把现象分类 → 生成最小代价的对照实验 → 明确两种结果各意味着什么
        ↓
人：执行实验，把原始输出回传
        ↓
模型：据此收敛或推翻假说
        ↓
（循环，直到范围缩到可以动手改的最小集合）
```

**这条循环最直接的价值是省掉了昂贵的试错。**
本项目每次比特流重建约 50 分钟，而 DPU 的两个根因**全部在只读手段下定位完成，零次重建**。

## 2. 实际使用的提示词

以下三个模板在项目中反复使用，也一并作为技能包提交（见 [`../skill/prompts/`](../skill/prompts/)）。

### 2.1 提示词一：证据优先的故障定位

**使用场景**：故障现象模糊、可能原因多、试错成本高。

**核心内容**（节选）：

> 我在做嵌入式/FPGA 联调，遇到一个故障。**请先不要给修复方案**，按下面三步走。
>
> **第 1 步：把现象分类。** 先判断这个现象属于哪一类，并说明判断依据：
>
> | 类别 | 特征 | 通常指向 |
> |---|---|---|
> | 稳定地错 | 每次结果都一样，但就是不对 | 配置问题、参数不匹配 |
> | **随机地错** | 每次结果都不同 | **时钟/时序问题**、竞态 |
> | **第一次对，之后错** | 首轮正确，后续漂移 | 状态被污染、缓冲区被覆盖 |
> | 完全没反应 | 无输出、无报错 | 东西根本没被执行 |
> | 看起来成功了但没效果 | 命令/构建/加载都成功 | **生效的是上一次的东西** |
>
> **第 2 步：设计对照实验。** 给我一个只读的、一次只动一个变量的实验方案。
> 明确写出**两种可能结果分别意味着什么**。
>
> **第 3 步：只在第 1、2 步完成后，才给修复方案。**

**这张分类表的实际命中记录**：

| 现象 | 分类命中 | 直接结论 |
|---|---|---|
| DPU 输出每次都不一样（15 个荒谬类别、坐标 `(-1510,-5858)`） | **随机地错 → 时钟/时序** | 转向 2x 时钟比例检查，命中 |
| 连续推理"第一次对、后面错" | **第一次对 → 状态被污染** | 定位到输出写覆盖输入缓冲区 |

> **这两个问题的外在现象几乎完全相同，但根因完全不同。**
> 区分它们靠的不是更用力地看同一个现象，而是提示词逼出来的**更细的观察维度**
> —— "从第几次开始错"。

### 2.2 提示词二：分层自审

**使用场景**：被要求"全面检查一遍"时，防止退化成"用更肯定的语气复述已知的事"。

**核心内容**（节选）：

> **三条纪律**（违反任何一条的结论都不要写出来）：
> 1. **不基于记忆判断，基于读回数据判断** —— 每条结论必须附证据
> 2. **一次只改一个变量**，改完立即验证
> 3. **先观测后修改** —— 提出任何修改前先完成只读观测
>
> **六层清单**：环境健康 → 比特流/配置 → 硬件设计/BD → 设备树 → 根文件系统 → **运行时状态** → **执行链观测**
>
> **特别提醒这几类"看起来成功了"**：
> - 命令执行了但被 shell 拒绝
> - 状态字段说成功，但生效的是上一次的东西
> - 构建成功但你的参数没被采纳
> - 读到了陈旧的产物文件，却当成本次运行的结果

**实际作用**：这条纪律**直接纠正了一次被写进文档的误诊**（见 §3.1）。

### 2.3 提示词三：对照实验设计

**使用场景**：需要一次把范围缩小一半以上，而不是逐项试。

**本项目最成功的一次对照实验**：

```
同一块板 + 同一内核 + 同一驱动 + 同一张输入图，只换比特流
```

| 变体 | 结果 |
|---|---|
| 已知良好的比特流 | `identical=1` + 正确检出 ✅ |
| 出问题的比特流 | 配置不匹配直接退出 ❌ |

**一次实验把范围从"整个系统"缩到"两个比特流的差异"，进而缩到三个布尔参数。**

> **这次实验还有超出预期的价值**：它**顺带证伪了另一个无关的怀疑** ——
> 当时以为内存分配参数（CMA）有问题，而对照实验证明
> 已验收良好的比特流在同一内核、同一 CMA 配置下原样复现 8/8。
> **所以这次实验同时结束了两条排查线。**

## 3. 自我纠错轨迹

**这一节如实记录，包括大模型判断错误的案例。**

### 3.1 ⚠️ 一次被明确推翻的误诊：把内核挂死归因于内存分配参数

| 阶段 | 内容 |
|---|---|
| **现象** | 内核在 `Starting kernel ...` 之后**永久沉默**（无 panic、无输出、无响应） |
| **大模型给出的判断** | "`mem=120M cma=80M` 导致内核无输出死亡" |
| **后续动作** | 这个结论被**写进了项目文档**，并据此长时间调整 CMA 大小 |
| **推翻它的观察** | 翻出当天 16:03 的日志，看到一行一直被当成常规输出而忽略的内容：<br>`Loading Device Tree to 1fff9000, end 1ffff7c6 ... OK` |
| **真正的根因** | **`fdt_high` 没有设置**，U-Boot 把设备树重定位到 RAM 顶端（`0x1fff9000` = 512 MB），而内核只认前 120 MB —— **设备树够不着，与 CMA 无关** |
| **第二个诱因** | `image.ub` 加载在 `0x10000000` 时，其内部 DTB 子镜像（偏移 `0x3F2BE4`）落在约 260 MB，同样超出 120 MB |
| **修复** | 加载地址改为 `0x01000000` + `setenv fdt_high 0xffffffff` |

**为什么这个错误能持续**：U-Boot 的输出里**一直写着答案**（DTB 的加载地址），
只是没人去和 `mem=` 的上限做那个减法。

**纠错后固化的纪律**：这就是"**不基于记忆判断，基于读回数据判断**"这条纪律的来源。
如果当时要求"每条结论附证据"，就会立刻发现那个 CMA 结论**没有任何证据支持**。

> 这条误诊也说明：**大模型可以自信地给出错误结论，而且看起来很有道理。**
> 协作流程里必须有一个"这条结论的证据是什么"的检查点。

### 3.2 DPU 拒绝加载模型：从"硬件坏了"到"三个布尔开关"

| 阶段 | 内容 |
|---|---|
| **现象** | `[DNNDK] DPU configuration mismatch for kernel tiny_yolo - parameter: Conv+Leakyrelu, DPU kernel: Enabled, DPU IP: Disabled.` |
| **最初的错误方向** | 怀疑 DPU 硬件故障、比特流加载失败、内存不足，把时间花在读寄存器和调 CMA 上 |
| **转折点** | 回到报错的**字面意思**：`DPU kernel: Enabled, DPU IP: Disabled` —— 答案已经写在里面了，这是**配置对比**，不是硬件故障 |
| **关键方法** | 让 DPU **自己报**特性表（`dexplorer -w`），让模型**自己报**要求（`ddump -f ... -d`），逐项对照 |
| **根因** | BD 里 `dpu_eu_0` 的三个主开关设错：`CONV_RELU_ADDON=2`（应 3）、`POOL_AVERAGE=0`（应 1）、`LOAD_AUGM=0`（应 1） |
| **推导依据来源** | **IP 自己生成的 `dpu_ip/dpu/gui/dpu_eu_v3_0.gtcl`** —— 它给出了特性与开关的推导公式 |
| **代价** | 全程只读，**一次比特流都没重建** |

**同一实验的副产品**：顺带证伪了 §3.1 残留的 CMA 怀疑（见 §2.3）。

### 3.3 `identical=0`：把"非确定性"当作判据

| 阶段 | 内容 |
|---|---|
| **现象** | 特性全 `Enabled`、模型也接受了，但推理输出**每次都不一样**：15 个荒谬类别、框坐标 `(-1510,-5858)-(1997,6246)` |
| **关键判断** | **配置错误会稳定地错，只有时钟/时序错误才会随机地错** |
| **证据来源** | 不是本项目文档，而是 **IP 安装目录里的约束文件** `dpu_ip/dpu/ttcl/timing_clocks_xdc.ttcl`：<br>`set_multicycle_path 2 -setup -start -from $clk_2x -to $clk_1x` |
| **根因** | 该工程把 `clk_out3` 从 200 MHz 降到了 150 MHz（大概是为了让时序更容易收敛），**破坏了 2 倍关系**。100 MHz 与 150 MHz 非整数倍，相位持续漂移 |
| **修复** | `CLKOUT3_REQUESTED_OUT_FREQ` 改回 200 MHz，MMCM 参数与已验证配置**逐位一致** |
| **验证** | `identical=0` → `identical=1`，输出与历史 8/8 记录**逐字节一致** |

**纠错后的固化动作**：把"同图跑两次比对输出"做成应用的常驻自检（`DETERM_CHECK`）。
**此前该工程的 DPU 计算通路从未被验证过** —— 历史文档只记录过"DPU 签名寄存器能读出来"。
**"寄存器活着"和"算得对"是两件完全不同的事，这是整条线上最贵的一课。**

### 3.4 模型段被链接器静默丢弃

| 阶段 | 内容 |
|---|---|
| **现象** | 程序能正常编译、正常启动，只在第一次加载模型时报 `dpuLoadKernel failed` |
| **根因** | `objcopy` **保留输入文件的 `ET_DYN` 类型**，于是链接器把模型目标文件当成共享库处理，**悄无声息地丢掉它的全部段** |
| **修复** | `arm-linux-gnueabihf-elfedit --output-type=rel model.o` |
| **纠错后的固化动作** | 把"模型段数必须为 7"做成**构建门禁脚本**，一秒完成检查。<br>大模型参与把这个检查通用化并**在真实产物上实测通过**（识别 7 段、payload 9,022,093 字节） |

### 3.5 IP 被锁定，构建"成功"但参数没生效

| 阶段 | 内容 |
|---|---|
| **现象** | 改完参数直接构建，构建成功、时序收敛、出片成功，但板上的 DPU 特性**还是旧的** |
| **发现方式** | 回板上用 `dexplorer -w` 读回，发现与改动前一样 |
| **根因** | IP 处于 locked 状态时 Vivado **不更新它的综合检查点**，只打印警告然后沿用旧网表：<br>`WARNING: [Project 1-577] ... the out-of-date checkpoint will be used` |
| **附带难题** | 鸡生蛋：所有 `.dcp` 缺失时 `generate_target` 被拒绝（"contains locked IPs"），而解锁又需要生成产物 |
| **解法** | 先逐 IP `upgrade_ip`（锁定数 5 → 0），再 `generate_target` |
| **加的一道保险** | `upgrade_ip` **可能重置 IP 配置**，所以升级后**重新校验三个特性开关**，不满足就 `exit 1` 拒绝构建 |

**纠错后固化的认知**：**"构建成功"在 Vivado 里是有层次的** ——
综合成功、实现成功、时序收敛、出片成功，**都不能证明你的改动被采纳了**。

### 3.6 一个"从未运行过"的应用却给出了结果

| 阶段 | 内容 |
|---|---|
| **现象** | 联调脚本报告成功，也拿到了结果文件 |
| **根因** | 日志被重定向到 `/tmp/app.log`，而 **`/tmp` 在 `init=/bin/sh` 环境下不存在**。<br>shell 无法建立重定向，于是**整条命令被拒绝，应用从未启动** |
| **更坏的地方** | 脚本随后读到的是一张**上一次留下的结果图** —— 假阳性 |
| **怎么发现的** | 三张"新"图片的**字节数完全相同**，这个巧合暴露了问题 |
| **修复** | 日志写到确定存在的目录，并且**用内容标记判定成功**（grep 一个每次运行必定出现的字符串），绝不用"命令返回了"或"文件存在" |

### 3.7 最贵的一个假设：摄像头行宽

| 阶段 | 内容 |
|---|---|
| **假设** | "传感器配置为 1280 像素/行，所以行宽是 1280" |
| **后果** | 每行错位 255 像素，而 `255 × 4 ≈ 1020 ≈ 1025`，制造了一个**"每 4 行重复"的假象**。<br>这个现象从最早一版就存在，把排查方向持续引向 FIFO、时钟、行结束信号 |
| **转折点** | 放弃推理，改用**只依赖数据本身**的方法：<br>假设候选行宽 → 按该宽度重排数据 → 计算相邻行相关系数 → 取最大者 |
| **决定性结果** | 宽度 **1025**：相关系数 **+0.9929**（899 行）；宽度 2050（2× 谐波）：+0.9870；宽度 **1280：极低** |
| **修复** | `frame_writer` 改为**自己数像素**生成帧边界（`REAL_FRAME_PX = 738000`），不依赖任何摄像头信号 |

**这条经验被提炼成技能包的第一条**：**不要假设参数值；
当所有推理都对不上时，设计一个只依赖数据本身的测量。**

### 3.8 两次无效的"时钟坏了"测量

| 阶段 | 内容 |
|---|---|
| **现象** | 软件采样循环报告"XCLK 死：20000 次采样、0 次跳变、恒定 1"，**同一个结论得出过两次** |
| **根因一** | 用来短接信号的**跳线根本没装**。操作者说的"插好了"指的是换了主接线。<br>没有跳线时，SDA 只是被上拉电阻拉高 —— **"恒定 1"什么也证明不了** |
| **根因二** | 即使装了跳线，**用 GPIO 以约 1 µs 间隔采样无法观测 24 MHz 信号**（违反奈奎斯特，会混叠） |
| **纠错** | 该会话记录里**明确作废了此前全部"XCLK 死了"的结论**；改用绕开 MMCM 的诊断比特流（逻辑分频得到已知频率源） |
| **固化教训** | **在用负向测量下结论之前，先证明探针有效（做一个正对照）。**<br>悬空输入读出来就是恒定 1，有没有信号都一样 |

### 3.9 一次由大模型主导的核查：13 处日志矛盾

| 阶段 | 内容 |
|---|---|
| **任务** | 把项目文档提炼成技能包 |
| **意外发现** | 系统性地比对"关于同一件事的所有说法"后，找出 **13 处互相矛盾** |
| **其中最有价值的两条** | 都不是"说法不同"，而是**"声称已完成的修复，实际没有达成目标"**： |
| | ① 某两个摄像头寄存器的补丁，**目标没有达成** —— 补丁后所有交付帧仍是 1025×720； |
| | ② 一条输入延迟约束被报告为"已应用并验证"，**但代码树里根本找不到它** |
| **直接影响** | 这两条**推翻了先前写进项目 README 的结论**，已修正 |
| **固化的方法** | "**实测 > 代码 > 产物 > 文档 > 注释**"的权威顺序，以及
"**已证实 / 未证实 / 已排除**"的三档标注法 |

> 这一项是大模型协作**最能体现价值**的地方：它能耐心地把散落在多份文档里的说法并列比对，
> 而人做这件事时容易因为"记得已经改好了"而跳过。

## 4. 智能体工作流设计

### 4.1 固定循环（见 §1.2）

```
人提供原始现象  →  模型分类 + 设计对照实验  →  人执行并回传原始输出  →  模型收敛或推翻
```

**关键约束**：循环里**模型永远不直接下"修好了"的结论** ——
结论必须由人执行后回传的读回值或产物来支撑。

### 4.2 子任务并行

在文档整理阶段，把"从多份日志里提炼某一类经验"这类**互不依赖的读取密集型任务**
并行分派给多个子任务（例如同时提炼：摄像头踩坑、bring-up 与交叉编译、性能优化与解耦）。
每个子任务只回传结构化结果，不占用主流程上下文。

**这次并行的直接收益**：三个子任务各自独立读了 5–20 份文档，
回传的结果里包含了**主流程没有注意到的矛盾清单**（§3.9）。
如果串行处理，很可能因为"已经知道大概情况"而跳过这些核对。

### 4.3 门禁优先于描述

把能自动判定的东西做成**脚本**而不是描述：

| 门禁 | 检查 | 失败后果 |
|---|---|---|
| `check_dpu_model_sections.ps1` | 可执行文件里的模型段数是否为 7 | 否则上板加载模型才失败 |
| `check_ip_lock_status.tcl` | Block Design 是否有锁定 IP | 否则构建会沿用旧网表 |
| `build_cam_stream.ps1` 内置 | 编译后自动数 `.deephi` 段 | 同上 |

**两个检查合计不到两秒，能挡掉一次 40 分钟的构建或一次板上往返。**

## 5. 协作效果

| 维度 | 结果 |
|---|---|
| 疑难问题定位 | DPU 的**两个独立根因**全部**只读定位，零次比特流重建**（每次约 50 分钟） |
| 一次实验的双重收益 | "同一内核换比特流"同时定位了参数问题、并证伪了内存怀疑 |
| 被纠正的错误 | **至少 1 次被写进文档的误诊**（CMA）、**2 处写进 README 的错误结论**（寄存器作用）、<br>**2 次无效测量**（XCLK 探针） |
| 文档一致性 | 找出 13 处矛盾并逐条裁决 |
| 性能结果 | 解耦使显示帧率 2.4 → 7.5 fps，**硬件零改动** |

## 6. 反思：大模型在嵌入式工程里的能力边界

**做得好的**：把散落的信息并列比对、生成可验证的假说、
把一次成功经验抽象成可复用形式、不知疲倦地做重复核对。

**做得不好的（本项目实际发生过）**：

1. **会自信地给出没有证据支撑的结论**（§3.1 的 CMA 误诊，还被写进了文档）。
   → 对策：强制"每条结论附证据"。
2. **会顺着提问者的框架走**。当人说"DPU 好像坏了"，模型容易在"DPU 坏了"这个方向上找答案。
   → 对策：提示词里明确要求"**不要被我的猜测带偏**"，并要求**先分类再动手**。
3. **看不到硬件**，对"命令是否真的执行了"没有直觉。
   → 对策：所有远端操作都要有**内容级的成功断言**，不能相信返回码。

**最有用的一条协作纪律**：
**让模型先给现象分类、再设计对照实验、最后才提修复方案。**
本项目里这条纪律换来的直接收益，是省掉了数次昂贵的重建与上板往返。
