# 显示/推理解耦方案 — 设计、收益推导与把握度评估

> 2026-10-16 · 目标：把网页画面从 2.5 fps 提到摄像头上限 7.5 fps
> 本文先用实测数字做算术推导，再讲实现，最后给出每一项的把握度和风险

---

## 一、为什么解耦能提升：问题定位

当前是**耦合**的：一帧画面必须走完「预处理 → DPU → 解码 → 画框 → 编码」才能推出去，
所以总时间被 `DPU 125.5 + 编码 80 + 预处理 55 + 解码 49` 撑到 328 ms。

但**这两件事其实互不依赖**：

| 谁需要什么 | 频率需求 | 决定因素 |
|---|---|---|
| **看画面** | 越高越好（人眼要流畅） | 摄像头帧率、JPEG 编码 |
| **知道框在哪** | 每秒几次就够 | DPU 硬件（125.5 ms） |

**把 DPU 从显示路径上挪走，显示路径就只剩编码那点工作量。**

## 二、架构设计

### 线程划分

```
                    ┌─────────────────────────────────────────┐
   摄像头 DDR 帧 ──▶│ 显示线程（主循环）                        │
   0x08000000       │  wait_frame_start()                      │
                    │  memcpy → g_frame  ────┐                 │
                    │  cvtColor → BGR        │ g_frame_seq++   │
                    │  画上 g_boxes（加锁读） │                 │
                    │  imencode → publish    │                 │
                    └────────────────────────┼─────────────────┘
                                             │ 新帧通知
                    ┌────────────────────────▼─────────────────┐
                    │ 推理线程（另一个核）                       │
                    │  等 g_frame_seq 变化                      │
                    │  拷贝一帧（加锁，约 5 ms）                 │
                    │  cvtColor → BGR                          │
                    │  set_input_image（letterbox+量化）55 ms   │
                    │  dpuRunTask 125 ms                       │
                    │  decode + NMS 49 ms                      │
                    │  g_boxes = 新结果（加锁写）                │
                    └──────────────────────────────────────────┘
```

**两条路径唯一的交点是 `g_boxes`（一把互斥锁，加锁时间以微秒计）。**

### 为什么这样切分

| 设计选择 | 理由 |
|---|---|
| 显示线程**自己**做 cvtColor，推理线程**另做一次** | 显示线程要在图上画框，画完的图不能给推理用（框线会被当成图像内容，干扰检测）。多花 6.4 ms 换正确性，值得 |
| 推理线程**拷贝**一帧而不是直接读共享缓冲 | 预处理要 55 ms，持锁这么久会阻塞显示线程。锁内只做 5 ms 的 memcpy |
| 用**序号**而不是条件变量通知 | 推理线程只要"最新的帧"，不关心中间跳过的帧。序号轮询最简单，且天然丢帧 |
| 框用**归一化坐标**（0~1）传递 | 显示和推理的分辨率一致，归一化后就与具体像素无关，也不怕将来改分辨率 |
| 显示线程**绑核 0**，推理线程**绑核 1** | Cortex-A9 是双核，绑核后 CPU 工作真并行，避免调度抖动 |

## 三、收益推导（这一步决定"有没有把握"）

### 显示路径的新耗时

全部取自本次实测数字，不是估算：

| 步骤 | 耗时 | 来源 |
|---|---|---|
| memcpy 1.4 MB | ~5 ms | 实测 grab 扣除等待后的余量 |
| cvtColor RGB565→BGR | **6.4 ms** | 实测 |
| 画框（已知框，只画矩形+文字） | ~3 ms | 实测 draw 11 ms 扣除状态条后估 |
| **imencode JPEG** | **80.0 ms** | 实测 |
| **合计 T_proc(显示)** | **≈ 94.4 ms** | |

### 套用台阶公式

```
T_total = ceil(T_proc / T_cam) × T_cam
        = ceil(94.4 / 133.33) × 133.33
        = 1 × 133.33
        = 133.33 ms
```

**→ 显示帧率 = 7.5 fps**（等于摄像头帧率，即**已经跑满传感器**）

### 关键判据：余量

```
摄像头帧周期        133.33 ms
显示路径 T_proc      94.4 ms
────────────────────────────
余量                 38.9 ms   （41%）
```

**只要 T_proc(显示) 不超过 133.33 ms，就稳定输出 7.5 fps。** 现在有 41% 的余量。

### 推理路径（决定框的更新率）

| 步骤 | 耗时 |
|---|---|
| 拷贝一帧 | 5 ms |
| cvtColor | 6.4 ms |
| letterbox + 量化 | 55.4 ms |
| **DPU** | **125.5 ms** |
| decode + NMS | 49.2 ms |
| **合计** | **≈ 242 ms** → **框更新 4.1 次/秒** |

### 效果对比

| 指标 | 当前（耦合） | 解耦后 | 变化 |
|---|---|---|---|
| **画面帧率** | 2.5 fps | **7.5 fps** | **+200%** |
| 框更新率 | 2.5 fps | 4.1 fps | +64% |
| 框滞后 | ≈ 同帧（0） | 242~500 ms | **变差** |
| 帧率稳定性 | 稳定 | 稳定（不是抖动的跳帧） | 同 |

## 四、把握度评估：逐项说明我为什么认为能做到

### 判据本身是算术，不是估计

显示帧率等于 7.5 fps 的推导只依赖两件事：
1. **T_proc(显示) = 94.4 ms** ← 由四项实测数字相加
2. **T_cam = 133.33 ms** ← 独立测量（数行计数回绕，45 次/6.00 秒）

`94.4 < 133.33` 是确定的不等式，**没有估算成分**。

### 下界保护：最坏情况也不会比现在差

即使内存争抢让显示 T_proc 从 94.4 涨到 140 ms（涨 48%），结果是：

```
ceil(140 / 133.33) × 133.33 = 2 × 133.33 = 266.7 ms → 3.75 fps
```

**仍然比现在的 2.5 fps 好 50%。** 所以这是一个下界受保护的投资。

### 双核是真并行

`/proc/cpuinfo` 显示两个 `ARMv7 Processor rev 0 (v7l)` —— Cortex-A9 双核。
绑核后：
- 核 0：显示线程（94.4 ms/帧，其中 80 ms 是 CPU 密集的 JPEG 编码）
- 核 1：推理线程（242 ms/帧，其中 125.5 ms 是 DPU 忙、CPU 空闲）

**推理线程的 DPU 阶段 CPU 是空闲的，正好不占用显示线程需要的算力。**

### 内存带宽需要认真算（这是最需要留意的共享资源）

一帧原始画面 1.4 MB（RGB565），转成 BGR 后 2.2 MB。按每帧访问量算：

**显示线程每帧**
| 操作 | 流量 |
|---|---|
| memcpy（读 1.4 + 写 1.4） | 2.8 MB |
| cvtColor（读 1.4 + 写 2.2） | 3.6 MB |
| 画框（读改 2.2 的一小部分） | ≈ 0.4 MB |
| imencode（读 2.2 + 写 0.05） | 2.25 MB |
| **合计** | **≈ 9 MB → 68 MB/s** |

> ⚠️ 这里有个**必须去掉的浪费**：现有代码里 `disp = bgr.clone()` 会多拷 2.2 MB。
> 那是耦合时代的产物（原图要留着给后续用）。解耦后显示线程的 `bgr` 只用来画框和编码，
> **直接在上面画框即可，省掉这次 clone —— 少 4.4 MB 流量、约 3 ms**。

**推理线程每帧**
| 操作 | 流量 |
|---|---|
| 拷贝一帧 | 2.8 MB |
| cvtColor | 3.6 MB |
| letterbox 到 416×416 | 2.7 MB |
| **DPU**（读权重 8.8 + 读输入 0.5 + 写输出 0.7） | 10 MB |
| **合计** | **≈ 19 MB → 79 MB/s**（DPU 那 10 MB 集中在 125 ms 内，峰值更高） |

**两线程合计约 150 MB/s。** DDR3 在 7z020 上实测可用带宽通常 400–800 MB/s，
所以占 **约 20–38%**。

**结论：不构成瓶颈，但也不是完全无压力** —— 这正是"显示路径 38.9 ms 余量"要防的东西。
好在余量足够（41%），且兜底方案明确（降分辨率）。

## 五、风险清单与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| **内存/L2 cache 争抢让显示 T_proc > 133 ms** | **中低** | 掉到 3.75 fps（仍优于现在） | ① 绑核 ② 显示线程用 `SCHED_FIFO` 提优先级 ③ 若仍不够，把输出分辨率降到 800×562（编码 80→50 ms，余量涨到 69 ms） |
| **并发 bug（花屏/崩溃/死锁）** | **中** | 严重（画面坏或进程挂） | ① 只用一个共享点（`g_boxes`）+ 一个帧缓冲锁，锁粒度极小 ② 所有共享数据都在锁内访问，不做"锁外读同一块内存" ③ 先在本机做逻辑推演，上板后连续跑 5 分钟看 `/stat` 是否稳定 ④ 保留旧版程序，随时可切回 |
| **框滞后 242~500 ms 观感差** | 取决于场景 | 中 | **技术上无法解决**（DPU 125.5 ms 是硬下限）。只能用"标注检测时间戳"或"框超时淡出"来提示用户 |
| 摄像头帧率波动（自动曝光改变行时间） | 中 | 显示帧率在 7.5/3.75 之间跳 | 台阶公式天然吸收：只要 T_proc < T_cam 就跟得上；波动时最多偶尔跳一帧 |
| 推理线程吃满一个核导致系统响应慢 | 低 | 轻微 | 推理线程里 DPU 等待阶段本来 CPU 空闲；必要时加 `usleep` 让出 |

## 六、实施步骤（每步独立可验证）

### Step 1：把函数拆开（无行为变化，零风险）
把现在的 `detect_and_draw()` 拆成两个：
- `decode_boxes(task, sw, sh)` → 返回 `vector<Box>`（DPU 输出 → NMS 后的框，归一化坐标）
- `draw_boxes(Mat&, const vector<Box>&)` → 把框画到图上

**验证**：单线程下先串起来跑，画面应该与现在**完全一致**。

### Step 2：加推理线程（主要工作量）
- `g_boxes` + `g_boxmtx`
- `g_frame` + `g_framemtx` + `g_frame_seq`
- 推理线程：等序号 → 拷贝 → cvt → pre → DPU → decode → 更新 `g_boxes`
- 显示线程：把 `detect_and_draw` 换成 `draw_boxes(g_boxes)`

**验证**：
- `/stat` 的 `fps` 应从 2.5 升到约 7.5
- 画面流畅度肉眼可见提升
- 连续跑 5 分钟，检查有无花屏、崩溃、`clients` 计数异常

### Step 3：绑核 + 优先级（若 Step 2 的帧率没到位）
```cpp
cpu_set_t set; CPU_ZERO(&set); CPU_SET(1, &set);
pthread_setaffinity_np(pthread_self(), sizeof(set), &set);
```

**验证**：对比绑核前后的 `[LOOP]` 分段耗时，看显示路径是否更稳。

### Step 4（可选）：降输出分辨率
若想再往上，或 Step 2 的余量被吃掉：
- 输出 800×562 → 编码约 50 ms → T_proc(显示) ≈ 64 ms → 余量 69 ms
- 代价：标签变小（可补偿放大字号）

## 七、解耦之后，"提高摄像头帧率"的意义变了（修正之前的结论）

这是我上一份分析里**说得不准的地方**，需要更正：

| 阶段 | 显示帧率的决定者 | 提高摄像头帧率的收益 |
|---|---|---|
| **耦合时**（现在） | 台阶公式，T_proc = 328 ms | 2.5 → 3.0 fps（**+20%**，性价比低，还要冒画质风险） |
| **解耦后** | `min(摄像头帧率, 1/T_proc显示)` | 7.5 → **10.6 fps**（**+41%**）→ 此时摄像头才重新成为瓶颈 |

解耦后：
```
摄像头 7.5 fps  → min(7.5, 1/94.4ms=10.6) = 7.5 fps    ← 被摄像头卡住
摄像头 30  fps  → min(30,  10.6)          = 10.6 fps   ← 被 JPEG 编码卡住
摄像头 30fps + 输出降到 800×562 → min(30, 20) = 20 fps  ← 被编码卡住
```

**所以正确的顺序是：先解耦（把显示路径腾空）→ 再提摄像头帧率（此时收益才兑现）→ 若还不够再降分辨率。**

我之前把"提高摄像头帧率"排在最后、理由是"收益只有 20%"，那是针对**耦合**状态算的。
**解耦之后它的收益会翻倍到 41%，优先级应该提前** —— 但仍然排在解耦之后。

## 八、结论

| 项 | 结论 |
|---|---|
| **能提升吗** | **能，2.5 → 7.5 fps（+200%）**，且推导只依赖实测数字，不含估算 |
| **把握度** | **高**。判据是算术不等式 `94.4 < 133.33`，且最坏情况（争抢导致超时）也只掉到 3.75 fps，仍优于现在 |
| **主要不确定性** | 内存/L2 争抢有多大（可用绑核 + 必要时降分辨率解决） |
| **主要代价** | 框滞后 242~500 ms，快速移动时框会"飘" —— 这是 DPU 硬件的账，无法用软件消除 |
| **实现复杂度** | 中：一个推理线程 + 两把锁 + 一个序号；改动集中在 `main` 和函数拆分 |
| **可回退** | 是。保留当前 `cam_stream` 二进制，随时切回 |

**建议：做。** 收益是数量级的（+200%），下界受保护，且不碰硬件、不动已验证的比特流。
主要不确定性（争抢）有一个明确的兜底方案（降输出分辨率），不会陷入死局。
