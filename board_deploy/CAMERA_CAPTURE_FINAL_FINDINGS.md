# 摄像头采集 —— 根因分析与最终修复（对比老师参考工程）

> 参考工程：`E:\xilinxFPGAlessonFacilities\5640_sccb_hdmi__cep`（能正常出图的版本）
> 本项目采集链路：OV5640 → `rtl/ov5640_cam_top.v` → `rtl/frame_writer.v` → AXI/HP3 → DDR

## 一、结论摘要

对比参考工程后，找到了 **4 个根本差异**，加上我们自己定位的 **3 个缺陷**，合计 7 处修复。
修复后画面已是**真实场景**、行宽正确（1280）、相邻行相关 +0.977、相邻列相关 +0.995 ——
仅剩"垂直重复 4 次"一个收尾问题（修复已构建，待上板复验）。

## 二、四个根本差异（来自与老师的逐行对比）

| # | 项目 | 老师（工作） | 本项目（原） | 后果 |
|---|---|---|---|---|
| 1 | **PCLK 时序约束** | `create_clock -period 10.000`（100 MHz）| `42.667`（24 MHz）| ✗✗ **噪声真凶**：实际 PCLK 84 MHz，设计却按 24 MHz 分析，输入捕获路径从未被优化 |
| 2 | **VSYNC 极性** | `cmos_vsync_r1 <= ~cmos_vsync_i;`（取反）| 原样使用 | ✗ 帧同步边沿错误 → `tuser` 乱发 → 写指针反复复位 |
| 3 | **PLL `0x3035`** | `0x41`（注释：PCLK = 84 MHz）| `0x21` | ✗ 传感器时钟配置不一致 |
| 4 | **格式 `0x4300`** | `0x60`（RGB565）| `0x61` | ✗ 输出格式低半字节不同 |

参考工程关键代码（`uisrc/03_ip/uiSensorRGB565/uiSensorRGB565.v`）：

```verilog
cmos_vsync_r1 <= ~cmos_vsync_i;                 // 第 65 行：VSYNC 必须反相
wire vs_p = !cmos_vsync_r2 && cmos_vsync_r1;    // 反相后的上升沿
href_cnt <= cmos_href_r2 ? href_cnt + 1'b1 : 1'b0;
data_en  <= (href_cnt == 1'd1);                 // 每 2 个 PCLK 一个像素
```

## 三、我们自己定位并修复的缺陷

| # | 缺陷 | 证据 | 修复 |
|---|---|---|---|
| 5 | **字节配对 off-by-one** | 仿真精确复现：2560 字节只配出 1279 个像素 | 采集使能误用 `href_d && cmos_href`（延迟 HREF 与当前 HREF 相与），每行丢最后一个字节；改为与数据对齐的延迟 HREF |
| 6 | **固定 1280 像素分帧** | 实测 HREF 窗口与假设不符 | 改为完全按摄像头 HREF/VSYNC 分帧 + 1 级流水正确产生 tlast |
| 7 | **`frame_writer` 忽略 tlast** | 画面呈斜向剪切（逐行累积偏移）| 改为 tlast 推进到下一行、tuser 回帧首，行距固定 2560 字节 |

## 四、⚠️ 最重要的一条工程经验：OOC 构建陷阱

**症状**：RTL 改了、构建成功、时序收敛，但**板上行为毫无变化**。

**铁证**：相隔 3 小时、中间重写过 RTL 的两次构建，比特流**载荷逐字节完全相同**（md5 `dbb91ba7…`）。

**原因**：`cam_top` 是 Block Design 的 module reference，它在**独立的 OOC 子工程** `design_1_cam_top_0_synth_1` 里综合。**只 `reset_run synth_1` 不会让它重跑**，主综合会拿缓存的旧网表去实现。

**修复**：构建前强制重置所有 BD 的 OOC 子工程 —— 见 `board_deploy/rebuild_force_ooc.tcl`：

```tcl
foreach r [get_runs -quiet -filter {IS_SYNTHESIS && NAME =~ "design_1_*"}] { reset_run $r }
```

**验证方法**：每次构建后比对**去掉 160 字节头部后的载荷 md5**，必须与上一版不同。

## 五、上板验证流程（已验证可靠）

```powershell
# 1) 先开监听（会持续发中断键，抢占 U-Boot 倒计时）
powershell -File board_deploy\capture_and_fetch.ps1 -CatchSec 3600 -Tag <名字>
# 2) 板子断电 → 上电（必须真正断电，否则等不到 U-Boot）
```

脚本自动完成：打断 autoboot → `init=/bin/sh mem=120M`（DTB 钉在 0x01000000）从 SD 卡启动
→ 配网 → `wget` 拉比特流 → `fpga_manager` 载流 → FCLK0=50MHz + PL 复位 → 分块 mmap 抓整帧
→ `httpd` 发布 → PC 取回 → 转 PNG。

**已知坑**：
- `fdt_high=0xffffffff`（禁止 U-Boot 重定位设备树；未设置会被搬到 ~1003MB，超出 `mem=` 上限 → 静默挂死）
- `mem=120M`：让 `0x08000000` 落在内核 RAM 之外，整块读才安全
- `/dev/mem` 的 `read()` 越过内核 RAM 会返回 0 字节，**必须用 mmap**，且**大块 mmap 会挂死**（要每 64KB 一块）
- `/tmp` 是指向不存在的 `/var/tmp` 的坏符号链接，用 `/www`
- **不要**在 fpga_manager 重配置期间访问 PL 寄存器（会把 PS 打挂）

## 六、当前状态与收尾

**已验证正确**：
- 行宽搜索：**1280 为最佳匹配**（corr 0.977）；相邻列相关 **0.995**
- 调试字（两次 VSYNC 间行数/16）实测 **44 → 704 行**，与 720 行吻合
- 画面为**真实场景**（房间/窗户，可辨认）

**唯一剩余问题**：画面垂直重复 4 次，每次 180 行 —— 定量分析：

```
垂直周期 = 180 行，帧高 720 行        → 720 ÷ 180 = 4
传感器 VTS = 740 行，740 ÷ 4 = 185    → 同样是 4 倍
⇒ s_axis_tlast 每行触发 4 次（HREF 每行附带约 320 像素的毛刺脉冲）
```

**修复（已构建，md5 `e84ee7c6…`）**：`MIN_LINE_PX` 64 → **512 像素**
（真实行 1280 ≫ 512 ≫ 毛刺 320，既保留真实行又滤掉毛刺）。

### 6.1 该修复未彻底奏效，改用更稳健的方案

上板后垂直重复仍在（lag180 从 0.98 只降到 0.85）。进一步推理：

```
调试字 704 "行" ÷ 4 = 176 ≈ 180（实测重复周期）  →  两者自洽
⇒ line_cnt_r 把 HREF 毛刺也计入了；摄像头每帧实际约 176~180 个 HREF 脉冲组
```

**⇒ 结论**：只要几何依赖 tlast（HREF 派生的），就始终受制于摄像头的信号质量。
**改为让 `frame_writer` 用「像素计数」推进行**：每写满 **1280 个像素**就换到下一行，
`tuser` 只负责把指针复位到帧首。

这样几何**完全由像素数决定**，与 HREF/tlast 的毛刺无关 —— 仿真验证 PASS
（1280 beats、数据与地址全对）。

### 6.2 ⭐ 最终根因：摄像头真实行宽是 1025 像素，不是 1280

纯像素计数版消除了重复（lag180 → +0.05），但画面变成斜向拖影。对采集数据做**全范围行宽搜索**
（`measure_line_width.py`）得到决定性结果：

```
width 1025 (899 rows) : +0.9929   ← 最佳，远超其它候选
width 2050 (449 rows) : +0.9870   ← 2×1025，谐波
width 1280            : 极低
```

**真实行宽 = 1025 像素**（传感器配置为 1280，实际输出却是 1025）。
用 1280 渲染时每行错位 255 像素，而 255×4 ≈ 1020 ≈ 1025，所以**每 4 行重复一次** ——
这正是从最早一版就一直出现的 `lag4` 周期性与斜向拖影的根源。

**最终方案（三项配合）**：

1. `frame_writer` **纯顺序滚动写入**，不做任何行距假设（不依赖 tlast/tuser）
2. `ov5640_cam_top` **去掉 per-HREF 的字节相位强制**，让配对跨 HREF 边界连续
   （HREF 每行有多个约 512 像素的脉冲，逐脉冲强制相位会在画面里留下接缝，把图切成方块）
3. PC 端 `measure_line_width.py` **从数据实测行宽并据此渲染**

**行宽测量方法**：对候选宽度重排数据、计算相邻行相关系数、取最大者。正确宽度下相邻行
高度相似（+0.99），错误宽度下行内容互相错位（≈0 或为负）。

### 6.3 已知的残留现象

滚动缓冲没有帧同步，缓冲区里会出现**一处滚动回绕接缝**（位置取决于抓帧时刻），
对识别无影响；如后续需要彻底消除，可恢复一个受控的帧同步（`tuser` 仅用于把指针复位到帧首）。
