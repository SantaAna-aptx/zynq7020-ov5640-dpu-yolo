# 帧率优化方案 — 风险评估

> 2026-10-16 · 当前 **2.4 fps**（399.5 ms/帧）
> 本文所有数字都是**板上实测**，不是估算。测量方式：程序内分段计时，每 60 帧输出一次平均值。

---

## 一、实测基线（这是决策依据）

### 分段耗时（60 帧平均，两次采样一致）

| 阶段 | 耗时 (ms) | 占比 | 性质 |
|---|---|---|---|
| **grab** 等帧边界 + memcpy 1.4 MB | **58.9** | 14.7% | **等传感器出帧** |
| cvt RGB565 → BGR | 6.5 | 1.6% | 已最优（OpenCV NEON） |
| pre letterbox 416×416 + 量化 | 55.4 | 13.8% | 可优化 |
| **dpu 硬件推理** | **125.5** | 31.4% | **硬件下限** |
| **decode YOLO 解码 + NMS** | **60.7** | 15.2% | **可大幅优化** |
| draw 画框 + 状态条 | 11.3 | 2.8% | 可接受 |
| **jpeg 编码** | **81.2** | 20.3% | 可优化 |
| **合计** | **399.5** | | → 2.5 fps（实测 2.4） |

### 摄像头真实帧率（独立测量）

用 Python 轮询 `0x41220000` 行计数、数回绕：

```
samples      : 263423 (22.8 us apart)
wraps        : 45 in 6.00 s
frame period : 133.33 ms -> 7.50 fps
```

**传感器只有 7.5 fps。** 这直接锁死了两个东西：

1. **`grab` 的 58.9 ms 是必然代价** —— 进入等待的时刻相对帧相位是随机的（我们的处理时间不是 133 ms 的整数倍），所以平均要等半个帧周期 = 66 ms。实测 58.9 ms 与之吻合。
2. **整个管线的绝对上限是 7.5 fps**，而且只有在"每一步都几乎零耗时"时才能接近。

---

## 二、不可优化的硬约束

| 约束 | 数值 | 说明 |
|---|---|---|
| **DPU 推理** | 125.5 ms | 单核 DPU 跑 tiny_yolo 的物理时间。D3 验收记录里也是 125.5 ms。**唯一办法是超频或换模型，都不划算** |
| **摄像头帧周期** | 133.33 ms | 除非改 OV5640 寄存器（见方案 F） |
| cvt | 6.5 ms | 已用 OpenCV NEON 路径 |

**乐观下限估算**：dpu 125.5 + grab 58.9 = **184 ms**（4.3 fps 上限），这是"其他全部优化到极致且摄像头不变"的情形。

---

## 三、逐方案评估

风险等级定义：
- **极低** = 一行改动，可立即回退，结果可逐位比对
- **低** = 改动小，影响面清晰，有验证手段
- **中** = 涉及并发或语义变化，可能出现难复现的偶发问题
- **高** = 需要重建比特流或改变硬件时序，失败代价高

---

### 方案 A：NMS 改为 best-class（收益 40 ms）

**现状问题**：`apply_nms` 对 **80 个类别各做一次全排序**。候选框有几百个时，
复杂度是 `O(80 × N log N)`，还要为每个类别分配一次 `vector<bool> keep(N)`。

**改法**：先对每个框取置信度最高的类别（< 0.5 直接丢），然后**只按该类别分组**做一次 NMS。

| 项 | 评估 |
|---|---|
| 收益 | decode 60.7 → 约 20 ms（**省 40 ms，总帧时间 -10%**） |
| **风险** | **中** |
| 具体风险 | **改变了后处理语义**。原实现是 per-class NMS（一个框在多个类别下都可能保留），改后是 best-class NMS。理论上边界情况下输出框会略有不同 |
| 为什么风险可控 | best-class NMS 是 YOLO 的标准做法；`CONF=0.5` 下同一框通常只有一个类过阈，实际差异极小 |
| 验证手段 | 对 `dog.jpg` 跑改前/改后，比对类别、置信度、框坐标。**不会再有 identical=1 那种逐位一致**，需人工判断是否可接受 |
| 可回退 | 是（保留原函数，编译开关切换） |

---

### 方案 B：`swap` 嵌套 vector 改扁平数组（收益 ~15 ms）

**现状问题**：`detect()` 里
```cpp
vector<vector<vector<float>>> swap(height*width, vector<vector<float>>(anchor, vector<float>(conf_box)));
```
对 26×26 那层要构造 **676 × 3 = 2028 个 vector**，每个 85 个 float。分配开销很大。

**改法**：改成单个 `vector<float>`，用 `idx = ((h*width + w)*ANCHOR + c)*conf_box + k` 手算索引。

| 项 | 评估 |
|---|---|
| 收益 | 约 10-15 ms |
| **风险** | **极低** |
| 具体风险 | 纯粹的数据布局改变，数学完全等价 |
| 验证手段 | **可以逐位验证**：同一输入下 `RAWOUT` 与检测结果必须完全一致 |
| 可回退 | 是 |

---

### 方案 C：JPEG 质量 72 → 60（收益 ~20 ms）

| 项 | 评估 |
|---|---|
| 收益 | jpeg 81.2 → 约 60 ms；带宽从 177 KB/s 降到约 140 KB/s |
| **风险** | **极低** |
| 具体风险 | 画质下降。风险点在于**文字标签周围可能出现块状伪影**（检测框上的"dog 0.98"），因为精细文字是 JPEG 最难压的内容 |
| 缓解 | 标签用更大字号、加粗；或画面右下角保留一个高质量的小尺寸"最近检测"区域 |
| 可回退 | 是（一个数字） |

---

### 方案 D：JPEG 编码移入独立线程（收益 ~60 ms）

**思路**：主线程做「抓帧→预处理→推理→解码→画框」，编码线程做「JPEG 编码→发布」。
DPU 在算的时候 CPU 是空闲的，正好可以让编码线程干活。

| 项 | 评估 |
|---|---|
| 收益 | 若完美重叠，jpeg 的 81 ms 可完全隐藏 → **总帧时间 -20%** |
| **风险** | **中低** |
| 具体风险 | ① **需要双缓冲**：编码线程还在编码第 N 帧时，主线程可能已画出第 N+1 帧并覆盖同一个 Mat。必须传递所有权或用两套缓冲。② 同步 bug 表现为**偶发画面撕裂或花屏**，难以稳定复现。③ 内存 +2.2 MB（板子剩 43 MB，可接受） |
| 为什么风险可控 | 这是经典的"生产者-消费者"模式，用一把互斥锁 + 序号即可；已有 `g_jmtx`/`g_seq` 的雏形 |
| 注意 | **收益取决于主循环会不会等编码线程**。若用无界队列，主循环永不等；但队列积压会导致显示的帧越来越旧。建议队列深度 1（丢弃旧帧） |
| 可回退 | 是 |

---

### 方案 E：抓帧等待改为"预测下一个帧边界"（收益 ~55 ms）

**现状**：`wait_frame_start` 轮询行计数直到 `<= 2`，平均等 58.9 ms。

**改法**：记录上一次帧边界的时刻 `t_prev`，用实测的帧周期 133.33 ms 推算下一个边界，
在 `t_prev + 133.33 - ε` 时才进入轮询（ε 取 3-5 ms）。

| 项 | 评估 |
|---|---|
| 收益 | grab 58.9 → 约 5 ms（**省 54 ms，总帧时间 -13.5%**） |
| **风险** | **中** |
| 具体风险 | **依赖帧周期稳定**。OV5640 的自动曝光在明暗变化时会改变行时间，帧周期会漂移。一旦预测偏早，读到的就是**正在写入的帧** → 画面出现撕裂带；偏晚则白等 |
| 缓解 | ① 不信任预测，仍然保留"确认行计数确实回绕过"的检查 ② 若预测时刻行计数不在合理范围，立即回退到纯轮询 ③ 用滑动窗口估计帧周期而不是写死 133.33 |
| 为什么风险可控 | 有"确认"这一步兜底，最差情况退化成当前行为，不会比现在更糟 |
| 可回退 | 是 |

---

### 方案 F：提高摄像头帧率（改 OV5640 寄存器）—— **收益最大**

**现状**：7.5 fps（133.33 ms/帧），而 OV5640 在 720p 下通常能跑 30 fps。偏低的原因很可能是
**自动曝光把行时间拉长了**（暗光环境下传感器会延长曝光以提亮），也可能与 PLL 分频配置有关。

**改法**：修改 `rtl/I2C_OV5640_1280720_Config.v` 里的寄存器表（曝光上限、PLL 分频、帧率相关寄存器），
然后**重建比特流**（约 50 分钟）。

| 项 | 评估 |
|---|---|
| 收益 | **巨大**：帧周期 133→33 ms，抓帧等待 66→16 ms；整个管线上限从 7.5 fps 提到 30 fps。**这是唯一能突破量级的优化** |
| **风险** | **中高** |
| 具体风险 | ① **画质可能变差**：缩短曝光会让画面变暗、暗部噪声增加。必须重新目视验证图像质量（这一步曾经花了很久才调好，包括色彩顺序、去噪、拼接问题） ② 要重建比特流并**重新验证摄像头通路**（行宽 1025、无拼接、颜色正确） ③ 有破坏已验证状态的风险 |
| 缓解 | 保留当前比特流（`unified_clkfix_sw.bin`）随时可回退；改之前先备份 RTL |
| 前提 | 需要先确认当前配置里到底是什么限制了帧率（查寄存器表），否则是盲改 |
| 可回退 | 是（保留旧比特流） |

---

### 方案 G：预处理进一步优化（收益 ~25 ms）

当前 `pre` 55.4 ms，已经用 OpenCV 的 NEON 路径（从 450 ms 降下来的）。进一步的空间：
- 把 `resize + cvtColor + 量化` 合成一趟处理，减少中间 Mat 的读写
- 量化循环用 NEON intrinsics 手工向量化

| 项 | 评估 |
|---|---|
| 收益 | 约 25 ms（55.4 → 30） |
| **风险** | **低-中** |
| 具体风险 | 手写 NEON 容易出错（字节序、边界），且**改变喂给 DPU 的张量会导致检测结果漂移**，需要重新验证检测正确性 |
| 可回退 | 是 |

---

### 方案 H：DPU 超频（**不建议**）

把 `dpu_2x_clk` 从 200 MHz 提到 250-300 MHz。

| 项 | 评估 |
|---|---|
| 收益 | dpu 125.5 → 约 100 ms（省 25） |
| **风险** | **高** |
| 具体风险 | ① 需要重建比特流，且**时序很可能不收敛**（2x 域是 DPU 内部最复杂的逻辑）② 就算收敛，也必须重新验证 `identical=1`（计算正确性）③ 而我们刚刚才为"2x 时钟必须是整数倍"踩过大坑 |
| 结论 | **收益小、风险大、还要动已验证的比特流。不推荐。** |

---

### 方案 I：降低输出分辨率（**不推荐**）

| 项 | 评估 |
|---|---|
| 收益 | jpeg 和 cvt 都变快，总帧时间可 -20% |
| 风险 | 低（技术上） |
| 为什么不推荐 | 画面从 1025×720 降到 800×562，**文字标签会变模糊** —— 而"看清检测结果"正是这个网页的核心价值 |
| 如果非要做 | 可以只对 JPEG 降采样，检测框坐标不动，但标签字号补偿放大 |

## 五、推荐路径（按风险从低到高，每步都可独立回退）

### 第一阶段：零风险微调（约 30 分钟）
**B + C** → 399.5 → 约 365 ms → **2.7 fps**
- 全部可以逐位验证，不改语义
- 如果效果不明显，随时回退，无任何遗留

### 第二阶段：软件架构优化（约 2-3 小时）
**A + D** → 约 265 ms → **3.8 fps**
- A 需要人工确认检测结果变化可接受（跑 dog.jpg 前后对比）
- D 需要仔细处理双缓冲，建议先在 PC 上做逻辑推演再上板

### 第三阶段：可选激进项（约 1.5 小时 + 50 分钟重建）
**E**（预测帧边界）→ 约 210 ms → **4.8 fps**
- 有"确认"兜底，最差退化到当前行为

### 第四阶段：只在确实需要时才做
**F**（提高摄像头帧率）→ 上限打开到 30 fps，实际可达 **5-6 fps**
- 必须重新验证画面质量，有破坏已验证状态的风险
- 建议**先查寄存器表确认瓶颈**，再决定是否动

**理论上限**（全部做完）：dpu 125.5 + grab(提高帧率后) 16 + cvt 6.5 + pre 25 + decode 15 + draw 11 ≈ **200 ms → 5 fps**

---

## 六、一句话结论

**当前 2.4 fps 的主要限制不是我们的代码，而是摄像头本身只有 7.5 fps、DPU 硬件要 125.5 ms。**
软件侧有约 **200 ms 的确定性优化空间**（主要来自 decode 的 61 ms 和 jpeg 的 81 ms，这两处实现得不够高效），
把帧率从 2.4 提到 **3.5-4 fps** 是低风险、可回退的。
再往上就需要动摄像头配置甚至比特流，收益更大但会威胁到目前已经验证通过的稳定状态。

**建议：先做第一 + 第二阶段**（加起来约 3-4 小时），把帧率翻到 3.8 fps 左右，
这一步不碰硬件、每步可回退；第三、四阶段等你看了实际效果再决定值不值得冒险。
