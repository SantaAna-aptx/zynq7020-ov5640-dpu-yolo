# 网页显示帧率的决定机制（含"台阶效应"）

> 2026-10-16 · 回答"提高 OV5640 帧率能否提升网页帧率"，并解释一个反直觉的实测现象

---

## 一、结论先行

**不能只靠提高摄像头帧率解决问题。** 精确的原因是一个"台阶效应"：

```
T_total = ceil(T_proc / T_cam) × T_cam

网页帧率 = 1 / T_total

T_proc = 处理一帧所需时间（与摄像头无关，取决于我们的代码和 DPU）
T_cam  = 摄像头帧周期（当前 133.33 ms，即 7.5 fps）
```

注意公式里的 **`ceil()`（向上取整）** —— 这就是台阶的来源。

---

## 二、为什么会有台阶：必须"等帧边界"

程序每一轮都要做：

```
wait_frame_start()   ← 等到摄像头开始输出下一帧
memcpy()             ← 搬一帧
处理 T_proc          ← 转换/预处理/DPU/解码/画框/编码
（回到开头，再等下一个帧边界）
```

关键在于**每一轮结束时要重新等一个新帧**。所以：

- 如果处理花了 327.8 ms，而帧周期是 133.33 ms，那处理期间摄像头已经完整过去了 2 帧（266.7 ms）
- 处理结束时，第 3 帧已经开始了 61.1 ms
- 所以还要再等 `133.33 - 61.1 = 72.2 ms` 才到第 4 帧的边界
- **总耗时 = 327.8 + 72.2 = 400 ms**，正好是 `3 × 133.33`

**换句话说：无论 T_proc 在 266.7~400 ms 之间的哪个位置，总耗时都是 400 ms。**

| T_proc 落在 | T_total | 网页帧率 |
|---|---|---|
| < 133.3 ms | 133.3 ms | **7.5 fps** |
| 133.3 – 266.7 ms | 266.7 ms | **3.75 fps** |
| **266.7 – 400.0 ms** | **400.0 ms** | **2.50 fps** ← 当前在这里 |
| 400.0 – 533.3 ms | 533.3 ms | 1.88 fps |

## 三、用实测数据验证这个模型

| 场景 | T_proc (ms) | `ceil(T_proc/133.33)` | 预测 T_total | **实测 T_total** |
|---|---|---|---|---|
| 优化前 | 340.6 | 3 | 400 ms | **399.5 ms** ✓ |
| 第一阶段后 | 327.8 | 3 | 400 ms | **399.4 ms** ✓ |

而每一轮单独测到的 `grab`（等待部分）也能对上：

| 场景 | 帧相位余数 `T_proc mod 133.33` | 预测等待 `133.33 − 余数` | **实测 grab** |
|---|---|---|---|
| 优化前 | 340.6 mod 133.33 = 73.9 | **59.4 ms** | **58.9 ms** ✓ |
| 第一阶段后 | 327.8 mod 133.33 = 61.1 | **72.2 ms** | **71.6 ms** ✓ |

**所以第一阶段 `grab` 从 58.9 涨到 71.6 ms 不是变慢，而是"处理时间变了 12.8 ms 导致帧相位错开、等待相应变长"** ——
两者精确抵消，这正是为什么总帧率纹丝不动。

**模型的预测与实测逐项吻合，可以放心用它做决策。**

## 四、逐项回答你的问题

### Q：能否仅通过提高 OV5640 输出帧率来提高网页帧率？

**能提高一点，但不足以解决卡顿。**

假设把摄像头提到 **30 fps**（T_cam = 33.33 ms），**软件完全不改**：

```
T_proc = 327.8 ms（不变）
T_total = ceil(327.8 / 33.33) × 33.33 = 10 × 33.33 = 333.3 ms
网页帧率 = 3.0 fps
```

**从 2.5 提升到 3.0 fps（+20%）** —— 有改善，但远远谈不上流畅。

### Q：会不会影响图像识别？

**分两种情况：**

**① 如果只是让传感器"更快地重复输出"（提高帧率但不改曝光/画质）**
→ **不影响识别。** 因为识别用的输入永远是同一张经过 letterbox 的 416×416 图，
与"每秒出多少帧"无关。检测精度、置信度、框位置都不会变。

**② 如果提帧率的代价是缩短曝光**
→ **会间接影响识别率。** OV5640 当前只有 7.5 fps，很可能是因为**自动曝光把行时间拉长了**
（暗光环境下传感器会自动延长曝光来提亮画面）。缩短曝光会让画面变暗、暗部噪声增加，
而 YOLO 对暗部和噪声是敏感的 —— 检测置信度会下降，小目标可能漏检。

**所以"提高摄像头帧率"这件事，技术上是"改帧率寄存器"，实际上很可能意味着"牺牲画质换速度"。**
而这套摄像头通路（色彩顺序、去噪、拼接）当初调了很久才稳定，重新动它需要完整重验。

### Q：那最终显示帧率到底由什么决定？

按当前实测的权重排序：

| 因素 | 当前耗时 | 占比 | 性质 |
|---|---|---|---|
| **DPU 硬件推理** | 125.5 ms | 31% | **物理下限，无法优化** |
| **JPEG 编码** | 80.0 ms | 20% | 可优化（但**质量参数几乎无效**，见下） |
| **letterbox + 量化** | 55.4 ms | 14% | 可优化 |
| **YOLO 解码 + NMS** | 49.2 ms | 12% | 可优化 |
| 画框 + 状态条 | 11.0 ms | 3% | 小 |
| cvt（RGB565→BGR） | 6.4 ms | 2% | 已最优 |
| memcpy 1.4 MB | ~5 ms | 1% | 已最优 |
| **等帧边界（T_wait）** | 71.6 ms | 18% | **由摄像头帧率决定** |
| **合计** | **399.4 ms** | | **2.5 fps** |

## 五、由此得到的三条重要推论

### 推论 1：软件优化必须先"跨过台阶"才有效

第一阶段省了 12.7 ms（decode −11.5，jpeg −1.2），但 T_proc 只从 340.6 降到 327.8，
**仍在 266.7~400 这个台阶内**，所以帧率一点没变。

**要跳到 3.75 fps，必须把 T_proc 降到 266.7 ms 以下 —— 还差 61.1 ms。**

这改变了我原来的优化策略：**不该做"每个优化都试一点"，而应该集中力量一次跨过一个台阶。**

### 推论 2：JPEG **质量参数几乎不影响编码时间**

实测 质量 72 → 60，帧大小从 66 KB 降到 52.8 KB（−20%），但编码时间只从 81.2 降到 80.0 ms。

**原因**：JPEG 编码的开销主要在**颜色空间转换 + DCT + 量化查表**这些固定步骤上，
质量参数只影响最后熵编码阶段。**所以"降质量换速度"这条路基本走不通**（但它能降带宽，仍有价值）。

真正的办法是**把编码挪出主循环**（独立线程），让它与 DPU 推理重叠 —— 这样那 80 ms 可以**完全隐藏**。

### 推论 3：提高摄像头帧率的真正价值是"把台阶变密"

对比两种情况（假设软件优化把 T_proc 降到 X）：

| T_proc | 摄像头 7.5 fps（台阶 133 ms） | 摄像头 30 fps（台阶 33 ms） |
|---|---|---|
| 327.8 ms | 400 ms → 2.5 fps | 333 ms → 3.0 fps |
| 266.7 ms | 266.7 ms → 3.75 fps | 266.4 ms → 3.75 fps |
| 200 ms | 266.7 ms → 3.75 fps | 200 ms → **5.0 fps** |
| 150 ms | 266.7 ms → 3.75 fps | 167 ms → **6.0 fps** |
| 133 ms | 266.7 ms → 3.75 fps | 133 ms → **7.5 fps** |

**关键看最后两行**：在 7.5 fps 的摄像头下，**T_proc 再怎么优化，帧率都被卡在 3.75 fps**
（因为台阶太宽，跳不到 133 ms 那一档 —— 而 DPU 一项就要 125.5 ms，根本不可能）。

而在 30 fps 下，台阶只有 33 ms，优化能**连续见效**，一路涨到 5-6 fps。

**所以两者是互补的：软件优化决定"能到多快"，摄像头帧率决定"台阶有多细、优化能不能兑现"。**

## 六、修正后的优化策略

| 阶段 | 内容 | T_proc | 摄像头 | T_total | fps | 风险 |
|---|---|---|---|---|---|---|
| 已完成 | decode 索引改写 + 质量 60 | 327.8 | 7.5 fps | 400 | 2.5 | 极低 ✓ |
| **第二步（推荐）** | **JPEG 移入独立线程**（隐藏 80 ms） | **247.8** | 7.5 fps | **266.7** | **3.75** | 中低 |
| 或 | NMS best-class(−40) + pre NEON(−25) | 262.8 | 7.5 fps | 266.7 | 3.75 | 中 |
| 第三步 | + NMS + pre（若走了线程路线） | ~183 | 7.5 fps | 266.7 | 3.75 | 中 |
| **第四步** | 同上但**提高摄像头到 30 fps** | ~183 | 30 fps | **200** | **5.0** | 中高 |
| 极限 | 全部做完 | ~150 | 30 fps | 167 | 6.0 | — |

**注意第二步的两个备选方案收益相同（都到 3.75 fps）**：
- **JPEG 线程**：一步到位省 80 ms，但涉及并发（中低风险）
- **NMS + pre**：两个独立改动共省 65 ms，不涉及并发，但 **NMS 会改变后处理语义**

## 七、一个需要你决策的取舍：画面流畅 vs 框是否跟手

还有一条**完全不同的思路**，值得单独说明，因为它能绕开 DPU 的硬件下限：

**把"显示"和"推理"解耦**：

```
采集 → 转换 → 画上【上上次的检测框】→ JPEG → 推流     以摄像头帧率跑（7.5 fps）
                    ↑
        DPU 推理在另一个线程里独立跑（约 3 fps），结果放进共享变量
```

- **好处**：画面立刻变成 **7.5 fps**（比现在流畅 3 倍），因为显示路径上只剩采集+编码，不需要等 DPU
- **代价**：**框和画面不同步**。框最多滞后 330 ms，目标移动快时框会"飘"在后面
- **风险**：中（需要线程 + 线程安全的框共享 + 坐标系一致）

**这个方案适合"看整体场景"，不适合"精确跟踪移动目标"。** 要不要做取决于你的使用场景 ——
如果是"把东西放到摄像头前看它能不能认出来"，那框飘一点完全可接受，**7.5 fps 的流畅感提升非常明显**。

---

## 八、一句话总结

> **网页帧率 = 1 / (帧周期的整数倍)**，这个"整数倍"就是台阶。
> 当前 T_proc = 327.8 ms 落在 3×133.33 = 400 ms 这一档，所以帧率是 2.5 fps。
> **只提高摄像头帧率**（7.5→30 fps）能把台阶从 133 ms 缩到 33 ms，帧率提升到 3.0 fps，但治标不治本；
> **必须先做软件优化把 T_proc 压到 266.7 ms 以下**才能跳到 3.75 fps。
> 两者结合才能到 5-6 fps。而 DPU 的 125.5 ms 是物理下限 —— **这套系统的现实上限就是 5-6 fps**。
