# 把慢加速器从显示通路上解耦（帧率台阶效应与双线程重构）

| 项 | 内容 |
|---|---|
| **类型** | 案例模板 |
| **适用场景** | 任何一个"**实时显示 + 慢速加速器**"的流水线：显示帧率被一个耗时远超帧周期的阶段（硬件推理、复杂后处理、编码）拖死，而你只需要"识别结果尽量新"，不需要"识别结果与画面严格同帧" |
| **使用方法** | ① 先测出各阶段耗时与帧周期，用台阶公式算出**当前处在哪一级**；② 若显示路径耗时已低于帧周期只是被别的阶段拖住 → 按本文档拆线程；③ 用"同图比对"确认加速器输出没有回归 |
| **失效条件** | 若应用**要求画面与框严格同帧**（例如逐帧录像取证、运动精确跟踪），解耦会引入一帧以上的滞后，本方案不适用。若显示路径本身的耗时**已经超过**相机帧周期，拆线程也救不了 —— 必须先优化显示路径本身 |
| **已验证效果** | 显示帧率 **2.4 → 7.4–7.5 fps（+208%）**，画面无撕裂，检测框位置与解耦前逐字节一致；**硬件与比特流完全未改动** |
| **投入** | 半天（约 40 行改动），但**省下**了一次约 50 分钟的比特流重建与全套硬件回归验证 |

## 1. 先量化：台阶效应

### 公式

设相机帧周期 `T_cam`、单次循环总耗时 `T_proc`，则实际显示帧率是：

```
T_total = ceil(T_proc / T_cam) × T_cam
fps     = 1 / T_total
```

### 为什么是"台阶"而不是平滑下降

因为每一轮循环**都以"等下一个帧边界"结束**。一轮的总时间必须是帧周期的**整数倍**；
`ceil()` 的代价是每显示一帧就丢掉 `ceil - 1` 个传感器帧。

所以只要 `T_proc` 还落在同一级台阶里，**优化再多也不涨帧率**。

### 实测台阶表（`T_cam = 133.33 ms`，即相机 7.5 fps）

| `T_proc` | `T_total` | 实际 fps |
|---|---|---|
| < 133.3 ms | 133.3 | **7.5** |
| 133.3 – 266.7 ms | 266.7 | 3.75 |
| 266.7 – 400.0 ms | 400.0 | 2.50 ← 本项目解耦前 |
| 400.0 – 533.3 ms | 533.3 | 1.88 |

### ⚠️ 这条公式最重要的用途：识别"白干的优化"

本项目第一阶段做了一轮微优化，把 `T_proc` 从 **340.6 ms 降到 327.8 ms**（省了 12.7 ms）。

结果**帧率一点没变**。原因：

```
340.6 ms → ceil(340.6/133.33) = 3 → 400.0 ms → 2.50 fps
327.8 ms → ceil(327.8/133.33) = 3 → 400.0 ms → 2.50 fps   ← 还在同一级台阶里
```

省下来的 12.7 ms 被"等待时间"原样吃掉了：
等待时间从 **58.9 ms 涨到 71.6 ms**（`340.6 mod 133.33 = 73.9` → 实测 58.9；
`327.8 mod 133.33 = 61.1` → 实测 71.6）。

> **预测精度**：预测等待 59.4 / 72.2 ms，实测 58.9 / 71.6 ms，**残差 ≤ 0.6 ms（< 0.2%）**。
> 公式可信到可以直接用来做决策。

**要跨到下一级台阶（3.75 fps），`T_proc` 必须降到 266.7 ms 以下 —— 当时还差 61.1 ms。**
这就是为什么值得换思路，而不是继续挤那 12 ms。

## 2. 思路转换：不动硬件，拆线程

关键判断：**显示通路自己只需要 94.4 ms（< 133.33 ms），本来就够跑满相机帧率。**
拖死它的是**串在同一个循环里的推理阶段**（预处理 55.4 + DPU 125.5 + 解码 49.2 ≈ 230 ms）。

所以只要把两条通路拆开，显示立刻回到 7.5 fps 上限。

### 结构

```
┌─────────────────── 显示线程（主线程）───────────────────┐
│ 1. wait_frame_start()  轮询行计数器直到 0..2              │
│ 2. memcpy 1.4 MB  DDR 0x08000000 → g_frame  (~5 ms)      │
│ 3. g_frame_seq++        通知推理线程有新帧                 │
│ 4. cvtColor → BGR                          (6.4 ms)      │
│ 5. draw(g_boxes)   在锁内                   (~3 ms)      │
│ 6. imencode JPEG                          (80.0 ms)      │
│ 7. 推给 HTTP M-JPEG 客户端                                │
└──────────────────────────────────────────────────────────┘
                          │  g_boxes + g_boxmtx  ← 唯一交汇点
┌─────────────────── 推理线程（core 1）────────────────────┐
│ 1. 等 g_frame_seq 变化（只关心最新帧）                    │
│ 2. memcpy 一帧（锁内，~5 ms）                             │
│ 3. cvtColor                               (6.4 ms)       │
│ 4. 预处理 letterbox + 量化                 (55.4 ms)      │
│ 5. dpuRunTask                            (125.5 ms)      │
│ 6. YOLO 解码 + NMS                        (49.2 ms)      │
│ 7. 写 g_boxes（锁内，归一化 0..1 坐标）                    │
└──────────────────────────────────────────────────────────┘
```

### 共享状态的设计要点

| 状态 | 保护方式 | 为什么 |
|---|---|---|
| `g_boxes` | 互斥锁 `g_boxmtx` | **唯一的交汇点**，只做写/读，持有时间极短 |
| `g_frame` / `g_frame_seq` | 互斥锁 + 序号 | 推理线程在锁内 copy 一份出来，之后全在私有内存上跑 |
| 客户端计数 | 固定，三条退出分支都要减 | 否则计数漂移，HTTP 线程永远不退出 |

**关键设计：锁的持有时间被限制在那 5 ms 的 memcpy 上。** 55.4 ms 的预处理发生在**私有副本**上，
不占锁 —— 这是"锁不会被慢操作拖住"的标准做法。

**用序号计数器而不是条件变量**：推理线程只关心**最新**那一帧，
中间帧丢掉正好是想要的行为，用序号自增就免费得到了"丢旧帧"的语义。

### 为什么画面不会撕裂

`frame_writer` 是**滚动写入** DDR 的，所以不加同步直接读有可能读到"半新半旧"的帧。

论证：**一次读取约 5 ms，而写入一帧需要 ≥ 33 ms（实测 133.33 ms）。**

```
时间轴：|─── 写第 N 帧 ───────────────|─── 写第 N+1 帧 ──...
        ↑
        行计数器回绕到 0..2 时立刻开始读
        |── 读 (~5 ms) ──|
```

读在帧边界之后**立刻**开始，读指针**始终跑在写指针前面**，
所以读到的每一个字节都属于**上一帧**（已完整写入）的数据。
读进 `g_frame` 之后，cvt / 画框 / JPEG 全在 PL 永不触碰的私有内存上跑 ——
**没有任何消费者会看到写了一半的帧。**

### 代价：一帧滞后

画面比现实晚 **一个相机帧周期（133.33 ms）**。对"把物体举到镜头前看识别结果"这种用法完全无所谓。

**检测框的滞后**（这个才是用户能感知的）：

```
copy 5 + cvt 6.4 + pre 55.4 + DPU 125.5 + decode 49.2 ≈ 253 ms
```

实测框更新率 **3.9 次/秒**（381 次推理 / 97 s）。

接受这个滞后的理由：**125.5 ms 的 DPU 是硬件下限**。
在"画面变慢"和"框变慢"之间只能选一个，而 3.9 次/秒足够回答"这个东西被识别出来了吗"，
显示流畅度提升 3 倍才是用户能直接看到的价值。

## 3. 被评估并否决的方案（含否决理由）

这一节比结论更有价值：**知道什么不该做，以及为什么。**

| 方案 | 预期收益 | 否决理由 |
|---|---|---|
| **只降 JPEG 质量**（72→60） | 预期 ~20 ms | **实测只省 1.2 ms**（81.2→80.0 ms）。原因：JPEG 的耗时主要在色彩转换、DCT 与量化表，**质量参数只影响熵编码**。"降质量换速度"这条路不成立，只适合当带宽杠杆（单帧 66→52.8 KB） |
| **JPEG 单独开线程** | ~81 ms | 需要双缓冲（编码第 N 帧时主线程已在覆盖同一个 Mat），同步错误表现为**间歇性撕裂**（最难查的一类 bug）；内存 +2.2 MB；队列深度必须为 1（否则显示越来越旧的帧）。不如整体解耦 |
| **直接降分辨率**（1025×720 → 800×562） | 编码 80→50 ms | 标签文字变糊，而"**能读出识别结果**"正是这个页面的核心价值 |
| **预测下一个帧边界**（替代轮询） | 58.9→~5 ms | 依赖帧周期稳定，但 **OVS5640 的自动曝光会随光线改变行时间**；预测早了就会读到正在写的帧 → 撕裂。要做得可靠就得加确认 + 回退 + 滑动窗口估计 |
| **提高相机帧率**（改寄存器表 + 重建比特流 ~50 min） | 周期 133→33 ms | 解耦前只值 2.5→3.0 fps；根因很可能是自动曝光拉长了行时间，**缩短曝光会变暗并增加暗部噪声 → 小目标漏检**；摄像头通路（色彩顺序、去噪、拼接、1025 行宽）花了很久才稳定，改完要全部重新验证 |
| **DPU 超频**（2x 时钟 200→250/300 MHz） | 125.5→~100 ms | 需要重建比特流；**时序几乎不可能收敛**（该域历史 WNS 在 150/300 MHz 下是 −7.0/−7.2/−8.4/−9.4/−10.5 ns，而 100/200 MHz 是 +0.505 ns）；还会强制重新验证计算正确性 |
| **换更小的模型** | — | 唯一能绕开 125.5 ms 物理下限的软件手段，但新模型要重新过 `dnnc`、重新跑 8/8 标准答案、还要确保 DPU 特性开关与新模型匹配（可能又牵出一次比特流重建） |

### 资源依据（为什么"上更大/更多的加速器"也不行）

| 资源 | 占用 |
|---|---|
| DSP | **212 / 220 = 96.4%** ← 绑定约束 |
| BRAM | **123 / 140 = 87.9%** ← 绑定约束 |
| LUT | 34,019 / 53,200 = 64.0% |
| FF | 63,101 / 106,400 = 59.3% |

DSP 与 BRAM 已经见底，**没有任何余量去放大或复制加速器**。

> **相关的一条硬件资源教训**：一个 1024×18b 的异步 FIFO，用跨时钟域 read-first 语义写出来
> 综合成了约 **19,000 个触发器**而不是 BRAM；改写成标准 BRAM 模板后**省下 3,500 个 slice** ——
> 这正是"DPU + 摄像头"这个组合最终能塞进去的原因。

## 4. 为什么这条路特别划算：零硬件改动

**同一个比特流**（`unified_clkfix_sw.bin`，md5 `54e99b97a838cdfb155c7b7cd72252fa`）
在同一个二进制上跑出了 2.4 fps 和 7.4–7.5 fps 两个结果。

所以这 **3 倍增益可证明是纯软件的** ——
不碰硬件、不碰已验证的比特流、不需要重跑硬件回归。
这是本项目里"性价比最高的一次改动"的定义。

### 提交前的带宽核算

| 通路 | 数据量 | 带宽 |
|---|---|---|
| 显示 | ~9 MB/帧 | 68 MB/s |
| 推理 | ~19 MB/帧（DPU 的 10 MB 权重/输入/输出集中在 125 ms 内） | 79 MB/s |
| 合计 | | ~150 MB/s = 可用 DDR3 带宽（400–800 MB/s）的 **20–38%** |

不构成瓶颈，但这是"38.9 ms 余量"值得关注的量化理由。

## 6. 可迁移的方法论

1. **先用公式判断"现在在哪一级台阶"，再决定是否优化。**
   本项目省了 12.7 ms 而帧率纹丝不动 —— 如果早算这一步，就不会做那轮微优化。
2. **把"通路"当成一等公民。** 问"**哪条通路真正决定了用户看到的东西？**"
   显示通路只需要 94.4 ms，它本来就能跑满相机；被拖死只是因为它和推理串在一起。
3. **解耦的判据不是"更快"，而是"把慢的部分移出关键路径"。**
   慢的部分依然慢，但不再决定显示帧率。
4. **改动前先做带宽/资源核算。** 本项目的核算结论是"不构成瓶颈"，
   这才是敢在没有余量（DSP 96.4%）的情况下继续用软件方案的理由。
5. **保留回滚路径。** 有完整备份，才敢做结构性重构。
