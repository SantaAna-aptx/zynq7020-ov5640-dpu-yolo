# 分层自审提示词 —— 把"全面检查一遍"变成可执行的动作

| 项 | 内容 |
|---|---|
| **类型** | 提示词工作流 |
| **适用场景** | ① 对大模型说"全面检查一下 / 确保没问题 / 地毯式排查"时；② 联调卡住、怀疑"某个环节其实没生效"时；③ 提交/演示前做最后一遍核对 |
| **使用方法** | 把下面的"提示词正文"整段贴给大模型，并把方括号里的项目替换成你自己的系统 |
| **失效条件** | 这是一套**检查框架**，不是自动化工具 —— 它不会自己去读寄存器，需要你（或执行者）真的去跑那些命令。若系统无法在运行时读回状态（例如纯仿真环境），第 5–6 层要换成仿真波形断言 |
| **已验证效果** | 在本项目中，它把"全面检查"从"凭印象复述"变成"逐层读回验证"，直接纠正了一次基于记忆的错误结论（把 DPU 故障误判为内存/CMA 问题），并暴露了多个"以为生效其实没生效"的环节 |
| **投入** | 用一次 10 分钟 |

---

## 为什么需要它

对工程师和模型来说，**"全面检查"是一个危险的要求** ——
它很容易退化成"把已知的事情用更确定的语气重说一遍"。

本提示词的核心是三条纪律，它们直接对应本项目踩过的坑：

1. **不基于记忆判断，基于读回数据判断。**
   本项目曾把"`cma` 太大导致内核死亡"写进文档并据此排查了很久 ——
   而真因是设备树被放到了 `mem=` 上限之外。当时如果要求"每条结论必须有读回值支撑"，
   就会发现那条结论根本没有任何证据。

2. **一次只改一个变量，改完立刻验证。**
   否则归因必然混乱，尤其是在"改完要等四十分钟构建"的场景下。

3. **先观测后修改。**
   先用只读手段确认状态，再动手改。本项目多个关键定位
   （DPU 特性表对照、FCLK 存活判据、时钟比例核对）**全部只读完成，一次 bitstream 都没重建**。

## 提示词正文（可直接复制使用）

> 我要对本项目做一次全面核查。请按下面的纪律和分层清单执行，
> 每一层都**先用只读手段观测，再给结论**。
>
> ### 三条纪律（违反任何一条的结论都不要写出来）
>
> 1. **不基于记忆判断，基于读回数据判断。** 每一条结论后面必须附上它的证据：
>    寄存器读回值 / 文件内容 / 命令输出。没有证据的，标注"未验证"而不是猜。
> 2. **一次只改一个变量**，改完立即验证。如果你打算一次改动多处，先说明理由。
> 3. **先观测后修改。** 在提出任何修改之前，先完成只读观测。
>
> ### 分层清单（从外到内，逐层给"当前状态 + 证据 + 是否存在问题"）
>
> **第 0 层 · 环境健康**
> - [ ] 开发工具进程是否干净（无残留进程、无工程锁）
> - [ ] 联调依赖的后台服务在运行（本地服务器、串口/网络通道）
> - [ ] 通道独占（串口没有被别的进程占用）
>
> **第 1 层 · 比特流 / 配置**
> - [ ] 构建产物与部署到目标上的**是同一份**（逐点核对哈希）
> - [ ] 目标报告"配置完成"的状态**是否可信**
> - [ ] 读一个**只有你的设计才有的**寄存器/窗口来确认配置真的生效
>       （不要相信通用的状态字段，它可能是假阳性）
>
> **第 2 层 · 硬件设计 / Block Design**
> - [ ] 各 IP 的关键参数**当前值**（不是你以为的值）
> - [ ] **全部时钟引脚**及其驱动者、频率
> - [ ] **全部时钟之间的比例关系**，以及 IP 假设的比例
> - [ ] 全部复位连接与极性
> - [ ] 地址映射（每个主口的 offset/range 是否覆盖它要访问的区域，且互不重叠）
> - [ ] 中断连接与编号
>
> **第 3 层 · 设备树 / 内核接口**
> - [ ] 各节点：基地址、中断号、compatible
> - [ ] 内存相关：内核可用内存上限、预留区、DMA 区
> - [ ] 实际的 `/proc/interrupts` 与硬件编号是否对得上
>
> **第 4 层 · 根文件系统 / 软件组件**
> - [ ] 依赖的库、驱动、模型文件是否齐全且版本匹配
> - [ ] 开机自动化脚本是否**真的会执行且不会失败**
>       （一个失败的启动脚本会让整个系统表现为"随机死机"）
>
> **第 5 层 · 运行时状态（目标板上读回）**
> - [ ] 时钟寄存器：写入后**读回**是否保持（这是判断时钟存活最直接的判据）
> - [ ] 加速器：版本、控制、中断状态
> - [ ] 中断控制器：pending 状态
> - [ ] 内存分配器：实际分布与是否重叠
>
> **第 6 层 · 执行链观测（终极）**
> - [ ] 任务运行**期间**（而不是结束后）读加速器状态
> - [ ] 总线主口事务计数在任务前后的**差值**（证明数据真的流过）
> - [ ] 同一输入跑两次，**逐字节比对输出**（证明结果确定且没有脏数据）
>
> ### 输出要求
> - 每一层给出：**当前状态 / 证据 / 判断（正常 or 有问题）**
> - 最后汇总：**哪些结论是有证据的，哪些只是推测**
> - **不要在完成观测前提出修改方案**
>
> ### 特别提醒：警惕这几类"看起来成功了"
> - 命令执行了但被 shell 拒绝（例如重定向到不存在的目录）
> - 状态字段说成功，但生效的是上一次的东西
> - 构建成功但你的参数没被采纳（工具只是警告，然后沿用旧产物）
> - 读到了**陈旧的产物文件**，却当成本次运行的结果
>
> 请对每一类明确回答：**我怎么区分"真的成功了"和"看起来成功了"？**

## 使用说明

1. **先把系统相关的具体项替换掉**（[ ] 里那些泛化描述换成你自己的寄存器地址、设备名、脚本名）。
   泛化的清单容易被泛化地回答。
2. **第 6 层最有价值**，也最常被跳过。本项目多次靠它定位问题：
   - "运行中读" 而不是 "结束后读" —— 结束后的状态可能已被超时清理
   - 总线计数差值 —— 比任何日志都直接地证明"数据流过"
   - 同图跑两次比对 —— 一个能同时发现"时钟比例"和"输入被污染"两类问题的自检
3. **把"已知陷阱清单"附在后面**（见下），它会随项目积累而变长，是本提示词里最保值的部分。

### 附：本项目积累的陷阱清单（可作为你的起点）

```
1. 脚本路径里的反斜杠转义（\v \r 之类）→ 一律用正斜杠
2. 向已关闭的输出通道打印 → 脚本静默中断 → 每步日志独立开闭
3. 后台延时命令在前一条命令结束后才开始计时 → 实验时序失效
4. 计划任务到达时刻会自动重复触发 → 进程堆积
5. 用 && 串联时，前一条失败导致后一条根本没执行
6. 变量为空 → 工具打印 Usage 而不报错 → 用固定字面值
7. 证据在超时清理后才读 → 读到空 → 必须在运行中读
8. 未经验证的变量假设（PLL 频率、分频语义、寄存器偏移）
9. 多个自动化脚本并发 → 互相打架/锁冲突 → 单实例纪律
10. "状态字段 = 成功" 的假阳性
```

## 提炼过程 —— 从哪些失败与观察中总结出来

1. **直接触发点**：当被要求"全面检查、确保百分之百正确"时，
   第一反应是**把已经做过的事情重新叙述一遍**，语气更肯定，但信息量为零。
   本提示词就是为了阻断这个退化。
2. **第 1 条纪律来自一次真实误诊**：当时"`cma` 导致内核死亡"的结论被写进文档，
   后来翻日志发现根本没有任何证据支持它，真因在别处。
   从此要求"每条结论附证据"。
3. **第 3 条纪律（先观测后修改）带来的是实打实的时间节省**：
   DPU 的三次关键定位（特性开关、时钟比例、时钟门控）**全部只读完成**，
   没有重建过一次比特流 —— 而每次重建约 50 分钟。
4. **第 6 层是后来补上的**：前几层都在查"配置对不对"，
   但真正的问题往往在"数据有没有真的流过、结果是不是确定的"。
   补上"运行中读 + 计数差值 + 同图比对"之后，这类问题才变得可观测。
5. **陷阱清单是这份提示词里唯一会持续增值的部分** ——
   每一条都对应一次真实的时间损失，所以值得单独维护。
