# prompts/ —— 提示词工作流

这些不是"随便聊两句"，而是**在真实故障中反复用过、并且确实改变了结果**的提示词模板。
每一条纪律背后都对应一次具体的时间损失。

| 提示词 | 解决什么问题 | 什么时候用 |
|---|---|---|
| [`layered-self-audit.md`](layered-self-audit.md) | "全面检查一遍"退化成"换个语气复述已知的事" | 被要求地毯式排查、联调卡住怀疑某环节没生效、演示前最后核对 |
| [`evidence-first-diagnosis.md`](evidence-first-diagnosis.md) | 过早收敛到某个猜测，然后在错误方向上反复试 | 故障现象模糊、可能原因一大堆 |

---

## 共同的三条纪律

这三条在两个提示词里都出现，因为它们是本项目最贵的三条教训：

### 1. 不基于记忆判断，基于读回数据判断

**触发事件**：本项目曾把"内存分配参数导致内核死亡"写进文档，并据此排查了很久。
后来翻日志才发现，**那条结论从来没有任何证据支持**，真因在完全不同的地方。

**做法**：每条结论后面附上它的证据 —— 寄存器读回值、文件内容、命令输出。
没有证据的，明确标注"未验证"，而不是用更肯定的语气说出来。

### 2. 一次只改一个变量

在"改一次要等 40 分钟构建"的环境里，一次改多处 = 归因混乱 + 极贵的试错。
先做只读观测，把范围缩到最小，再动手。

**收益**：本项目的三次关键定位（加速器特性开关、时钟频率比、时钟门控）
**全部只读完成，一次比特流都没重建。**

### 3. 先观测后修改

在提出任何修改方案之前完成只读观测。这条看似显然，
但在"着急修复"的心态下最容易违反 —— 包括大模型在内的执行者，
都有直接跳到修复方案的倾向。

## 这两份提示词为什么值得单独提交

竞赛的评分标准里有一条是"**技能包的提炼过程：从哪些失败或观察中总结、如何验证有效**"。
这两份提示词恰好完整地满足这一点：

- **来源是失败**：三条纪律各自对应一次真实的误诊或空转，不是凭空设计的规范；
- **可验证有效**：`evidence-first-diagnosis.md` 里的分类表直接命中过两个疑难问题，
  且区分开了两个"现象完全相同"的不同根因；
- **可复用**：两份提示词都不依赖本项目的具体硬件，换一个嵌入式项目、换一块板卡同样适用。

## 使用小技巧

1. **把系统具体信息替换进占位符。** 泛化的清单会被泛化地回答。
2. **提供原始现象，不要提供你的结论。**
   说"X 坏了"会把执行者锁死在 X 方向上；说"现象 A、B、C，其中 C 是换了旧版本就正常"
   才能支撑真正的推理。
3. **要求区分"证据推断"与"经验猜测"。** 两者都有价值，但必须分清。
4. **让执行者先问、再推。** 缺信息时要求它先问，而不是基于假设往下走。
5. **维护自己的陷阱清单。** 这是整套方法里唯一会持续增值的部分 ——
   每加一条，就意味着一次损失被固化成了资产。
