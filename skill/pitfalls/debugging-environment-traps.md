# 嵌入式联调环境陷阱：命令静默失效与假阳性

| 项 | 内容 |
|---|---|
| **类型** | 踩坑清单 |
| **适用场景** | 通过串口 / SSH 在资源受限的板子上做无人值守联调，或从主机脚本驱动板子 |
| **使用方法** | 联调脚本上线前逐条核对本文档；出现"改了没效果""命令没反应"时优先怀疑这几条 |
| **失效条件** | 部分条目特定于 `init=/bin/sh` 的最小根文件系统与 USB 转串口芯片，换环境后不一定复现 |
| **已验证效果** | 每一条都实际导致过数小时的空转；修正后联调脚本可靠 |
| **投入** | 认识成本高，改正成本极低 |

---

这些坑的共同特征：**命令看起来执行了，实际上没有；或者失败了但你看不出来。**
它们不会报错，只会让你在错误的前提下继续推理。

## 1. `/tmp` 可能不存在，而重定向到不存在的目录会**让整条命令被拒**

### 现象

应用"启动了"但没有任何输出；更糟的是，循环里还能拿到"结果"。

### 根因

在 `init=/bin/sh` 的最小根文件系统里 **`/tmp` 可能不存在**。
于是：

```sh
/app > /tmp/app.log 2>&1 &        # /tmp 不存在 → shell 无法建立重定向
                                  # → 整条命令被 shell 拒绝，应用从未启动
```

**关键点：shell 在解析阶段就失败了，所以应用根本没跑，而且不会给你任何提示。**

### 更坏的情况：假阳性

如果脚本随后去读取一个**上一次**留下的结果文件（例如 `result.jpg`），
读到的其实是**陈旧文件**，于是看起来"应用跑过了、有结果"。
排查方向就此完全跑偏。

### 对策

1. 日志写到**确定存在的目录**（例如应用自己的目录或 `/home/root/`）。
2. **不要用"结果文件存在"判断成功** —— 它可能是陈旧的。
   要在日志里断言一个**每次运行必定出现**的特征字符串：
   ```sh
   grep -q 'DETERM_CHECK' /home/root/app/app.log || echo 'APP DID NOT RUN'
   ```
3. 联调前先确认目录存在：`ls -d /tmp` 而不是假定它有。

## 2. 串口不要开 `DtrEnable` / `RtsEnable`

### 现象

板子**完全停止应答**，看起来像死机。

### 根因

在 .NET 的 `SerialPort` 上设置 `DtrEnable = true` / `RtsEnable = true`
会让本板的串口控制线产生电平变化，板子随即不再响应。

### 对策

**不要设置这两个属性**（保持默认）。已验证可用的联调代码从不设置它们。
串口重连时也不需要"复位"这些线。

## 3. `[System.IO.Ports.SerialPort]::GetPortNames()` 可能漏掉你的端口

### 现象

PC 重启后，`GetPortNames()` 返回的列表里**没有 COM10**（芯片是 CP210x，设备管理器里正常）。

### 对策

**不要去枚举、不要做"自动发现端口"** —— 直接打开已知的端口号（`COM10`）。
枚举在这类环境下不可靠，而端口号是稳定的。

## 4. `reboot -f` 会让本板停机，且不会自己起来

### 现象

```
Reboot failed -- System halted
```

### 对策

**永远不要指望软重启。** 需要重启就物理断电再上电。
联调脚本要把"需要一次物理断电"作为一个显式步骤写出来，而不是假装可以自动重启。

## 5. 主机脚本里的正则/字符串陷阱

### 现象 A：内联正则**以反斜杠结尾**导致整个命令抛异常

```
ArgumentException: \ 在模式末尾非法
```

一个写成 `...\.runs\` 的路径片段会让 PowerShell 报错，
而如果它在循环里，会**刷屏式地产生错误输出**，把真正有用的信息淹没。

**对策**：路径匹配用 `-like` 或子串包含，或者把正则放进独立脚本文件。
不要在内联命令里写复杂的正则。

### 现象 B：脚本里出现非 ASCII 字符导致解析失败

PowerShell 对 `.ps1` 文件里的全角括号、中文冒号、`≈` 之类的字符很敏感，
可能在**解析阶段**就失败。

**对策**：`.ps1` 脚本正文保持纯 ASCII。
中文放到 `.md` 文档里，或者用 UTF-8 带 BOM 并在文件头显式声明。

### 现象 C：主机上的编码来回转换

从 PowerShell 调用 Python 时，中文参数会经过一次编码转换（本例里变成 GBK 乱码）；
Python 的 stdout 默认编码也可能是 GBK，打印非 ASCII 内容直接抛
`UnicodeEncodeError: 'gbk' codec can't encode character`。

**对策**：
- 不要把中文当命令行参数传；用文件路径通配符或环境变量传。
- 让脚本**自己写输出文件**（显式 `encoding='utf-8'`），不要让 shell 重定向去管编码。
- 需要看输出时设置 `PYTHONIOENCODING=utf-8`。

## 6. 不要做宽泛的进程清理

### 现象

一条 `Stop-Process` 之类的宽泛清理命令，把**联调依赖的后台服务**（本地 HTTP 服务器、
启动器等）一起杀掉，导致后续步骤莫名其妙全失败。

### 对策

**按 PID 精确终止**，或者按明确的可执行文件路径匹配。
永远不要写"杀掉所有 python.exe / 所有 node.exe"这种命令。

## 提炼过程 —— 从哪些失败与观察中总结出来

这一份是**多次空转之后归纳出来的**，不是一次事故的记录。共同教训：

1. **"命令看起来跑了"是一个需要被验证的假设。**
   远程联调里，最贵的错误不是命令失败，而是**命令失败了但你以为它成功了**。
2. **假阳性的危害远大于报错。** 报错会逼你去看，假阳性会让你在错误前提上继续推理几小时。
   所以联调脚本必须**主动断言成功条件**（`grep` 一个必定出现的字符串），
   而不是从"文件存在""端口有响应"这类间接迹象去推断。
3. **凡是"环境差异"造成的问题，都要在脚本里显式写出来**（例如"需要一次物理断电"），
   因为在另一台机器上复现时，最耗时的恰恰是这些默认假设。
