# 比特流必须字交换 + 先加载比特流再 insmod

| 项 | 内容 |
|---|---|
| **类型** | 踩坑清单 |
| **适用场景** | 在 Linux 下用 `fpga_manager` 在运行时加载 PL 比特流，尤其是加载后要 `insmod` 依赖 PL 中 IP 的内核模块 |
| **使用方法** | 按"排查步骤"核对加载方式与加载顺序 |
| **失效条件** | 仅适用于通过 Linux `fpga_manager` 运行时加载的场景。若由 FSBL/U-Boot 在启动阶段加载比特流，本项不适用 |
| **已验证效果** | 修正后 `state=operating` 且 DPU 可用；此前 `insmod` 导致内核 oops |
| **投入** | 定位约 1 小时（两条都很隐蔽） |

---

## 坑 1：`.bin` 必须经过字交换（byte/word swap）

### 现象

```
Invalid bitstream, could not find a sync word
```

### 根因

`zynq-fpga` 驱动要求的 `.bin` 是**字交换（word-swapped）**格式，
而 Vivado 直接导出的 `.bin` 不是。二者看起来都是二进制，但字节序不同，
驱动找不到同步字（sync word）。

### 修复

对比特流做字交换处理后再加载。加载方式是写 `firmware` 属性：

```sh
echo <文件名> > /sys/class/fpga_manager/fpga0/firmware
```

### ⚠️ 附带的假阳性陷阱

**`state` 读回 `operating` 并不代表你刚加载的那个比特流生效了。**

加载失败时 `state` 仍可能显示 `operating` —— 它反映的是 **QSPI 里那一片厂商比特流**，
而不是你刚写进去的东西。

> **教训：`state=operating` 不能作为"加载成功"的判据。**
> 必须用**功能性的证据**确认：PL 里某个只有你的设计才有的寄存器/窗口能读出来。

## 坑 2：必须先加载比特流，再 `insmod`

### 现象

`insmod` 时**段错误**或内核 oops。

### 根因

内核模块的 probe 函数会访问 PL 中 IP 的寄存器窗口。
以 DPU 为例，`dpu.ko` 的探针要访问 `dpu_eu` 在
**`0x40000000` 的 16 MB 窗口内、偏移 `0x40F00000`** 处的内容
（即物理地址 `0x40F00000`）。

如果此时 PL 里挂的是厂商比特流（没有这个 IP），**该地址没有对应的 AXI 从设备应答**，
访问直接失败 → oops。

### 修复

固定顺序：**先加载比特流（并确认加载成功），再 `insmod`**。

## 排查步骤（合并顺序）

1. 加载比特流后，**不要相信 `state`**，直接读一个只有你的设计才有的地址验证：
   ```sh
   devmem 0x40000000        # 应为 DPU 签名，例如 0x0D9C13F1
   ```
2. 若读到全 `0xFFFFFFFF` 或访问报错 → 比特流没生效（检查是否字交换、文件名是否正确）。
3. 确认生效后，再 `insmod dpu.ko`。

## 提炼过程 —— 从哪些失败与观察中总结出来

1. **坑 1 的发现**：驱动报 `could not find a sync word` 时，
   第一反应是"文件损坏"，反复重传、校验 md5 —— 文件是好的，是**格式**问题。
   定位靠的是驱动源码/文档里对 `fpga_manager` 接受格式的说明。
2. **假阳性的发现**：一度以为加载成功了，因为 `state` 显示 `operating`。
   直到发现读 `0x40000000` 得到的是厂商比特流的东西，
   才意识到 `state` 反映的不是"我这次加载"的结果。
3. **坑 2 的发现**：`insmod` 段错误时先怀疑模块与内核版本不匹配，
   但同一模块在正确顺序下可以正常加载 —— 是**顺序**问题。
   根因线索来自 `dpu.ko` 探测的地址落在 PL 窗口内这一事实。
4. **共性**：两个坑都属于"**系统给的反馈本身是误导性的**"这类。
   `state=operating` 是假阳性，`insmod` 段错误看起来像版本问题。
   **对策都是用功能性的、端到端的证据去验证，而不是相信状态字段。**
