# DPU 输出写会污染任务输入缓冲区 → 第一次对、后面全错

| 项 | 内容 |
|---|---|
| **类型** | 踩坑清单 |
| **适用场景** | DNNDK（`dpuRunTask` 系列接口）连续跑多次推理，**第一次结果正确，之后结果漂移**；或批量跑多张图时准确率莫名下降 |
| **使用方法** | 加一条"同图跑两次比对输出"的自检（`identical=`）；若第二次与第一次不同，按本文档处理 |
| **失效条件** | 特定于 DNNDK v3.x 的任务接口行为。若应用已经在每次推理前重新写入输入张量（绝大多数正常写法），则不会遇到本问题 |
| **已验证效果** | 修复后 `identical=1`，8 张测试图 8/8 全检出；修复前每次执行结果都不同 |
| **投入** | 定位难度**高**（现象与"时钟问题"完全一样）；修复只需一行 |

---

## 现象

推理**第一次执行总是对的**（RUN1 能检出目标），但后续执行结果持续漂移：

```
DETERM_CHECK: run1=-8615966 run2=-9379926 identical=0
```

> ⚠️ **这是最容易误诊的一条**：`identical=0` 与
> [2x 时钟比例错误](dpu-nondeterminism-clock-ratio.md) 的现象**一模一样**。
> 两者都会表现为"非确定性"，但根因完全不同。
> **鉴别方法**：本问题的特征是"**第一次一定对**"；
> 时钟比例问题的特征是"**每一次都错，且错得毫无规律**"。

## 根因

**DPU 的输出写入会落到任务的输入缓冲区上** —— 每次执行之后，输入张量被输出数据改写了。
下一次执行时读到的是脏数据，于是结果开始漂移，且越跑越偏。

因为污染发生在**推理之后**，所以第一次执行的计算永远是正确的 ——
这正是"第一次对、后面错"这个独特指纹的来源。

## 排查步骤

1. 加自检：同一张图连续跑两次，**逐字节比较两次输出**，打印 `identical=`。
2. 若 `identical=0`，**先看是不是"第一次对、第二次错"**：
   - 是 → 本问题（输入缓冲区被污染）
   - 否（每次都不一样且都错） → 先查 [2x 时钟比例](dpu-nondeterminism-clock-ratio.md)
3. 交叉验证：在每次执行间**重新写入输入张量**。若结果立刻变确定，就确认是本问题。

## 修复

**应用在每次 `dpuRunTask` 之前刷新输入缓冲区**（把原始输入重新写进去），
而不是只写一次就反复执行。

```c
for (each inference) {
    set_input_image(...);      /* ← 关键：每次执行前都要重新写 */
    dpuRunTask(...);
    decode_boxes(...);
}
```

## 提炼过程 —— 从哪些失败与观察中总结出来

1. **一度被归因到错误的方向**：因为现象与时钟比例问题相同，
   第一反应是回去查 `dpu_2x_clk` 比例。
2. **区分两个根因的关键观察**：把多次执行的原始输出逐次打印出来对比，
   发现"**第一次总是正确的**"这个规律 —— 时钟问题不会这么规律。
3. **推论**：既然第一次对，说明硬件计算通路是好的；问题出在**第二次的输入已经变了**。
   顺着这个方向检查输入缓冲区，立刻证实。
4. **固化为常驻自检**：`DETERM_CHECK: run1=… run2=… identical=` 从此成为应用的固定输出项。
   它同时能发现本问题和时钟比例问题，是性价比最高的一条自检。
5. **教训**：两个完全不同的根因可以有**完全相同的外在现象**。
   区分它们靠的是**额外的、更细的观察维度**（这里是"第几次开始错"），
   而不是更用力地检查同一个现象。
