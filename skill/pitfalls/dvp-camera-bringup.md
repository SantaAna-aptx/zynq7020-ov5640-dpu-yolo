# DVP 摄像头采集排错清单（OV5640 类并行接口）

| 项 | 内容 |
|---|---|
| **类型** | 踩坑清单 |
| **适用场景** | 并行接口（DVP：PCLK / VSYNC / HREF / D[7:0]）的摄像头在 FPGA 上采集。画面噪声、错位、斜向拖影、垂直重复、分屏接缝、颜色异常，或者**完全没有数据 / 配置不进去** |
| **使用方法** | **严格按 §0 → §1 → §2 → §3 的顺序排查。** 顺序错了会在错误的前提上反复试 —— 本项目最大的弯路就是先调几何、后查通信 |
| **失效条件** | ① MIPI CSI-2 / LVDS 等串行接口的摄像头不适用（没有 HREF/PCLK 这套语义）；② 若使用厂商完整提供且已验证的采集 IP，§3、§4 多数不适用；③ 本文档的经验基于 OV5640，其他传感器的寄存器地址与默认值不同（但排查方法与现象分类通用） |
| **已验证效果** | 从"零 ACK、无数据、全 0xFF"修到"1025×720 真实场景可辨认、相邻行相关 +0.9929、相邻列相关 +0.995" |
| **投入** | **本项目最耗时的一条线**（数周）。但每一步都有确定的判据，不像"调参"那样不可收敛 |

## §0 先读这一条：两个"反直觉"的前提

### 0.1 不要假设行宽 —— 传感器"配置为"多少，不代表它"输出"多少

**本项目的核心错误**：按配置值 **1280 像素/行**渲染，而摄像头**实际输出 1025 像素/行**。

后果：每行错位 255 像素，而 `255 × 4 ≈ 1020 ≈ 1025`，
于是**每 4 行重复一次** —— 这个"4 行周期性"从最早一版就存在，
把排查方向引向 FIFO、时钟、行结束信号，持续了很久。

**行宽测量方法（纯数据驱动，不依赖任何硬件假设）**：
对采集到的原始字节流，假设一个候选行宽、按该宽度重排行数据，计算**相邻行相关系数**，取最大者。

```python
for width in candidates:              # 例如 512 .. 2560
    rows = reshape(raw, width)
    corr = correlate(rows[:-1], rows[1:])
    print(width, corr)
```

实测结果（决定性）：

| 候选行宽 | 相邻行相关系数 |
|---|---|
| **1025** | **+0.9929** ← 最佳 |
| 2050 | +0.9870（2×1025，谐波） |
| 1280（配置值） | 极低 |

**正确宽度下相邻行高度相似；错误宽度下行内容互相错位，相关系数趋近 0 或为负。**

> 当所有"推理出来的"解释都对不上时，改用这种"从数据自证"的手段。
> 它不需要你相信任何文档。

### 0.2 SCCB 的第 9 位不是真正的 ACK

在 SCCB 的**写**阶段，第 9 个时钟位是 **"don't care"** —— 从机**不驱动** SDA。
所以采样到 1 是**正常现象**，不能用它判断设备是否存在。

**判断传感器是否活着，唯一可靠的方法是读它的 ID 寄存器**：

```
0x300A / 0x300B 应为 0x56 / 0x40
```

（也可读回配置寄存器间接验证，例如 `0x4300` / `0x3035` / `0x3036` / `0x3824`。）

## §1 第一层：能不能和传感器通信（SCCB / I2C）

### 1.1 SDA 三态极性被弄反 —— 一条指令都没发出去

**现象**：SCL 在翻转，但 SDA **从未被拉低**；寄存器写入全部无效；
全地址扫描 `0x00`–`0xEE` **零个 ACK**；芯片 ID 读到 `0xFF 0xFF`。
而 `i2c_config_done` **仍然置 1**。

**根因**：Block Design 里把 `cam_top/cmos_sda_oe` 接到了 `sda_iobuf/T`，
而 **`IOBUF.T` 是高有效三态**：`T=1` = 高阻，`T=0` = 驱动。

原 RTL 写的是：

```verilog
assign i2c_sdat_OE = bir_en ? 1'b0 : 1'b1;   // 只在 ACK 时隙驱动，而且驱动的是高
```

于是 **START 和每一个数据位都停在高阻态**，同时那 4 个 ACK 时隙反而在**驱动高电平**。

**修复**（改成开漏语义）：

```verilog
assign i2c_sdat_OUT = i2c_sdat_out;
assign i2c_sdat_OE  = i2c_sdat_out;    // 0 = 拉低, 1 = 释放
```

**判据**：修复后板上读到 sticky ACK 位 = 1；修复前**一个 ACK 都没有过**。

> ⭐ **可迁移的教训**：在 Zynq Block Design + IOBUF 的组合里，
> **三态控制（T 或 OE）的极性约定必须在 BD 里核对**，不能凭经验假设。
> I²C/SCCB 这类开漏总线，**三态控制应当由数据值驱动**，而**不是由某个时隙使能驱动**。

### 1.2 "配置完成"是假的 —— ACK 校验被注释掉了

**现象**：`i2c_config_done` / `cam_cfg_done` = 1，但**从机从未应答**。
设计在一个死掉的总线上报告"摄像头已配置"。

**根因**：配置引擎里的 **ACK 检查被注释掉了**，
于是"完成"完全是靠状态机走完 252 项表项**推断**出来的。

**修复**：在寄存器接口里加一个 **sticky latch**：

```verilog
if (i2c_capture_en && bir_en && i2c_sdat_IN == 1'b0) sccb_ack_seen <= 1'b1;
```

把它作为 `i2c_ack_o` 引出，并**打包进调试字** —— 于是"传感器应答过吗"变成**一个可读的位**。

> ⭐ **教训**：一个只写不读的 SCCB 主机，**绝不能从自己的状态机推断成功**。
> 一定要 latch 一个"从机把 SDA 拉低过"的粘滞位，并暴露给软件。

### 1.3 SCCB 速率：降到 ~30 kHz

**现象**：额定速率下从未被接受；整个项目里唯一观测到的一次 ACK 出现在
"上电数小时后 + 416 kHz"的某个会话；改用合规时钟 + PWDN 接地后是零 ACK。

**根因**：手工杜邦线互连，**高 SCCB 时钟让总线处于临界状态**。
OV5640 数据手册的上限（`fSIOC` 最大 400 kHz）是**PCB 级的上限**，不是使用目标。

**修复**：实例化时把时钟降到 **33 kHz**（模块默认 400 kHz）：

```verilog
i2c_timing_ctrl_reg16_dat8_wronly #(
    .CLK_FREQ(50_000000), .I2C_FREQ(33_333)
) u_i2c (...);
```

**判据**：33 kHz 下 sticky ACK = 1；对照数据手册时序表，在 16–33 kHz 下每个参数都有 **20–30 倍余量**。

> ⭐ **教训**：飞线连接的 OV5640，SCCB 按 **~30 kHz** 跑，并加一个**硬件 ACK 探针**。
> **把 400 kHz 当数据手册上限，不要当目标。**

### 1.4 自愈式重配置：观察 PCLK 决定要不要重跑配置表

**现象**：一次配置可能永远留下一个沉默的传感器；
摄像头只在某次重配置之后才醒，但**没有任何东西会去重配置它**。

**根因**：从传感器到 SCCB 引擎之间**没有任何反馈通路**。

**修复**：在配置时钟域加一个重试状态机，观察 **PCLK 域的"自由计数器"**：

```
每次 cmos_pclk → pclk_free8 自增
i2c_done 之后：
  等 retry_timer[26]（50 MHz 下约 1.34 s），把 pclk_free8 锁存到 pclk_s1
  再等 retry_timer[25]（约 0.67 s），比较
    未变化 → retry_pulse 复位 I2C 引擎 (i2c_eng_rst_n = ARESETN & ~retry_pulse[0])，重跑整张表
    有变化 → retry_stop <= 1（此后永不重配置）
```

文档里描述为"每约 2.5 s 重跑一次配置表，永续重试"。

**判据**：调试字里的 `dbg_retry` 位与 PCLK 计数器的低半字节在变化；
首次出现真实 DVP 数据特征（293 个非零字节、值域多样 `0xa5 0x29 0x44 0x19`，
而不是全 `0xFF`）。

> ⭐ **教训**：让 SCCB 主机**通过观察传感器自己产生的时钟（PCLK）来自愈**，
> 超时就重跑配置表。**永远不要假设一次只写的过程成功了。**

### 1.5 物理层：PWDN 与 RST 的接法

| 引脚 | 正确接法 | 症状（接错时） |
|---|---|---|
| **PWDN** | 接**数字地** | 悬空 → 传感器停在硬件掉电状态 → XCLK 无响应、无 ACK、无 PCLK、无数据，**整个系统沉默** |
| **RST** | 接 **3.3 V**（先拉低 1 s 再释放到 3.3 V 可得到干净的复位释放） | 悬空 → 传感器停在复位状态。**绝不能接 GND** |
| FREX / STROBE | 可悬空 | — |

**PWDN 这个坑特别贵**：本板原理图上模组的 PWDN 下拉电阻 **R3 4.7 kΩ 标注为 DNP（不贴）**，
所以 PWDN 是**悬空**的。而 OV5640 的 PWDN **高有效**，
且寄存器 `0x3008` 的复位默认值 `0x42` 里 bit6 就是 PowerDown ——
**悬空的 PWDN 足以把传感器按在硬件掉电状态。**

**判据（关键）**：**用万用表量"模组那一端"的 PWDN 对地电压，应为 0 V。**
**不要只量 FPGA 输出引脚** —— 中间可能根本没接通。

> ⚠️ 如实说明：本项目在把 PWDN 接地并断电重启后，日志里**仍然记录着零 ACK**。
> 所以 PWDN 在本项目里被记为"**已排除 / 已接地**"，而**不是**被证明的修复。
> 但它的症状与"SCCB 总线死了"完全一样，**必须先排除**它再去查协议层。

### 1.6 模块身份：按模组自己的丝印识别，不要照抄别人的引脚表

**现象**：反复接错线；真实模组上 RST 是悬空的；
XCLK/PCLK 到底在 7/8 脚还是别处一直含糊。

**根因**：手上的模组**不是**先前那张引脚表所依据的模组。
丝印是 **"OV5640 Core Board 2.0"**，ID = `0x78`，
引脚为 D3V3 / DGND / SCLK / SDA / VS / HS / PCLK / XCLK / D7..D0 / RST / PWDN / FREX / STROBE。
早先的表假设的是另一种 2×10 的 VIP 排针定义。

> ⭐ **教训**：**先按模组自己的丝印和原理图确认引脚，再去信任何现成的引脚映射表。**
> 并且**显式地**把 RST 拉高、PWDN 拉低，防止板子上的 GND 意外落到 RST 上。

### 1.7 无效的"XCLK 死了"测量（两次）

**现象**：一个软件采样循环报告"XCLK 死：20000 次采样、0 次跳变、恒定 1"，**同一个结论得出过两次**。

**根因（两个独立错误）**：

1. **探针根本没装**。原计划用跳线把 XCLK 短接到被采样的 SDA 线上，
   而操作者说的"插好了"指的是换了 XCLK 主接线。没有跳线时，
   SDA 只是被上拉电阻拉高 —— **"恒定 1"什么也证明不了**。
2. **即使装了跳线，用 PS GPIO 以约 1 µs 间隔采样也无法观测 24 MHz 信号**（违反奈奎斯特，会混叠）。

**修复**：**不要用软件 GPIO 采样去推断时钟是否存在。**
用 MMCM 的 LOCKED 位（通过 GPIO 引出）或仪器。
后续的诊断比特流干脆绕开 MMCM，**在逻辑里把 FCLK0 除以 16** 得到一个已知频率源。

> ⭐ **教训**：**在用负向测量下结论之前，先证明探针有效**（做一个正对照），
> 并检查采样定理。**悬空输入读出来就是恒定 1，有没有信号都一样。**

### 1.8 传感器 IO 域与 FPGA bank 电平可能不匹配

**症状**：RST = 3.3 V、PWDN = GND、线束反复检查四遍之后，**仍然零 ACK、ID 读回 `0xFF/0xFF`**。

**怀疑方向**：OV5640 的数字 IO 域标称 **1.8 V**
（数据手册 `VIH = 1.26 V`、`VIL = 0.54 V` @ DOVDD = 1.8 V），
而 FPGA bank 是 **LVCMOS33**，用 3.3 V 驱动 SIOC/SDAT 和 DVP 线，
**超过了 DOVDD + 0.3 V**。两个独立风险：

- **破坏性过压**：SIO pad 可能被打坏
- **反向阈值问题**：FPGA 的 LVCMOS33 `VIH = 2.0 V`，可能读不稳 1.8 V 的高电平

**处置**：换用已验证的模组 + 转接板组合，或加电平转换。

> ⚠️ 这一条在本项目中**未被证实**，记录为"最大嫌疑"，
> 最终结论是"模组坏了或没供电"。

> ⭐ **教训**：接线之前先核对**传感器 IO 域 vs FPGA bank VCCO**。
> 3.3 V 直驱 1.8 V 的 pad 既是阈值问题，也是**过压损坏**问题。

## §2 第二层：有没有数据（时钟与复位链）

### 2.1 MMCM 输入低于 7 系列最小输入频率 → LOCKED 永不置位 → XCLK 死

**现象**：`mmcm_locked = 0`，XCLK 被门控关掉，OV5640 没有主时钟，什么都不输出。

**根因**：ACLK 是 PS 的 FCLK_CLK0 = 50 MHz，而原设计用 `DIVCLK_DIVIDE = 1`，
把 MMCM 的**输入频率压到了 7 系列允许的最小输入频率之下**，于是 LOCKED 永远无法置位。

**修复**：

```verilog
MMCME2_ADV #(
    .CLKIN1_PERIOD(20.0),          // 50 MHz
    .CLKFBOUT_MULT_F(48.0),
    .DIVCLK_DIVIDE(2),             // ← 让鉴相器看到合法的频率
    .CLKOUT0_DIVIDE_F(50.0)        // → VCO 1200 MHz, CLKOUT0 = 24 MHz
) ...
```

并且**用 LOCKED 门控 XCLK**（加 2 级同步器）：

```verilog
cmos_xclk = en_sync ? clk24_b : 1'b0;
```

**判据**：调试字显示 `mmcm_locked = 1`，且 24 MHz XCLK 存在。

> ⭐ **教训**：当 MMCM 输入处在低端（约 50 MHz）时，**必须用输入分频器**让鉴相器看到合法频率。
> 并且**永远用 LOCKED 去门控输出时钟**。

### 2.2 PCLK 时序约束必须反映真实频率（噪声的真凶）

| | 约束值 | 含义 |
|---|---|---|
| 错误 | `create_clock -period 42.667`（另有拷贝写成 `41.666`） | 按 24 MHz 分析 |
| 正确 | `create_clock -period 10.000 -name cmos_pclk_clk` | 按 100 MHz 分析 |

**本设计的实际 PCLK 是 84 MHz**（`0x3035 = 0x41`），却按 24 MHz 做时序分析
→ **输入捕获路径从未被优化过**。

**现象**：画面在水平方向是有结构的（HREF/VSYNC 分帧正常），
但**每一行都有约 790 次数值跳变** —— 是噪声，不是场景。

**判据**：改成 10 ns 后，每行约 790 次跳变的噪声消失。

> ⭐ **这是"噪声真凶"。** 在找到它之前，噪声被反复归因于信号完整性、走线、
> 上拉电阻、模组质量。
>
> **规律：只要时钟约束比实际频率宽松，整条输入路径就处于"未被约束"状态。
> 工具不会报错，只会给你一个没优化过的设计。**
>
> 注意：PCLK 应按**传感器 PLL 的实际输出**约束，**而不是你喂给传感器的 XCLK**。

### 2.3 DVP 输入延迟缺少 `-clock_fall` → 无法满足的保持违例

**现象**：多次构建 WNS 在 −7.0 到 −10.5 ns 之间；
`cmos_data[*] -> data_d_reg[*]` 上有 **−3.04 ns 的保持违例**；
"布线后修保持"阶段空转数小时。

**根因**：**OV5640 在 PCLK 的下降沿发射 DVP 数据**，而采集逻辑在上升沿采样。
没有 `-clock_fall` 时，工具会**按错误的边沿**去检查输入路径，得出不可靠的保持要求。

**修复**：对 `cmos_data` 的输入延迟加 `-clock_fall`。

**报告结果**：WNS +0.538 / TNS 0.000 / **WHS −0.575 → +0.018** / THS 0.000。

> ⚠️ **诚实提示**：本项目当前代码树里**没有任何 XDC 含 `-clock_fall`**，
> 也没有 `cmos_data` 的 `set_input_delay`。这条约束**只存在于叙述记录里，没有落到文件上**。
> 用它之前请自己重新测量建立/保持关系。

> ⭐ **教训**：对于**下降沿发射**的 DVP 总线，输入延迟必须参考 PCLK 的**下降沿**。

### 2.4 调试字被反复重新打包 —— 不同构建的数字不可比

**现象**：`0x41220000` 的读数在不同构建之间无法比较；
"静默丢像素"和"SOF 是否存在"最初完全不可见。

**实际出现过的几种打包方式**（按时间顺序）：

| 打包 | 来源 |
|---|---|
| `{mmcm_locked, xclk_gate, sccb_ack, fifo_ovf, pclk_free8[3:0]}` | `capture_v4/v5.tcl` |
| `{[7] mmcm_locked, [6] xclk_gate, [5] sccb_ack(sticky), [4] retry, [3:0] pclk_free8}` | `verdict_v5.tcl` |
| `{[7] mmcm_locked, [6] sccb_ack, [5] fifo_ovf, [4] sof_seen, [3] frame_skip_ge10, [2:0] sof_cnt}` | `diag_read.tcl` |
| 最终：`dbg_pclk_cnt = line_cnt_r[11:4]`（两次被接受的 VSYNC 之间的 HREF 窗口数 ÷ 16），`dbg_i2c_done = mmcm_locked` 走独立的 1 位通道，`dbg_retry = retry_pulse[0]` | `ov5640_cam_top.v` |

最终解码表的意义（很值得学）：

```
720/16 = 45  → 几何正确
360/16 = 22  → VSYNC 每帧来 2 次
180/16 = 11  → 每帧 4 次 = 4 份堆叠的副本
```

另外在 FIFO 写侧加了**粘滞的 `fifo_ovf`** 位，让**静默丢像素**变成一个可读的标志。

> ⭐ **教训**：**暴露一个决定性的标量 + 一组粘滞故障位**；
> 打包方式一改，**必须同步更新所有解码器和文档**，否则你会拿不可比的数字互相比较。

## §3 第三层：数据对不对（几何、极性与分帧）

### 3.1 行结束标记从来没进 FIFO → 数据流完全没有行边界

**现象**：DMA 报 `ERR_FSZ_MORE`，**零帧提交**，帧计数卡在 1，DDR 里还是预填值。

**根因**：行结束标志在 **HREF 下降的那一拍**抬高，
而**同一拍 `px_valid_w = 0`**，所以 `fifo_wr` 是低的 ——
**行结束位永远写不进 FIFO**。于是这条 AXI-Stream **完全没有行结尾**。

**修复**：让行结束标记**与该行的最后一个像素同一拍**：

```verilog
line_end_w = href_d & ~cmos_href;
```

最终 RTL 里改为在 `href_fall` 时把挂起的像素刷出并置 `px_eol_w=1`
（用 `px_in_line >= MIN_LINE_PX` 做毛刺过滤）。

**判据**：仿真 `SIM_RESULT=PASS`（128 拍、2 帧、errors=0）；板上开始产生确定的行结束。

> ⭐ **教训**：**行尾标记必须搭载在一个真实的数据拍上。**
> 绝不要用那个"恰好会抑制数据"的有效门去限定它。

### 3.2 `tuser`（帧起始）每行都置位，而不是每帧一次

**现象**：DMA 把每一行都当成新帧；写入器的写指针被逐行复位；画面垂直方向乱序。

**根因**：`frame_on` 在**每一行结束时被清除**，于是每行的第一个像素看起来都像帧起始。

**修复**：只在**被接受的 VSYNC 下降沿**清除帧标志。

**判据**：仿真 + 板上 `sof_seen = 1`，每帧一个 SOF。

> ⭐ **教训**：**SOF 必须从帧边界（VSYNC）导出，绝不能从行边界导出。**

### 3.3 字节配对 off-by-one：每行丢最后一个字节

**现象**：仿真输入 2560 字节，只配出 **1279 个像素**（少一个）；
板上实测行结束落在**第 1279 个**而不是第 1280 个像素上。

**根因**：采集使能用的是 `href_d && cmos_href`（**延迟 HREF 与当前 HREF 相与**）。
延迟 HREF 多保持一拍，于是**每行最后一个字节被跳过**，整个字节配对发生偏移。

**修复**：在**延迟后的 HREF** 为高时采集（`href_d`），
并在 `href_fall` 以及被接受的 VSYNC 两处都刷出挂起像素。

> ⭐ **教训**：**绝不要把同一个选通信号的"延迟版"和"当前版"相与来当数据限定条件。**
> 数据与它的使能必须**用相同级数的流水对齐**。

### 3.4 在每个 HREF 边沿强制字节相位 → 画面被切成方块

**现象**：每约 512 像素出现一条可见接缝，**画面看起来被切成方块**。

**根因**：字节相位 `byte_sel_r` **在每个 HREF 上升沿都被强制复位**。
而本板的 **HREF 在一行之内有多个脉冲**（每个约 512 像素），
于是字节配对在每个脉冲处都被重新对齐。

**修复**：让字节配对**跨 HREF 边界连续运行**。
（`px_in_line` 仍在 `href_rise` 复位，但只用于 `MIN_LINE_PX` 毛刺过滤。）

RTL 里的理由写得很好：*跨脉冲边界的像素只是一个亚像素效应，而强制的相位复位不是。*

> ⭐ **教训**：**HREF 不保证每行只有一个干净的脉冲。**
> 任何以"HREF 每个边沿"为键的对齐逻辑都会把画面切片。

### 3.5 HREF 毛刺造成额外的行结束 → 画面垂直重复 4 次

**现象**：720 行的缓冲区里装了 **4 份 180 行的图**；lag-180 相关 0.98；
传感器 VTS = 740，而 `740 / 4 = 185` —— 与 4 倍重复吻合。

**根因**：行结束来自**每一个 HREF 下降沿**，而 HREF 带有额外的亚行脉冲
（日志中记录为约 320 px、约 512 px、"约四分之一行"）。
当 `MIN_LINE_PX = 64` 时这些毛刺通过了过滤，于是**每条真实行产生 4 个行结束**，
写入器每条相机行前进 4 行。

**修复**：`MIN_LINE_PX = 512` —— 真实行是 1280（≫ 512），毛刺约 320（< 512）。

**判据**：板上 lag-180 从 0.98 降到 0.85；仿真 PASS。

> ⭐ **教训**：**用"最小像素数"过滤行结束事件，
> 阈值取在"实测毛刺宽度"与"真实行宽"之间。**
> **绝不要接受任何 HREF 边沿都当作行结束。**
>
> ⚠️ 但注意：这个修复**没有彻底解决**问题（0.98 → 0.85）—— 见下一条。

### 3.6 最终方案：几何完全由像素计数决定

因为阈值过滤只是缓解，本项目最终改成：

1. **`frame_writer` 纯顺序滚动写入**，不做任何行距假设，
   帧边界**自己生成**：`REAL_FRAME_PX = 32'd738000`（= 1025 × 720 像素 = 1,476,000 字节）
2. **`cam_top` 去掉逐 HREF 的字节相位强制**，让配对跨 HREF 连续
3. **PC 端从数据实测行宽并据此渲染**

**残留现象（已知并接受）**：滚动缓冲没有帧同步，
缓冲区里会出现**一处滚动回绕接缝**（位置取决于抓帧时刻），对识别无影响。

> ⭐ **结论性经验**：**只要几何依赖某个可能带毛刺的信号，就永远受制于信号质量。**
> 把几何改成由**自己的计数器**决定，问题就从"信号完整性"变成了
> "一个可以仿真的确定性问题"。
>
> **代价**：你从此自己负责帧边界（必须知道真实帧像素数 738,000），
> 并且要接受那个回绕接缝。

### 3.7 VSYNC 极性：引脚是低有效，必须取反

**现象**：用引脚的原始极性时，帧同步边沿在错误时刻触发 ——
在一个"30 fps"的传感器上**实测到 64.5 个帧同步边沿/秒**（每帧好几个）；
画面水平方向完美但**垂直方向乱序，且呈 4 行周期**；
每一个多余的边沿都复位了写入器的写指针。

**根因**：本板的 **VSYNC 是低有效**。可用的参考实现**把它取反**：

```verilog
cmos_vsync_r1 <= ~cmos_vsync_i;
wire vs_p = !cmos_vsync_r2 && cmos_vsync_r1;
```

**修复**：

```verilog
vsync_d       <= ~cmos_vsync;
wire vsync_fall_d = vsync_d & ~vsync_d2;
```

**判据**：修复前 64.5 边沿/秒，修复后每帧一个被接受的边沿，`sof_seen = 1`。

> ⭐ **教训**：**不要从数据手册的时序图去推断 DVP 的 VSYNC 极性 —— 去测量它。**
> 并且在写分帧逻辑之前，**先和一个能正常工作的设计对比极性**。

### 3.8 去抖阈值必须在你修好信号之后重新推导

**现象（两种失败模式）**：

- 阈值设 500 行：**真实帧同步被完全拒绝** → `tuser` 从不触发 → 写入器自由运行 →
  3 个约 240 行的帧挤进 720 行缓冲 → 正好就是看到的**三份垂直重复副本**。
- 完全不过滤：**单个毛刺就能在一帧中途复位写指针**，产生若干重叠副本。

**根因**：那个 500 是从**修复前**的"64.5 边沿/秒"测量推出来的 ——
而 VSYNC 极性一修，那个数字就失去意义了。

**修复**：`MIN_LINES_PER_FRAME = 64`，配 3 级 VSYNC 滤波：

```verilog
wire vsync_accept = vsync_flt_r[2] && (line_cnt_r >= MIN_LINES_PER_FRAME);
```

> ⭐ **教训**：**修好一个信号之后，要从它重新推导所有基于它的阈值。**
> 用被污染的数据算出来的阈值，会把真实事件拒之门外。

### 3.9 传感器寄存器：格式与通道顺序

**现象**：怀疑像素格式不对（参考工程写 `0x4300 = 0x60`，本表写 `0x61`）；
另外怀疑过 R/B 被交换。

**结论**：**保留 `0x4300 = 0x61`，没有做 R/B 交换。**

**判据（很有价值的方法）**：**测量各通道均值**：

```
本设计:   R 79.4 / G 91.8 / B 80.8   → R ≈ B（相差 1.8%）
参考帧:   R 91.9 / G 101.3 / B 104.7
```

**R ≈ B 就排除了 R/B 交换**；约 9% 的绿色偏多是荧光灯下的白瓷砖墙造成的。

另外 `0x501f = 0x01`（ISP 输出 RGB）与 `0x300e = 0x58`（使能 DVP）与官方 demo **逐字节相同**。

> ⭐ **教训**：**用各通道均值来解决"通道顺序"的怀疑 —— `R ≈ B` 就能排除 R/B 交换**，
> 然后再去动格式寄存器。`0x4300` 差 1 个 LSB **不一定**是 bug。

### 3.10 寄存器表本身的坑

| 坑 | 说明 |
|---|---|
| **`LUT_SIZE` 会截断表** | `assign LUT_SIZE = 1'b1 + 8'd255;` = **256**，只发出索引 0..255。追加在索引 258 的表项**永远写不出去**（补丁里对 `LUT_SIZE` 的替换没匹配上文件文本，另有三个寄存器从未插入） |
| **同一寄存器在表里出现两次** | **后面的索引生效**。追加"覆盖项"是可行的改法，但要清楚语义 |
| **表内注释会过期** | `0x3035 = 0x41` 的文件内注释写着"15 fps"，而参考工程对同一个值注释"PCLK = 84 MHz"（由 HTS/VTS 推算是 60 fps），实测帧率又是 7.5 fps。**三个说法互不相容** |
| **`0x3820`/`0x3821` 的补丁未达成目标** | 补丁把 `0x3820` 从 `0x40` 改成 `0x47`，期望恢复 1280 行宽；但**补丁之后所有交付帧仍然是 1025×720** |

> ⭐ **教训**：扩展基于 `case` 的寄存器 LUT 时，**长度常量是修复的一部分**。
> 保持索引连续，并在任何补丁之后**断言 `size >= 最大索引 + 1`**。
>
> 以及：**寄存器表的假设在重新测量之前只是假设。**

## §4 采集通路的数字设计要点

### 4.1 跨时钟 FIFO：格雷码同步链被接到了错误的时钟域

**现象（两个，都是实测的）**：

- **整个设计里唯一失败的时钟对**：`clk_fpga_0 -> cmos_pclk_clk` WNS **−9.212 ns** / TNS −204.172 / 24 个失败端点；
  反向 −5.564 / −158.846 / 34 个；
  最差路径 `u_fifo/rptr_sync2_reg[5]/C -> u_fifo/mem_reg/WEA[0]`，`Requirement = 0.005 ns`
- `fifo_ovf = 1`，丢像素、行长度错误

**根因**：`rptr_sync` **被读时钟**打拍、`wptr_sync` **被写时钟**打拍 ——
**每个指针被同步进了它自己那一侧**。后果是：

- `wr_full` 由**读域寄存器**组合计算得出，却去驱动 BRAM 的写使能
  → 形成一条**裸的 `clk_fpga_0 -> cmos_pclk_clk` 路径**
- full/empty 都没有经过同步器采样

**修复**：把两个 always 块的时钟**对调**
（读指针同步进**写时钟**用于 `wr_full`；写指针同步进**读时钟**用于 `rd_empty`），
并在 XDC 里声明两个域异步：

```tcl
set_clock_groups -asynchronous -group [get_clocks cmos_pclk_clk] -group [get_clocks clk_fpga_0]
set_false_path -from [get_clocks clk_fpga_0] -to [get_clocks clk_24m]
```

**判据**：板上 `fifo_ovf` 由 1 变 0；失败的时钟对消失；
**项目历史上时序第一次收敛**（WNS −7.0..−10.5 → −9.2 → **+0.538**，WHS +0.018）。

> ⭐ **教训**：在手写格雷码 FIFO 里，
> **每个指针必须被同步进"对面"的时钟域**，
> 而且**在读域算出来的 full 标志绝不能去驱动写使能**。

### 4.2 AXIS 握手不合规：无条件弹出 FIFO

**现象**：`tvalid` 为高时 `tdata` 发生变化（协议违规）；
下游拉低 `tready` 时，数据被**静默丢弃**。

**根因**：`assign fifo_rd = ~fifo_empty;` —— **每个周期都弹出**；
没有输出保持寄存器；而该 FIFO 是**同步读**（`rd_data` 在 `rd_en` 之后**一拍**才有效）。

**修复**：加一级保持寄存器并支持背压：

```verilog
can_issue     = (~axis_valid_r) | axis_consumed;
assign fifo_rd = (~fifo_empty) & can_issue;
```

并在 `tready` 到来之前**保持** `tdata` / `tvalid`。

**判据**：仿真注入 `tready` 停顿（每 97 拍里停 23 拍）后 **0 错误、tdata 稳定**：
`[TB] checked 128 beats, 2 frames, errors=0; fifo_ovf=0 mmcm_locked=1; SIM_RESULT=PASS`。

> ⭐ **教训**：用同步读 FIFO 时，**只有在下一拍输出寄存器会空出来的时候才可以发起读**，
> 否则你必须自己缓冲。

### 4.3 修握手时自己造出来的读指针死锁

**现象**：一个拍都出不来，采集通路完全无输出。

**根因**：`rd_en` 被 `fifo_dout[17]` 门控。
而在**同步读 FIFO** 上，`fifo_dout` 只在 `rd_en` 之后**一拍**才有效 ——
**读操作永远无法发起**：循环依赖 / 永久死锁。

**修复**：读决策只依赖 `fifo_empty` 与输出寄存器状态；
SOF/丢包决策放在**读之后**、在保持寄存器里做。

> ⭐ **教训**：**永远不要让同步读 FIFO 的读使能依赖它自己的数据输出。**

### 4.4 REQP-1840：异步复位到达 BRAM

**现象**：

```
[DRC REQP-1840] RAMB18 async control check: ...
  design_1_i/cam_top/inst/u_fifo/mem_reg ... driven by a register that has
  an active asynchronous set or reset. This may cause corruption of the
  memory contents and/or read values
```

**根因**：存储器的控制端被一个带异步置位/复位的寄存器碰到
（异步 FIFO 的复位结构延伸到了 BRAM）。

**状态：未修改，记录为已知的小问题。** 采集画面看起来干净，
但**如果出现随机坏行或噪声，优先查这里**。

缓解已经在 RTL 风格里：存储器的写块和读块**不含任何复位**
（`always @(posedge wr_clk) if (wr_ok) mem[...] <= ...`，读侧同理），
这正是推荐的 BRAM 写法。

> ⭐ **教训**：**保持 BRAM 的读写端口不含任何复位。**
> 若出现 REQP-1840，确认存储器使能来自一个**没有异步置位/复位**的寄存器。

### 4.5 为什么最终抛弃了 VDMA

这一节解释了"为什么要自己写采集 RTL"：

**现象**：软件动作之前 `SR = 0x00014811`，且 W1C 写（`0x43010034 = 0xFF0`）清不掉；
各种 VSIZE 全部报 `ERR_FSZ_MORE`；跑 7 秒后 64/64 个字仍是预填值；帧计数卡在 1。

**根因（四条）**：

1. **数据流在 S2MM 还没启动时就到了**，把 `ERR_INTERNAL` / `ERR_FSZ_MORE` 锁存住，
   而**通道复位清不掉它们**
2. **CR bit6（Fsync Source Select）没置位** —— 驱动需要 `0x00010053` 而不是 `0x00010013`，
   否则 IP 去听一个**没连接的 `s2mm_fsync` 端口**
3. **BD 的 AXIS 接口没有带 TUSER**（缺 `HAS_TUSER`），
   所以虽然网表里有这个网络，**IP 从来没有收到它**
4. **`C_USE_S2MM_FSYNC=0`（自由运行）时该 IP 根本无法在时序内实现**
   （Explore: WHS −7.100 / THS −4801；Quick: WNS −7.198 / WHS −5.015），
   配置进 PL 的设计是死的

**处置**：先把 `cam_top` 配置后的静默窗口从 11 帧（约 0.37 s）延长到 130 帧（约 4.3 s），
好让软件先编程并启动 S2MM；**最终删掉 VDMA，改用自研 `frame_writer`**
（单拍 64 位 AXI 写直接进 `S_AXI_HP3`）。

**判据**：修静默窗口后 `SR = 0x00010000`、err = 000；
换掉 VDMA 后 DDR 里是**真实像素**而不是预填值。

> ⭐ **教训**：**在传感器开始出流之前先启动 S2MM**；
> **置上 Fsync 源选择位**；
> **在生成的网表里核实 BD 接口真的带了 TUSER** ——
> 或者干脆绕过这个 IP。

## §5 提炼过程 —— 从哪些失败与观察中总结出来

1. **顺序错了，代价是数周。** 最初先调几何（分帧、行距、tlast），
   而底层通信（SCCB）和时钟（PCLK 约束、MMCM 锁定）都还没建立。
   最终固化的顺序是：**先能通信 → 再有数据 → 再谈数据对不对**。

2. **"假成功"在本项目出现了三次，每次形式不同**：
   `i2c_config_done = 1`（ACK 校验被注释掉）、
   `IOBUF` 三态极性反了（SCL 在动但 SDA 从未拉低）、
   行结束标记从未进入 FIFO。
   **共同点：设计用"自己的状态机走完了"代替了"外部世界确认了"。**

3. **"从数据自证"打败了"从文档推理"。**
   行宽 1025 的发现靠的是相邻行相关搜索；
   通道顺序的结论靠的是各通道均值。
   **当所有推理都对不上时，设计一个只依赖数据本身的测量。**

4. **最贵的单个错误是"假设行宽 1280"**，
   它制造了一个"每 4 行重复"的假象，把方向引向 FIFO 和时钟，持续很久。

5. **"修好一个信号后要重新推导依赖它的阈值"** 这条来自一次真实的自伤：
   VSYNC 极性修好之后，用旧测量推出的 500 行去抖阈值把真实帧同步完全拒绝了。

6. **跨时钟 FIFO 的同步链接反时钟域** 是本项目唯一失败的时钟对，
   也是**时序第一次收敛**的直接原因 ——
   说明"时序不收敛"有时根因不在约束，而在 RTL 的架构错误。

7. **物理层（PWDN 悬空、RST 悬空、IO 域不匹配、模组身份搞错）花了很久**，
   因为它们的症状与协议层故障**完全相同**（零 ACK、无数据）。
   **这类"症状相同、层次不同"的问题，必须设计能区分层次的实验**
   （例如用一个时钟源不可能失败的诊断比特流，逐引脚注入）。

8. **两次无效的"XCLK 死了"测量**给了最普适的一课：
   **在用负向测量下结论之前，先证明探针有效。**
   悬空输入恒为 1，探针没接的时候，"没有信号"和"有信号"读数一样。
