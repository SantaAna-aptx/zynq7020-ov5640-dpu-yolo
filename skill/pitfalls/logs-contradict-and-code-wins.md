# 工程日志会自相矛盾 —— 建立权威顺序，并如实标注未证实项

| 项 | 内容 |
|---|---|
| **类型** | 踩坑清单 + 方法 |
| **适用场景** | 一个持续数周的工程，日志、注释、文档、脚本里对同一件事有多种说法；或者你要根据这些记录**写报告、做复盘、交接给别人** |
| **使用方法** | 按 §3 的"权威顺序"裁决每一条矛盾；按 §4 的三档标注法把结论分类，再写进报告 |
| **失效条件** | 如果项目只有单一权威记录（例如从零开始且只有一份设计文档），本项不适用。本项针对的是**长期、多人/多轮、多份记录并存**的工程 |
| **已验证效果** | 在本项目中一次性找出 **13 处**互相矛盾的说法，其中 **2 处直接推翻了先前写进项目 README 的结论**；其余被分类为"已证实 / 未证实 / 已排除" |
| **投入** | 梳理一次约 1–2 小时；**收益是避免把错误结论写进提交材料** |

---

## 1. 为什么必然会矛盾

这不是"记录不认真"，而是长期工程的**结构性现象**。三个原因：

### 1.1 结论会被新证据推翻，但旧结论不会自动消失

本项目里"行宽是 1280"曾经是一个**有数据支持的结论**（相关系数 0.977），
后来被更强的证据推翻（全范围搜索发现 1025 的相关是 0.9929）。
但**两句话都留在同一份文件里**：

> 同一份 `CAMERA_CAPTURE_FINAL_FINDINGS.md`：
> 第 76 行说"1280 为最佳匹配（corr 0.977）"，
> 第 109–120 行说"1280 极低，1025 最佳（+0.9929）"。

### 1.2 注释与代码会分道扬镳

代码改了，注释没改。本项目最典型的例子：

```verilog
// ov5640_cam_top.v 文件头（第 1–6 行）：
//   "33kHz push-pull SCCB ... Push-pull SDA at all times (in i2c_timing_ctrl file, OE=1)"

// 而实际代码（i2c_timing_ctrl_reg16_dat8_wronly.v 第 386 行）：
assign i2c_sdat_OE = i2c_sdat_out;        // ← 开漏，与注释说的正好相反
```

**文件头说的是"推挽"，代码是"开漏"，而修复 SCCB 的关键恰恰是改成开漏。**

### 1.3 同一份记录里的数字来自不同的测量口径

- "30 fps"（SOF 计数器，把每个 SOF 当一帧）
- "7.5 fps"（行计数器回绕，263,423 次采样 / 6 秒）

两者若都成立则互相矛盾。**很可能是同一个缺陷从两个角度被测量**——
`30 / 7.5 = 4`，正好等于"每帧多出 4 个边界"那个故障模式（它造成了画面 4 次垂直重复）。

## 2. 本项目实际发现的 13 处矛盾

记录下来不是为了自我批评，而是**说明这类矛盾有多普遍**，以及它们值得被系统性地找出来。

| # | 矛盾内容 | 处置 |
|---|---|---|
| 1 | **帧率**：SOF 约 30/s vs 实测周期 133.33 ms = 7.50 fps | 标注为未解决；实测值优先，30/s 疑为异常边界计数 |
| 2 | **行宽搜索**：同一文件里先写 1280 最佳（0.977），后写 1025 最佳（0.9929） | 以 1025 为准（证据更强、且被最终渲染结果验证） |
| 3 | **HREF 行为**：`frame_writer.v` 说"HREF 在本板从不下落，下降沿计数器恒为 0"；`cam_top.v` 说 HREF 每行有多个脉冲；引脚探针实测 HREF 高 39 / 低 21 次 | 三说互斥。以引脚实测为准（HREF 会下落），探针计数为 0 疑为计数器接错 |
| 4 | **HREF 毛刺宽度**：约 320 px vs "每个约 512 px" vs 整个 HREF 窗口约 3700 PCLK 字节（而假设是 2560） | 三个数字被用来支持不同的修复；标注为"毛刺宽度未经一致测量" |
| 5 | **SDA 推挽 vs 开漏**：文件头说推挽（OE=1），代码是开漏，修复记录说开漏才是解药 | **以代码为准**（开漏） |
| 6 | **SCCB 速率**：250 kHz（审计文档）vs 33 kHz（代码 + 修复记录） | 以代码为准（33 kHz） |
| 7 | **FCLK0 寄存器值**：`0x00400500` vs `0x00201400`，两者都被标注为"50 MHz" | 同一个字段不可能有两种正确解码，**至多一个对**；以能复现功能的那次记录为准 |
| 8 | **`0x3035`**：表内注释说 `0x41` = 15 fps；参考工程对同一值注释 "PCLK = 84 MHz"（由 HTS/VTS 推算 60 fps）；另说 `0x21` = 30 fps；**实测 7.5 fps** | 四个说法互不相容，**全部标注为可疑**，以实测帧率为准 |
| 9 | **表项数**："252 项"（多份文档）vs `LUT_SIZE = 256`、实际有索引到 258 的条目 | 以代码为准（256，且 258 不可达） |
| 10 | **`0x3820`/`0x3821`**：补丁声称这是"行宽 1025 的最可能原因"，但补丁**实施后所有交付帧仍是 1025** | **目标未达成**，必须如实记录为"未证实" |
| 11 | **模组 RST**：一处说"未引出、内部上拉、绝不能接 GND"；另一处说实际模组有 RST 引脚、悬空、必须接 3.3 V | 矛盾源于**模组型号不同**（见 #13 类问题）；以实际模组的丝印与实测为准 |
| 12 | **PWDN 结果**：一处把"PWDN 接地"当作已确认的根因与一行修复；另一处记录接地后**仍然零 ACK** | **标注为"已排除"而非"已修复"** |
| 13 | **`-clock_fall`**：两处报告说这是已应用并验证的修复，但**当前代码树里没有任何 XDC 含 `-clock_fall`** | 约束**只存在于叙述里，没有落到文件上**。用它之前必须重新测量 |

## 3. 权威顺序（遇到矛盾时的裁决规则）

按下面的顺序裁决，**上位否决下位**：

```
① 板上/仪器实测数据            ← 最高
② 可运行的代码 / 约束文件的实际内容
③ 生成产物本身（md5、读回值、日志输出）
④ 当次会话的过程记录
⑤ 事后写的总结文档
⑥ 文件头/代码块注释            ← 最低
```

三条具体推论：

- **代码优先于注释**（矛盾 #5、#6、#9 都是这样裁决的）。
  "读赋值语句，不要读文件头。"
- **实测优先于文档**（矛盾 #1、#2、#7、#8）。
- **"产物"优先于"叙述"**（矛盾 #13）：
  说"加了某个约束"不算数，**在文件里找到它才算数**。

> ⚠️ 但要注意：**实测也可能错**（矛盾 #3 的探针计数器、两次无效的"XCLK 死了"测量）。
> 所以实测数据要附带**它的测量方法**，
> 而"探针是否有效"本身需要一次正对照来证明。

## 4. 三档标注法（写进报告的正确姿势）

不要试图把矛盾"抹平"。**分三档如实标注**，这本身就是工程严谨性的体现：

| 档位 | 含义 | 写法示例 |
|---|---|---|
| ✅ **已证实** | 有可复现的实测数据或产物支持 | "PCLK 约束必须为 10 ns —— 实测每行约 790 次跳变的噪声消失" |
| ⚠️ **未证实** | 有理论依据、有局部证据，但**未达到目标或未做端到端验证** | "`0x3820` 补丁**未达成**恢复 1280 行宽的目标，补丁后所有交付帧仍为 1025×720" |
| ❌ **已排除** | 做过实验并否定了这个假设 | "PWDN 接地后仍然零 ACK —— PWDN 记为**已排除**，而非已修复" |

**为什么"未证实"这一档最重要**：它防止把**假设**当成**结论**传下去。
本项目里有两处"看起来已经修好了"的说法（`0x3820` 补丁、`-clock_fall` 约束），
如果照抄进提交材料，就是**把未验证的东西当成果报告**。

## 5. 可操作的做法

1. **写报告前，先做一次矛盾扫描。**
   把关于同一件事的所有说法并列出来（本项目的 13 条就是这么找出来的），
   逐条按 §3 的权威顺序裁决。

2. **在代码里，把"为什么"写在赋值旁边，而不是文件头。**
   文件头最容易过期。本项目最终把关键理由写进了 RTL 赋值处的注释
   （例如"不要让同步读 FIFO 的读使能依赖它自己的数据输出"）。

3. **凡是"只存在于叙述里"的修复，要么补进文件，要么标注为未落实。**
   矛盾 #13 的 `-clock_fall` 就属于这一类。

4. **让关键结论带上"验证方式"。**
   "行宽是 1025" 之所以可信，不是因为写在文档里，
   而是因为**"对候选宽度重排数据、算相邻行相关系数"这个方法可以重跑**。
   → 记录结论时**连同测量方法一起记录**。

5. **给测量本身留一条正对照。**
   两次无效的"XCLK 死了"测量之所以发生，是因为**探针没接**时悬空输入也读恒定 1。
   凡是负向结论（"没有信号""没有响应"），先证明探针有效。

6. **交付前把矛盾清单本身也交出去。**
   它比一份"完美无瑕"的报告更可信 ——
   因为它展示了**你知道哪些是确定的、哪些还不确定**。

## 6. 提炼过程 —— 从哪些失败与观察中总结出来

1. **触发点是一次"核对代码与文档是否一致"的检查**，
   本意只是确认几处细节，结果一次找出 13 处矛盾。

2. **最有冲击力的两条**（#10 与 #13）都不是"说法不同"，
   而是"**声称已完成的修复，实际上没有达成目标或没有落到文件里**"：
   - `0x3820` 补丁的目标是恢复 1280 行宽，**补丁后仍然全是 1025**
   - `-clock_fall` 被报告为已应用验证，**但树里根本没有这条约束**

   这两条直接改变了对"项目已经完成到什么程度"的判断。

3. **两处曾经写进项目 README 的错误说法因此被修正**：
   原先写"追加 `0x3820`/`0x3821` 消除上下分屏、修正 `0x4300=0x61` 修正 R/B 顺序"；
   实际上 ① 日志**从未**把分屏归因于这两个寄存器
   （分屏/接缝归因于逐 HREF 强制相位与 4 次垂直重复），
   ② `0x4300` **根本没有被改**，而实测各通道均值 R≈B **证明不存在 R/B 交换**。

4. **派生出一条通用做法**：报告里分"已证实 / 未证实 / 已排除"三档。
   这不只是诚实，它同时**保护了作者** ——
   把未验证的东西明确标出来，比被评审发现要好得多。

5. **最终认识**：**矛盾不是记录的失败，而是长周期工程的常态。**
   有价值的能力不是"记录得毫无矛盾"，而是**能从一堆互相矛盾的记录里，
   按证据强度裁决出可用的结论，并如实标出剩余的空白**。
