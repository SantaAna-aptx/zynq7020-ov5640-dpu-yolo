# RTL 改了但板上毫无变化 → Block Design 的 OOC 子工程用了旧网表

| 项 | 内容 |
|---|---|
| **类型** | 踩坑清单 |
| **适用场景** | RTL 源码放在 Block Design 的 **module reference** 里，改了 RTL（或改了 IP 参数）后重建，**构建成功、时序收敛，但板上行为完全没变** |
| **使用方法** | ① 构建前强制重置所有 BD 的 OOC 子工程；② 构建后比对**比特流载荷的 md5**（不是整个文件的 md5） |
| **失效条件** | 适用于 Vivado 把 BD 里的 module reference 放到**独立 OOC 综合工程**的场景。纯 RTL 工程（无 Block Design）不存在这个 OOC 分层，但"主工程综合没重跑"的同类问题仍然可能发生 |
| **已验证效果** | 定位后强制重置 OOC 子工程，改动才开始进入比特流；此前**相隔 3 小时、中间重写过 RTL 的两次构建，比特流载荷逐字节完全相同** |
| **投入** | 定位**很久**（因为所有表面指标都显示"成功"）；修复是一行 Tcl |

---

## 现象

改了 RTL → 构建成功 → 时序收敛 → **上板行为与改动前完全一样**。

最折磨人的地方在于**每一个表面指标都是"成功"**：

- 综合没有报错
- 实现没有报错
- 时序收敛
- 比特流生成成功
- 加载成功，系统也能跑

只有"行为"没变。

## 根因

`cam_top` 这类模块是以 **module reference** 的形式放进 Block Design 的。
Vivado 会为它在**独立的 OOC（out-of-context）综合子工程**里做综合，
例如 `design_1_cam_top_0_synth_1`。

**只 `reset_run synth_1` 不会让这些 OOC 子工程重跑。**
主综合于是拿着**缓存的旧网表**去做实现 —— 于是你得到的是一个"用旧 RTL 构建的新比特流"。

## 决定性证据

**相隔 3 小时、中间重写过 RTL 的两次构建，比特流载荷逐字节完全相同**（md5 一致）。

> 这条证据之所以是"铁证"，是因为它排除了所有解释：
> 只要构建过程重新综合过那份 RTL，输出不可能逐字节相同。
>
> **这也给出了一个极好的通用验证手段 —— 见下。**

## 修复

构建前**强制重置所有 BD 的 OOC 子工程**：

```tcl
foreach r [get_runs -quiet -filter {IS_SYNTHESIS && NAME =~ "design_1_*"}] {
    reset_run $r
}
```

参考脚本：`rebuild_force_ooc.tcl`。

## ⭐ 通用验证手段：比对**载荷** md5，而不是整个文件的 md5

比特流文件前面有一段**头部**（本例 160 字节），包含构建时间戳之类的信息，
**每次构建都会变**。所以：

- **整个文件的 md5 每次都不同** → 无法用来判断"内容是否真的变了"
- **去掉头部后的载荷 md5 才是内容的指纹**

**规则**：改了 RTL 或 IP 参数之后重建，**载荷 md5 必须与上一版不同**。
如果相同，说明你的改动根本没进比特流 —— 无论工具报告了什么。

```
构建 → 去掉比特流头部 → 算载荷 md5 → 与上一版比较
                           │
                   相同 ───┴─── 不同
                    │              │
             改动没生效        改动已进入
         （去查 OOC / IP 锁定）
```

> 这条检查只要几秒，却能挡住一整轮"构建 40 分钟 + 上板验证"的空转。
> **在本项目里，它是一个被反复使用的构建门禁。**

## 同类问题

同样表现为"**工具报告成功，但改动没生效**"的还有另一条独立机制：
IP 处于 locked 状态时，Vivado 不更新它的综合检查点，只打印警告然后沿用旧网表。
见 [`vivado-stale-ip-netlist.md`](vivado-stale-ip-netlist.md)。

**两者的排查入口相同**：在构建日志里主动搜警告关键词，并核对载荷 md5 或回板上读回配置。

## 提炼过程 —— 从哪些失败与观察中总结出来

1. **最初的错误方向**：行为没变时，第一反应是"是不是加载错了比特流"、
   "板上是不是有旧文件"、"缓存问题"。
   于是反复核对 md5、反复重新加载、甚至换 SD 卡 —— 都无效，因为**比特流本身就是旧的**。

2. **转折点是比较"两次构建的产物"**。
   一开始只比整个文件的 md5，发现不同，就以为改动进去了；
   后来意识到**头部含时间戳，每次必然不同**，改为比对载荷部分，
   才发现两次构建**逐字节相同** —— 这是决定性的。

3. **这条证据同时给出了长期可用的门禁**：
   从此"载荷 md5 必须变化"成为构建流程的一部分，
   而不是等问题出现后再去查。

4. **教训**：**"构建成功"这个词在 Vivado 里是有层次的。**
   综合成功、实现成功、时序收敛、比特流生成成功 —— 这些**都不能证明你的改动被采纳了**。
   唯一可靠的证据是**产物内容发生了变化**（载荷 md5）或**回板上读回实际配置**。

5. **与 IP 锁定那条坑的关系**：
   两者是不同机制（一个是 OOC 子工程没重跑，一个是 IP 检查点过期），
   但**症状和排查入口完全相同**。所以在这个技能包里它们互相交叉引用 ——
   遇到"改了没生效"，两条都要查。
