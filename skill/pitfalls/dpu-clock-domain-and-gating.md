# DPU 计算域死锁 → 先确认 FCLK 是否真的活着（内核会门控未使用的时钟）

| 项 | 内容 |
|---|---|
| **类型** | 踩坑清单 |
| **适用场景** | Zynq-7000 上 PL 加速器（DPU / 自研 IP）控制口可访问、寄存器读得出来，但**计算任务超时或无中断** |
| **使用方法** | 按"排查步骤"逐条定位：先分清"控制口活着"与"计算域活着"，再逐个校验 FCLK 寄存器的读写性 |
| **失效条件** | 适用于 Zynq-7000（PS7）。Zynq UltraScale+ MPSoC 的时钟寄存器地址与门控机制不同（`CRL_APB`），但"内核会关掉未使用时钟"这个陷阱是一样的 |
| **已验证效果** | 定位后 8 张图 8/8 命中、`identical=1`；此前 DPU 任务全部超时 |
| **投入** | 定位约半天；修复是改一根网线（Block Design 里换时钟源） |

---

## 现象

DPU 的 **S_AXI 控制口完全正常**：签名寄存器 `0x40000000` 读得到 `0x0D9C13F1`，
`insmod dpu.ko` 成功。但一跑计算就超时：

```
DPU 任务超时、dpu_isr=0、AP_CTRL=0
```

> **这是 Zynq 上最容易被误判的一类故障**：寄存器能读能写，让人以为"IP 是好的、时钟是好的"。
> 实际上 IP 通常有**两个时钟域** —— 控制口（S_AXI）和计算域（m_axi / 2x）。
> **控制口活着完全不能证明计算域活着。**

## 根因

计算域的唯一时钟来源是一个 `clk_wiz`，而 `clk_wiz` 的输入接在 **FCLK_CLK1** 上。
`FCLK_CLK1` 被 Linux 内核的时钟框架（`clkc`）当作"未使用时钟"**门控关掉**了 ——
寄存器写入不保持，读回恒为 0。

完整证据链（每一条都是板上 `devmem` 实测）：

| # | 事实 | 推论 |
|---|---|---|
| 1 | DPU 签名寄存器读出 `0x0D9C13F1` | **S_AXI 控制口活着** |
| 2 | S_AXI 控制口时钟 = FCLK_CLK0（BD 网表确认） | 控制口依赖 FCLK0 |
| 3 | `FCLK0_CTRL(0xF8000170)` 在内核 `late_init` 之后仍读回 `0x00400A00` | **FCLK0 实测存活** |
| 4 | 早前 DPU 能跑计算（当时 m_axi 接的就是 FCLK0） | FCLK0 能进 PL 并驱动数据面 |
| 5 | DPU 任务超时、`dpu_isr=0`、`AP_CTRL=0` | **计算域死** |
| 6 | 计算域唯一来源 = `clk_wiz`，`clk_wiz` 输入 = **FCLK_CLK1** | 计算域依赖 FCLK1 |
| 7 | `FCLK1_CTRL(0xF8000174)` **写入不保持**，读回 `0x00000000` | **FCLK1 死亡** |

6 → 7 → 5 构成完整闭环：**FCLK1 是设计中唯一未被证明存活的时钟，而它恰好是计算域的唯一源头。**

## 排查步骤

### 第一步：分清两个时钟域

问自己一个问题：**"我读到的这个寄存器，属于哪个时钟域？"**
控制口（S_AXI）和计算域（m_axi、2x）通常不是同一个时钟。

### 第二步：用"写入后读回"判断 FCLK 是否真的活着

这是最直接的判据 —— **写进去读回来还是原值，才算活着**：

```sh
# FCLK0
devmem 0xF8000170 32 0x00201400 ; devmem 0xF8000170     # 读回应为 0x00201400
# FCLK1
devmem 0xF8000174 32 0x00201400 ; devmem 0xF8000174     # 若读回 0x00000000 → 被内核门控
```

> ⚠️ **"内核已经启动完"不等于"时钟被关掉了"**。不能只看 `late_init` 前后某个瞬间，
> 必须在**应用真正要跑的时候**再验一次。

### 第三步：确认时钟树

用脚本打印 `clk_wiz` 频率、各 IP 的时钟引脚及其驱动者（`inspect_bd_clocks2.py`），
确认计算域时钟的来源是**哪个 FCLK**。

### 第四步：若仍挂起，用 AP_CTRL 与中断计数二级鉴别

后台跑任务，同时读 `AP_CTRL(0x40000008)` 与中断计数：

| 观察 | 结论 | 下一步 |
|---|---|---|
| `AP_CTRL` bit0 置位 + 无中断 | 计算时钟域仍死（MMCM 未锁定） | 查 MMCM 参数 |
| `AP_CTRL` 全零 | 控制口写路径 / 复位问题 | 查 `proc_sys_reset` |

## 修复

把 `clk_wiz_0/clk_in1` 从 FCLK_CLK1 网**改接 FCLK_CLK0** 网。

选 FCLK0 的理由是**频率精确匹配**：`PRIM_IN_FREQ=50` 需要输入正好 50.000 MHz，
而 FCLK0 可以配成精确的 50.000 MHz（见下）。改完 FCLK_CLK1 网完全悬空，无害。

### 关键：FCLK0 的频率配方（Zynq-7000 时钟寄存器）

```sh
devmem 0xF8000008 32 0xDF0D          # 解锁 SLCR
devmem 0xF8000170 32 0x00201400      # FCLK0_CTRL
devmem 0xF800012C 32 0x01E00C40      # APER_CLK_CTRL：放开各外设时钟门控
devmem 0xF8000008 32 0x0000          # 重新上锁
```

`0x00201400` 的含义：**IO_PLL mux（bit21）+ DIV0 = 20**。
配套事实：**本板实测 IO_PLL = 1000 MHz（不是常见资料里的 500 MHz）**，
而 ARM_PLL = 666.666 MHz、DDR_PLL = 1066.666 MHz。

因此 `1000 MHz ÷ 20 = 50.000 MHz` —— **精确**，不是近似。
这一点很关键：`clk_wiz` 输入若不是精确 50.000，输出就无法做到精确的 100/200 MHz，
会直接触发 [DPU 推理结果非确定](dpu-nondeterminism-clock-ratio.md)。

> 验证输出频率的方法：改完频率**必须重新 `generate_target` 之后**再去读
> `CLKOUT3_ACTUAL_OUT_FREQ`。刚 `set_property` 完就读是空的，曾因此白白中断一次构建。

### 相关的 PL 复位时序

```sh
devmem 0xF8000240 32 0xF ; devmem 0xF8000240 32 0x0    # PL reset 脉冲
devmem 0xF8000004 32 0x767B                            # FPGA_RST_CTRL
```

## 提炼过程 —— 从哪些失败与观察中总结出来

1. **最初的错误方向**：因为控制口寄存器读得出来，一度认为"时钟没问题"，
   把时间花在驱动、内存、DMA 上。
2. **转折点**：把"IP 有几个时钟域"这个问题显式写下来，逐域核对 ——
   立刻发现"计算域的唯一源头恰好是唯一没被验证过的时钟"。
3. **最有价值的方法论**：**"写入后读回"是判断时钟是否存活的直接判据**，
   比看 dmesg、看驱动、猜 MMCM 参数都快。
4. **另一个副产品**：这条排查顺带确认了 IO_PLL 实际是 1000 MHz，
   纠正了"常见资料里 500 MHz"的想当然 —— 于是 FCLK0 才能做成精确的 50.000 MHz。
5. **教训**：此前"DPU 签名能读出来"被当成了 DPU 通路可用的证据。
   实际上它只证明了**控制口**可用。这个错误结论让后续排查偏离了很久。
