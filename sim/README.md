# sim/ —— 仿真与验证

赛题 3.3.5.1 要求提交"仿真或验证结果，说明功能正确性是如何确认的"。
本目录是这套验证体系的**第一层**（RTL 仿真），另两层见下文 §4。

---

## 1. 目录结构

```
sim/
├── run_sim.bat          参数化的 xvlog → xelab → xsim 运行脚本
├── README.md            本文件
└── logs/
    ├── fw_tb/           ✅ 当前 RTL 实测（2026-10-16）
    │   ├── sim_1_xvlog.log
    │   ├── sim_2_xelab.log
    │   └── sim_3_run.log
    └── cam_tb/          ⚠️ 历史归档（2026-09-13，旧版 RTL）
        ├── sim_1_xvlog.log
        ├── sim_2_xelab.log
        └── sim_3_run.log
```

testbench 源码仍在 `rtl/` 下（见根 [`README.md`](../README.md) §13 的目录对照说明）。

---

## 2. 如何运行

```bat
rem 默认跑 cam_tb2，日志落在 sim\logs
sim\run_sim.bat

rem 指定 testbench 与日志目录
sim\run_sim.bat fw_tb sim\logs\fw_tb
sim\run_sim.bat cam_tb sim\logs\cam_tb
```

| 参数 | 说明 |
|---|---|
| 第 1 个 | testbench 名：`fw_tb` \| `cam_tb` \| `cam_tb2` |
| 第 2 个 | 日志输出目录，默认 `sim\logs` |

**工具链路径不再是硬编码**：脚本默认找
`D:\vivado2019.1\VIVADO20191\Vivado\2019.1\bin`，
可以用环境变量覆盖：

```bat
set VIVADO_BIN=C:\Xilinx\Vivado\2019.1\bin
```

仓库根目录由脚本自身位置推导，所以**从任何目录检出都能直接运行**。
（改造前它放在 `rtl\` 下，且写死了 `E:\yoloProject\rtl` 与 `D:\vivado2019.1\...` 两个绝对路径，
别人无法使用。）

**退出码**：`0` = 跑完且打印了 `SIM_RESULT=PASS`；`1` = 编译/精化错误或未通过；`2` = 找不到工具链。

## 3. 三个 testbench 的验证状态（如实说明）

> 本节刻意区分"**当前 RTL 上通过了**"与"**曾通过/未完成**"。
> 一份把三者都写成"PASS"的表格会掩盖真实情况。

| testbench | 覆盖对象 | 检查内容 | **当前 RTL 状态** |
|---|---|---|---|
| **`fw_tb`** | `frame_writer` | 4 像素小端打包；`tuser` 复位写指针到 `FRAME_BASE` 并递增帧计数；帧内地址按 8 递增；AXI 写通道握手（`awvalid`/`wvalid`/`bready`）；**慢从机压力测试**（伪随机拉长 `awready`/`wready`/`bvalid`）不丢数不重复 | ✅ **通过**（2026-10-16 本次实测） |
| `cam_tb` | `ov5640_cam_top` | AXIS 打包、`sof` / `eol` 正确性 | ⚠️ **在当前 RTL 上会失败**（原因见 §3.2）；归档日志来自 2026-09-13 的**旧版 RTL** |
| `cam_tb2` | `ov5640_cam_top` | 每帧一个 `tuser`；`tlast` 落在每行第 1280 像素；像素数据匹配；**`tvalid` 保持期间 `tdata` 不变**（AXIS 协议）；FIFO 不溢出 | ⚠️ **未完成**（仿真时间不可接受，原因见 §3.3） |

### 3.1 ✅ `fw_tb` —— 通过，且修掉了一个测试台自身的 bug

实测输出：

```
[TB] frame_writer test start
[TB] beats=1280 expected=1280 errors=0
SIM_RESULT=PASS
$finish called at time : 235370 ns : File "E:/yoloProject/rtl/fw_tb.v" Line 158
```

**运行时发现的第一个结果其实是 `SIM_RESULT=FAIL`**，但错误信息很说明问题：

```
[TB] beats=1280 expected=1280 errors=0
[ERR] beat 640 addr got=08000000 exp=08001400
```

`beats` 与 `errors` 都正确，只有**地址**从第 640 拍开始不符。
而 `640 = LINES × PX_PER_LINE ÷ 4 = 2 × 1280 ÷ 4` —— **正好是第 2 帧的第一拍**。

**诊断结论：RTL 是对的，测试台的期望错了。**
`frame_writer` 在每个 `tuser`（帧首）把滚动窗口复位回 `FRAME_BASE`，这是它的设计意图
（让缓冲区始终以帧边界开头）；而测试台原来的期望是"地址永远递增"。

修正为按帧取模：

```verilog
exp_addr = 32'h0800_0000 + 8 * (i % (LINES * PX_PER_LINE / 4));
```

**这个案例本身值得记录**：它说明"仿真失败"不等于"设计错了" ——
**必须先判断是设计不符合规格，还是测试台的期望过时**。
判据是错误的具体形态（数据全对、只有地址在帧边界处不符）而不是"有没有报错"。

### 3.2 ⚠️ `cam_tb` —— 每行只发 16 像素，被 RTL 的毛刺过滤器滤掉了

`cam_tb` 的传感器模型每行只发 **16 个像素**（32 字节），共 4 行。

但当前 RTL 的 `ov5640_cam_top` 有一个**毛刺过滤器**：

```verilog
MIN_LINE_PX = 512;   // 一条真实行远大于 512，HREF 上的毛刺脉冲约 320
```

`MIN_LINE_PX` 的作用是滤除 HREF 每行附带的毛刺脉冲
（本板 HREF 一行内有多个脉冲，曾造成画面垂直重复 4 次）。

**16 像素 < 512，所以整行会被判定为毛刺而被丢弃**，永远不产生行结束信号，
测试台也就永远等不到它的 64 个像素。

> **归档的那个 PASS 日志来自 2026-09-13**，当时 RTL 还没有 `MIN_LINE_PX`。
> 因此那份日志**不能作为当前 RTL 的验证证据**，只作为历史记录保留。

**修复方向**：把每行像素数从 16 提到 512 以上（并在检查逻辑里同步该常量）。
`cam_tb2` 已经是这样做的，所以 `cam_tb` 实际上**已被 `cam_tb2` 取代**。

### 3.3 ⚠️ `cam_tb2` —— 仿真时间不可接受，未完成

`cam_tb2` 的设计本身是对的（它发完整的 1280 像素/行，并用伪随机 `tready` 停顿
压力测试 AXIS 握手），但它与当前 RTL 的两个参数**组合出了一个不可仿的规模**：

| 参数 | 值 | 来源 |
|---|---|---|
| `PX_PER_LINE` | 1280 | 必须匹配 RTL 的 `LINE_PX` |
| `LINES` | 65 | 必须 > RTL 的 `MIN_LINES_PER_FRAME = 64` |
| 需要的帧数 | **132+** | RTL **丢弃前 130 帧**（配置后的静默窗口） |

于是仿真至少需要：

```
130 帧 × 65 行 × (1280×2 + 10) 周期 ≈ 2200 万个 PCLK 周期 ≈ 940 ms 仿真时间
```

而测试台自己的超时保护设在 **120 ms** —— 也就是说它**注定超时**，
而且要在 CPU 上跑到那个点先得花很久。实测：**xsim 跑满 10 分钟 CPU 仍未完成**。

**这不是死循环，是规模问题。** 判别依据：仿真日志只打印了启动行，
而 CPU 时间持续增长、进程状态正常。

**改进方向（供后续修复）**：

1. **把"丢弃前 N 帧"做成 RTL 参数**（例如 `SKIP_FRAMES`），
   仿真时设为 0 或 2、综合时保持 130。
   这是最干净的解法 —— 静默窗口是**为软件启动准备的真实需求**，
   但仿真里没有软件要等，没必要付出这个代价。
2. 或者让测试台**只验证协议层**（`tdata` 稳定性、FIFO 不溢出），
   不要求 `tlast` 落在第 1280 像素，从而可以用更短的帧。

**当前处理**：`cam_tb2` 保留在仓库中作为**后续修复的起点**，
但**不计入已完成的验证**。它的检查项目前由 §4 的第二、三层覆盖。

## 4. 仿真在整个验证体系中的位置

RTL 仿真只是第一层。**功能正确性的主要证据来自更强的第二、三层**，
因为"仿真通过"证明的是"逻辑符合我的预期"，而"黄金比对通过"证明的是"硬件算得对"。

| 层 | 手段 | 覆盖什么 | 证据位置 |
|---|---|---|---|
| **1. RTL 仿真** | `fw_tb`（通过） | 自研 `frame_writer` 的打包、寻址、AXI 握手、背压 | 本目录 `logs/fw_tb/` |
| **2. 黄金参考逐字节比对** | 应用内建 `DETERM_CHECK`：同图连续推理两次，逐字节比较输出 | **硬件计算是否正确**；能同时发现时钟比例错误与输入缓冲被覆盖两类故障 | `data/` 与 [`../report/design_report.md`](../report/design_report.md) §5.2 |
| **3. 8 图标准答案验收** | 8 张标准图片，核对检出类别与确定性 | 端到端功能正确性 | [`../data/validation_scorecard.md`](../data/validation_scorecard.md) |

**为什么第 2 层比仿真更有说服力**：

```
DETERM_CHECK: run1=-7891502 run2=-7891502 identical=1
BOXES: raw=6 after_nms=3
```

它检验的是**真实硬件在真实配置下**的输出确定性，而且这条自检
**曾经发现过一个仿真完全不可能发现的问题** ——
DPU 的 2x 时钟不是 `m_axi` 时钟的精确 2 倍时，输出会变成随机垃圾
（特性开关全对、加载也成功，只有输出每次不同）。
仿真的 RTL 工程里没有 DPU IP，所以这个问题只能在上板后用这条自检抓到。

**如实说明**：本项目的仿真是"**局部**仿真"（只覆盖自研 RTL），
不覆盖 DPU IP 内部、不覆盖 PS 侧软件。这是这类项目的常态，
但应当说明清楚，避免让"有仿真"听起来像"全链路仿真"。
